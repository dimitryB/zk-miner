# HemiProve — Contract Interaction Guide

Self-contained reference for `zkui` (job-submission frontend/CLI) and `zkminer` (prover daemon) integrations.

**Target chain**: any EVM. Anvil (31337), Hemi testnet (743111), Hemi mainnet (43111).
**Solidity**: 0.8.38. **Proxy pattern**: UUPS + diamond-lite router. **Reentrancy guard**: shared TSTORE (Cancun).

## 2. The two lifecycles

### Prover onboarding (once per prover address)

```solidity
// 1. Acquire HEMI (faucet, mint, buy)
IERC20(HEMI_TOKEN).approve(STAKING, stakeAmount);

// 2. Stake
IHemiProveStaking(STAKING).stake(proverAddress, uint128(stakeAmount));

// 3. Advance one block before `claimJob`. On live networks the
//    next block already qualifies; on anvil: `cast rpc anvil_mine 1`.
//    No wall-clock wait at claim time (there is no minimum staking age).
```

**Important**: `stake(prover, amount)` takes the prover address explicitly, but only the prover itself may call it (`msg.sender == prover`, else `Unauthorized`); `msg.sender` funds the tokens.

### Job lifecycle (per job)

```
caller: submitJob(descriptor, auction, cycle, bid) → jobId
prover: claimJob(jobId, priceFloor, premiumFloor)   (locks collateral, sets deadline; the floors
         are the exact eth_call quote at a mined block, §4)
         → wait for the receipt; re-read jobs(jobId).prover == you   (§3a, broadcast rule)
prover: fulfillJob(jobId, descriptor, publicValues, proof)
         → binding check → JobFulfilled + HEMI to the prover
```

A job reserved to its prover (a NONE job, or the assigned prover inside its exclusivity window) can also be claimed and fulfilled in one transaction, `claimAndFulfillAssigned` (§4), under the rules of the broadcast rule's one exception (§3a).

**Pricing.** A job is a reverse (ascending-price) Dutch auction: its price rises from `minPrice` to `maxPrice` over `rampUpPeriod`, measured in job-local time (§4), and the first claim locks it at the price at inclusion. A competitive job (`underbidWindow > 0`) adds bidding below that ceiling (§4): it is claimable directly at the ramp price until its first bid, and from the first bid of a round it is won by bidding.

Alternate exits: `slashAndReopen(jobId)` (any keeper, 30 min + 30 s after the effective deadline: `getJobStatusView(jobId).slashOpensAt`), `releaseJob(jobId)` (the prover of a Locked job, voluntary, until one second before the end of its 30-min grace: the fulfil is accepted one second longer), `refundBid(jobId)` (the live bidder of an Open job, free, and only while a governance cause holds: a live bid is otherwise binding), `cancelJob(jobId)` (caller only), `gracePauseRelease(jobId)` (the job's prover or its authorized claiming operator once a pause has lasted more than 15 min; the live bidder of an Open job only once a pause has lasted more than 7 days), `graceRelease(jobId)` / `graceReleaseWithDescriptor` (anyone, while the job's adapter is disabled or its verifier blacklisted), `cancelStaleJob(jobId)` (anyone, for a job stale under governance or at the reopen limit). Costs and effects: §6.

## 3. `submitJob` — the payload

Signature (Core facet, called via router):

```solidity
function submitJob(
    JobDescriptor calldata descriptor,
    AuctionConfig   calldata auction,
    CycleConfig     calldata cycle,
    CompetitiveBidConfig calldata bid
) external whenNotPaused nonReentrant returns (bytes32 jobId);
```

Other submit entry points, validated identically (binding rules included): `submitJobSimple(descriptor, presetName)`, `submitJobBatch(descriptors[], configs[], cycleConfigs[], bidConfigs[])` (≤ `MAX_BATCH_SIZE` = 10) and

```solidity
// The binding words are parameters.
function submitJobDefault(
    bytes32 programId, bytes32 proofSystemId, bytes calldata inputData, address callbackContract,
    bytes32 expectedJournalHash, bytes32 journalFields
) external whenNotPaused nonReentrant returns (bytes32 jobId);   // the "standard" preset; assignedProver = 0, so a NONE call
                                                                  // (a binding marker alone included) reverts
```

### `JobDescriptor` (10 fields — see `src/libraries/Types.sol`)

```solidity
struct JobDescriptor {
    bytes32 programId;           // RISC Zero imageId, SP1 vkey, OpenVM keccak256(abi.encode(appExeCommit, appVmCommit)):
                                 //   the ONLY tie to a binary (§3a, prover checklist step 2a)
    bytes32 proofSystemId;       // keccak256("risczero.groth16.v1"), keccak256("sp1.groth16.v1"), keccak256("sp1.plonk.v1"),
                                 //   keccak256("openvm.halo2.v1") (743111), or CUSTOM_VERIFIER: the zkVM and the wrapper of its seals
    address callbackContract;    // address(0) = no callback; else onProofVerified is called at most once, at fulfil, if the
                                 //   address has code (nothing checks it at submit; a codeless address gets CallbackFailed, §5)
    address assignedProver;      // address(0) = any prover; else see exclusivity and NONE (§3a)
    bytes32 tag;                 // arbitrary metadata (e.g., off-chain job hash)
    bytes   inputData;           // the guest input / a hint for provers (opaque to the protocol; hashed)
    bytes   callbackExtraData;   // extra bytes forwarded to the callback
    bytes   extraVerifierData;   // adapter-specific data (OPENVM_HALO2_V1: abi.encode(appExeCommit, appVmCommit);
                                 //   CUSTOM_VERIFIER: the verifier address + data)
    bytes32 expectedJournalHash; // the journal binding (§3a)
    bytes32 journalFields;       // the FIELDS ranges, and in slot 0 an optional binding marker (§3a);
                                 //   0 = FULL (or NONE when the hash is 0 too)
}
```

`inputData.length + callbackExtraData.length + extraVerifierData.length` must be ≤ `MAX_DESCRIPTOR_BYTES` = 65,536, else `DescriptorTooLarge(size, max)` at submit.

**The journal is capped too.** Every fulfil path reverts `JournalTooLarge(length, max)` when `publicValues` is longer than `MAX_JOURNAL_BYTES` = 32,768 bytes, for every prover. op-geth refuses a transaction larger than 131,072 bytes (RLP of the signed transaction). With both caps, every fulfil path leaves room for the seal:

| Fulfil path | Fixed calldata | Descriptor at the cap (ABI-padded, upper bound) | Journal at the cap | Tx envelope (upper bound) | Before the seal | Room for the seal (at least) |
|---|---:|---:|---:|---:|---:|---:|
| `fulfillJob` | 612 | 65,629 | 32,768 | 256 | 99,265 | 31,807 |
| `fulfillJobHashed` | 548 | 65,598 (`inputData` is not sent) | 32,768 | 256 | 99,170 | 31,902 |
| `fulfillJobBatch`, one job | 868 | 65,629 | 32,768 | 256 | 99,521 | 31,551 |
| `claimAndFulfillAssigned(jobId, P, Q, …)`: a reserved job only, within the rules of §4 | 676 | 65,600 (the measured worst-case padding, `test/fixes/DescriptorCap.t.sol`) | 32,768 | 256 | 99,300 | 31,772 |
| `multicall([slashAndClaim(jobId, f), fulfillJob])`: **unsafe, never send** (below) | 932 | 65,629 | 32,768 | 256 | 99,585 | 31,487 |
| `multicall([claimJob(jobId, P, Q), fulfillJob])`: **unsafe, never send** (below) | 964 | 65,600 (the measured worst-case padding, `test/fixes/DescriptorCap.t.sol`) | 32,768 | 256 | 99,588 | 31,484 |

The `multicall` rows are size bounds only. That transaction carries the seal before your lock exists, so anyone staked can copy it from Hemi's public mempool and settle the job with it (§3a, broadcast rule). The safe paths are the first three rows; the smallest room among them is 31,551 B. `claimAndFulfillAssigned` (`fulfillJob`'s calldata plus the two 32-byte floors) also carries the seal before a lock exists, but only on a job nobody else can lock: it is the one exception to the broadcast rule, and only where §4 says it is safe. The claim floors account for 64 B of `claimJob(jobId, P, Q)` and 32 B of `slashAndClaim(jobId, f)`: the unsafe claim multicall leaves ≥ 31,484 B, the smallest room of the tabled rows (the untabled, equally unsafe `multicall([claimJobBatch([jobId], [P], [Q]), fulfillJob])` leaves ≥ 31,292 B: its claim leg is 292 B instead of 100 B). The descriptor column of the other rows uses the looser 3 × 31 B padding bound (65,629 B), so their room is understated by 29 B.

The governance seals are far smaller: RISC Zero Groth16 260 B, SP1 Groth16 356 B, SP1 PLONK 964 B, RISC Zero PoVW 384 B, OpenVM Halo2 1,760 B (OpenVM is registered on 743111 only). A `fulfillJobBatch` of several jobs and other wrappers add their own bytes; one job per transaction always fits. A `CUSTOM_VERIFIER` seal is the caller's choice: a verifier that needs a seal larger than the room makes a job nobody can deliver. Measure before claiming (§3a, prover checklist).

Well-known `proofSystemId` constants (see `src/libraries/Constants.sol`). Each names the zkVM and the wrapper of its seals: the wrapper fixes the seal format, so one id never accepts another wrapper's seal.

### 3a. Journal binding (`expectedJournalHash`, `journalFields`)

**The binding is the only payout gate.** Before any state write, payment or callback, the router checks the journal (`publicValues`) against the binding the caller committed. A mismatch reverts `JournalMismatch(expected, actual)` and nothing is paid. The journal cap and the binding run first, **before** the verifier call, so a wrong journal fails without spending the verifier's gas. Callbacks are observational: a rejecting callback never withholds payment (§5). The check runs on every fulfill path: `fulfillJob`, `fulfillJobHashed`, `fulfillJobBatch` and `claimAndFulfillAssigned`.

Why it exists: the verifier attests only "program P accepted journal J". Without a binding, any valid proof of the program pays: one replayed from another job, copied from another chain, or freshly made on a trivial input. The binding makes the job pay only for a proof whose journal carries the job's input. A binding marker (below) goes further: it makes the job pay only for a proof made for that job and for the prover holding its lock.

The mode is derived from the two words; there is no mode byte (with a binding marker in slot 0, `journalFields` below means the bits after slot 0):

| `expectedJournalHash` | `journalFields` | Mode | Fulfill check |
|---|---|---|---|
| ≠ 0 | 0 | **FULL** | `keccak256(abi.encode(JOURNAL_PREDICATE_DOMAIN_V1, proofSystemId, programId, publicValues)) == expectedJournalHash`. Use it when the whole journal is known at submit (you simulated the guest). |
| ≠ 0 | ≠ 0 | **FIELDS** | `keccak256(concat of the used ranges of publicValues, in slot order) == expectedJournalHash`. Use it when the output is not known: pin the journal bytes that encode the input, leave the result free. |
| 0 | 0 | **NONE** | No check. Allowed only with `assignedProver != 0`: bilateral trust between the caller and that prover. |
| 0 | ≠ 0 | — | Rejected at submit. |

`JOURNAL_PREDICATE_DOMAIN_V1 = keccak256("HemiProve.JournalPredicate.v1")`.

**Submit rules** (every submit entry point), reverting `InvalidJournalBinding(reason)`:
1. `journalFields != 0` with `expectedJournalHash == 0`.
2. FIELDS with no used slot (`uint256(journalFields) & JOURNAL_FIELDS_LENGTH_MASK == 0`): it would bind the empty string.
3. NONE with `assignedProver == 0`. `submitJobDefault` has no assigned prover, so it cannot create a NONE job.
4. NONE with a `CompetitiveBidConfig` (`underbidWindow != 0`).
5. FIELDS with a used slot whose `offset + length` exceeds `MAX_JOURNAL_BYTES` = 32,768: only a journal the fulfil paths refuse could satisfy it. Under the journal-prefix marker the ranges count from byte 64, so the bound is 32,704. Unused slots (length 0) are not checked.
6. The proof-nonce marker (`0xfffffffe`) on a `proofSystemId` other than the two SP1 ids, `SP1_GROTH16_V1` and `SP1_PLONK_V1`.
7. `OPENVM_HALO2_V1` (its verifier takes exactly 32 public-value bytes): the journal-prefix marker (`0xffffffff`; its 64-byte prefix cannot fit), or a used FIELDS slot ending past byte 32 (`offset + length > 32`, in place of 5).

With a binding marker, rules 1 to 5 (and 7's range rule) apply to the bits after slot 0. The checks run in the order 6 or 7 (the marker), then 1, 3, 4 when `expectedJournalHash == 0`, then 2, then 5 or 7 (the ranges). A FULL job binds a hash, so its journal length is unknown at submit: a FULL job whose journal is longer than the cap (for `OPENVM_HALO2_V1`, not exactly 32 bytes) can never be fulfilled.

**`journalFields` packing.** 8 slots × 32 bits. Slot `i` occupies bits `[255 − 32i .. 224 − 32i]`, so slot 0 is the top 32 bits. Each slot is `(uint16 offset << 16) | uint16 length` over `publicValues`. Length 0 = unused slot (its offset is ignored). Ranges may overlap and need not be sorted; the hash follows slot order.

```solidity
// slot i holds (offset_i, length_i)
bytes32 journalFields = bytes32(
    (uint256((off0 << 16) | len0) << 224) |
    (uint256((off1 << 16) | len1) << 192)    // ... up to slot 7: << 0
);
// FIELDS hash: the plain keccak of the pinned bytes, no domain tag
bytes32 expectedJournalHash = keccak256(abi.encodePacked(
    journal[off0 : off0 + len0],
    journal[off1 : off1 + len1]               // ... in slot order
));
```

A requester that knows the input-side values computes the same hash without the journal, as `keccak256(abi.encodePacked(field0, field1, ...))` of those values in the guest's byte encoding. A used range that ends past `publicValues.length` is a mismatch, reported as `JournalMismatch(expectedJournalHash, 0)`; it is never truncated.

**Binding markers (slot 0): a proof made for this job and this prover.** Without a marker a job binds a statement, and any proof of that statement settles it (below, "What a binding does not do"). Slot 0 of `journalFields` (its top 32 bits) can instead hold one of two markers. A marker holds no range: the mode table and the submit rules then apply to slots 1..7, and FIELDS ranges sit there. Both checks run at fulfil, on every path, before the statement binding, the governance errors, the gas preflight and the verifier call, so a wrong proof costs no verifier gas; a mismatch reverts and nothing is paid.

| Slot 0 (`uint256(journalFields) >> 224`) | Marker | Proof systems | Fulfil check | Mismatch |
|---|---|---|---|---|
| `0xffffffff` (`JOURNAL_PREFIX_MARKER`) | journal prefix | any but `OPENVM_HALO2_V1` (submit rule 7) | `publicValues[0:64] == abi.encode(jobId, job.prover)`: the jobId, then the prover's address as a full word (12 zero bytes, then the address; dirty high bytes are refused). FULL and FIELDS then apply to `publicValues[64:]` only: the FULL hash is over that slice, FIELDS offsets count from byte 64 | `JournalPrefixMismatch(jobId, prover)` (also for a journal shorter than 64 bytes) |
| `0xfffffffe` (`PROOF_NONCE_MARKER`) | SP1 proof nonce | `SP1_GROTH16_V1` and `SP1_PLONK_V1` only (submit rule 6) | `proofBytes[68:100]`, the nonce word of the SP1 v6 seal under either wrapper (both verifiers read their public input 4 there: selector, exit code, VK root, nonce, then the Groth16 or PLONK proof), equals `getProofNonce(jobId, job.prover).nonce`. FULL and FIELDS apply to the whole journal | `ProofNonceMismatch(expected, actual)` (`actual` = 0 for a seal shorter than 100 bytes) |

- **"The prover" is `job.prover`**, the staked address that holds the lock: the caller of `claimJob` or `claimAndFulfillAssigned`, the `prover` argument of `claimJobDelegated`, the winner of `settleBid`. Never an operator key: an operator that serves several staked provers proves once per prover.
- **A marker with no statement binding** (`expectedJournalHash == 0`, nothing after slot 0) is NONE and keeps NONE's rules (an assigned prover, no bidding: rules 3 and 4), so an open job always carries a statement binding. `submitJobDefault` (no assigned prover) can make FULL or FIELDS jobs with a marker, never a marker alone. A marker is part of `journalFields`, so `descriptorHash` authenticates it.
- **The requester computes the binding as for an unbound job** whose journal is the part after the prefix (the jobId and the prover are not in the descriptor: the router supplies them at fulfil). Examples: prefix + FULL, `journalFields = bytes32(uint256(0xffffffff) << 224)` and `expectedJournalHash = keccak256(abi.encode(JOURNAL_PREDICATE_DOMAIN_V1, proofSystemId, programId, output))` with `output` the journal after its first 64 bytes; prefix + FIELDS on the output's first word, `journalFields = bytes32((uint256(0xffffffff) << 224) | (uint256(32) << 192))` (slot 1 = `(0, 32)`, i.e. journal bytes 64..96) and `expectedJournalHash = keccak256(abi.encodePacked(output[0:32]))`; nonce + FULL on SP1, `journalFields = bytes32(uint256(0xfffffffe) << 224)` with the FULL hash over the whole journal.
- **The journal prefix in the guest.** The host passes the 64-byte prefix `abi.encode(jobId, prover)` as input; the guest commits it first, as raw bytes, then its own output: RISC Zero `env::read_slice` and `env::commit_slice(&prefix)`, SP1 `sp1_zkvm::io::read_vec()` and `sp1_zkvm::io::commit_slice(&prefix)`. Never `commit` (it adds serde or bincode framing, below). An ABI guest may instead encode the prefix as the first two static words of its output (`abi_encode_params` of a tuple that starts with `(bytes32 jobId, address prover)`); never alloy `abi_encode()` of a struct with a dynamic member, whose leading `0x20` head-offset word displaces the prefix. The guest need not check the prefix (the router does), and the jobId is known once the submit is mined (it depends on the job index), so prove after the submit. A program that does not commit the prefix can never satisfy a prefix job: execute before you claim (checklist step 2).
- **The SP1 proof nonce.** `getProofNonce(bytes32 jobId, address prover) returns (uint256 nonce, uint32[4] limbs)` (`0x8162527d`, FulfillCycle facet, at the router) computes it with the same function as the fulfil check:
  ```
  B      = keccak256(abi.encode(PROOF_BINDING_DOMAIN_V1, block.chainid, router, jobId, prover))
  limb_i = (uint256(B) >> (96 − 32·i)) & 0x3fffffff     // i = 0..3: the low 128 bits of B as four big-endian
                                                          // 32-bit words, each masked to 30 bits (below the KoalaBear prime)
  nonce  = Σ limb_i << (31·(3 − i))                      // limb 0 most significant: SP1's own packing
  ```
  `PROOF_BINDING_DOMAIN_V1 = keccak256("HemiProve.ProofBinding.v1")` = `0xd9d0b06eb5709bf8ec053d0c242bcb55e68556ff65978aa7ecadc92fd79cde4a`; `router` is the router proxy. `limbs` is exactly the argument of the SP1 SDK's `with_proof_nonce` (prover checklist step 7a), in Groth16 and PLONK mode alike. The view does not read the job: it answers for any jobId and address, a job not yet submitted included, and says nothing about whether the job carries the marker. Cross-check vector: chain id 743111, router `0x1111…11`, jobId `0x2222…22`, prover `0x3333…33` give B = `0x57ea0cc5979a420f66d1c66a3577428918d1097b68ce9cf6de4353ab566b4653`, limbs `[0x18d1097b, 0x28ce9cf6, 0x1e4353ab, 0x166b4653]`, nonce `0x31a212f6a33a73d8f21a9d5966b4653`. On your own node:
  ```bash
  cast call "$HEMI_PROVE" 'getProofNonce(bytes32,address)(uint256,uint32[4])' "$JOB_ID" "$STAKED_PROVER" --rpc-url "$RPC"
  ```
- **Reserved values.** Slot-0 values with offset `0xffff` and length `0xfff0` to `0xfffd` stay refused at submit (rule 5 with a hash, 7 on `OPENVM_HALO2_V1`; rule 1 without one) and are kept for later markers.
- **OpenVM jobs carry no marker**: the prefix is refused (rule 7) and the nonce marker is SP1's (rule 6). An `OPENVM_HALO2_V1` job binds the statement only (FULL over its 32-byte journal, or FIELDS within it), so an OpenVM proof settles any job with the same statement: the broadcast rule (below) is the only protection of an OpenVM proof.
- **Recommendation for requesters of open jobs:** use a marker, the journal prefix for a program that commits it, the proof nonce for SP1 (under either SP1 id). Prove-first provers can serve such jobs (the jobId and their own address are known before the claim).

**Pin exactly the bytes the guest commits, framing included.** The router hashes raw journal bytes; it does not know your guest's serializer:
- **RISC Zero `env::commit(&value)`** writes risc0 serde: every `u8` is padded to a little-endian `u32` word. A `[u8; 32]` committed this way is 128 journal bytes (byte `k` at offset `4k`, followed by three zero bytes). `u32` is 4 bytes LE, `u64` two LE `u32` words. Every `Vec`, `String` and slice gets a length prefix.
- **SP1 `sp1_zkvm::io::commit(&value)`** writes bincode: fixed-width little-endian integers, `[u8; N]` as N raw bytes, and a `u64` LE length prefix before every `Vec`/`String`.
- Under both `commit` forms, alloy `B256` and `Address` (and any byte newtype whose serde form is a byte string) are **length-prefixed**: a `B256` is not 32 raw bytes at the offset you expect. Commit `[u8; 32]`, or use `commit_slice`.
- **`env::commit_slice` / `io::commit_slice`** write raw bytes. A guest that commits an ABI-encoded value this way (alloy) has a raw ABI journal: static fields are 32-byte words in declaration order. alloy `abi_encode()` of a struct (or tuple) that has **any dynamic member** starts with a `0x20` head-offset word, so the struct's first field is at byte 32, not 0, and each dynamic member is a head offset plus a length word plus padded data. `abi_encode_params()` / `abi_encode_sequence()` and all-static structs have no outer offset word.

Compute `expectedJournalHash` over the framed bytes, never over a re-encoding (`abi.encode(seed)` is not what `env::commit(&seed)` wrote). Read the framing off a real journal your guest produced.

**Worked examples.** These are illustrative: check your guest's exact struct and serializer before pinning anything.

- *HashChainConsumer (in this repo).* proof-gen `methods/sha256-iter-guest` commits, with `env::commit_slice`, `seed (32) || iterations as u32 LE (4) || final_hash (32)`. Pin `[0, 36)`: `journalFields = bytes32(uint256(36) << 224)` = `0x00000024 00…00`, `expectedJournalHash = keccak256(abi.encodePacked(seed, iterationsLE))`. See `src/demo/HashChainConsumer.sol` `_journalBinding`. Every input byte is fixed-size and pinned, so the pin determines the input.
- *OxygenConsumer (in this repo).* 256-byte ABI journal `(version, network, prevStateRoot, newStateRoot, blockHash, height, prevBlockHash, expectedBits)`, eight static words. The demo pins every word it knows at submit: `[0, 96)` (version, network, prevStateRoot) and `[128, 224)` (blockHash, height, prevBlockHash), i.e. slots `(0, 96)` and `(128, 96)`: `journalFields = 0x00000060 00800060 00…00`, `expectedJournalHash = keccak256(abi.encode(version, network, prevStateRoot, blockHash, height, prevBlockHash))`. `blockHash` is the **canonical** hash of the block at that height, named by the owner or its keeper: `proveNextBlock(uint64 targetHeight, bytes32 blockHash)` (owner or `keeper()` only, `NotOwnerOrKeeper` otherwise; `ZeroBlockHash()` for 0), in the journal's byte order (the order of `latestBlockHash`), taken from hVM's Bitcoin view or a Bitcoin node for a height with enough confirmations (6 or more on mainnet); the contract itself reads no hVM precompile. Given the block, `newStateRoot` is deterministic, so only a proof of this transition of the canonical block pays. The callback re-checks version, network, prevStateRoot, prevBlockHash and height, but not `blockHash` (the pin guarantees it for the contract's own jobs), and it does not check `expectedBits` against the previous block (that check would refuse canonical testnet minimum-difficulty blocks, which are paid anyway, and leave the consumer stuck). The owner's `cancelCurrentJob()` resets a stalled job. A pin of only `[0, 96)` and `[160, 224)` would leave `blockHash` (and with it `newStateRoot`) to the prover: at a low-difficulty height a forged fork block that extends `prevBlockHash` would settle, and the consumer would adopt it.
- *op-succinct-style aggregation output.* An ABI-encoded static struct such as `(bytes32 l1Head, bytes32 l2PreRoot, bytes32 l2PostRoot, uint64 l2BlockNumber, bytes32 rollupConfigHash, bytes32 multiBlockVKey, address proverAddress)` is 7 words at offsets 0, 32, …, 192. `OPSuccinctFaultDisputeGame` rebuilds `proverAddress` from `msg.sender` and checks the proof against its own `rootClaim`, so the requester knows **every** word at submit: `proverAddress` is the address that will submit the proof to the game, and `l2PostRoot` is the claimed output root. Pin all seven words (FULL is simplest: the whole journal is known). Leaving `proverAddress` free lets a prover settle a proof only it can use: the requester pays, and a challenger-prover can fulfil and withhold.
- *SP1 Blobstream-style header range.* An ABI-encoded `(bytes32 trustedHeaderHash, bytes32 targetHeaderHash, bytes32 dataCommitment, uint64 trustedBlock, uint64 targetBlock, uint256 validatorBitmap)` is 6 words. The requester fixes the trusted header and both heights; the prover produces the target header hash, the data commitment and the bitmap. Pin slot 0 = `(0, 32)` and slot 1 = `(96, 64)`: `journalFields = 0x00000020 00600040 00…00`, `expectedJournalHash = keccak256(abi.encodePacked(trustedHeaderHash, uint256(trustedBlock), uint256(targetBlock)))`.

#### Binding cookbook

FIELDS binds the bytes at the pinned offsets and nothing else: not the journal length, not an unpinned byte, not a guest input the guest does not commit. The rules:
1. **The pinned ranges must determine the input uniquely.** Before going live, run a **mutation check**: change each input field in turn, rebuild the journal (run the guest, or encode it exactly as the guest does), and confirm the FIELDS hash changes. "Test against a real journal" alone is not enough: a pin over a constant passes it.
2. **Fixed-size data first.** A variable-length field placed before a pinned range shifts every later offset, so for another input the pin covers other bytes. Put the fixed-size input words first, or have the guest commit a fixed-size digest of its input (for example `sha256(input)`) as its first journal word and pin that word.
3. **Pin the length (and the ABI head offset) of variable-length data.** A pin over the data of an ABI `bytes` / `string` / array, or over a raw `commit_slice(input)`, that leaves out the length binds only a prefix: a longer input with the same first bytes matches. Pin the length word, and in ABI encodings the head-offset word that points to it, or commit a digest instead.
4. **Know the serializer's framing** (above): length prefixes under `commit`, the alloy `0x20` head offset, risc0 serde's 4-byte words.
5. **Pin every word the consumer rebuilds or knows at submit**: anything the consuming contract recomputes from its own state or from `msg.sender`, or that the requester knows when it submits (op-succinct `proverAddress` and the claimed root; Oxygen's canonical `blockHash`). An unpinned word is the prover's choice.
6. **Never pin bytes only the computation determines and you cannot predict** (the result): a binding no honest proof satisfies gets the claiming prover slashed (a known residual: `DEPLOY_RUNBOOK.md`, threat model, residual 6).

**Negative examples.** Each pin below also settles a proof of a different input.

| Journal | Wrong pin | What else matches | Fix |
|---|---|---|---|
| `commit_slice(input) ‖ commit_slice(result)`, `input` of variable length | `[0, len(input))` | a longer input with the same prefix; the result moves | the guest commits `sha256(input)` first; pin `[0, 32)` |
| ABI `(bytes input, bytes32 result)` | the data words of `input` only | an input with the same leading bytes and a different length | also pin the head offset and the length word |
| alloy `abi_encode(Out { bytes32 inputHash; bytes data })` | `[0, 32)`, "the first field" | everything: `[0, 32)` is the constant `0x20` head offset | pin `[32, 64)` |
| `env::commit(&input_b256)` | `[0, 32)` as the raw 32 bytes | the pin covers the length prefix and part of the value | commit `[u8; 32]` via `commit_slice`, or pin the framed bytes |
| any | a version or magic word only | any input | pin the input words |
| op-succinct output | `proverAddress` left free | a proof only its prover can submit to the game | pin `proverAddress` (192, 32) and the claimed root |
| Oxygen journal | `blockHash` left free | a forged fork block at a low-difficulty height | pin the canonical `blockHash` (`[128, 160)`), named at submit from hVM's Bitcoin view or a Bitcoin node at a confirmed height |

**What a binding does not do.**
- Without a binding marker, it binds the job to a *statement*, not to the job, the chain or the prover. A proof of the same statement settles every such job that binds it. That reuse is accepted by design: the buyer gets the result it asked for. It includes an identical statement proven on another chain (for example the 743111 rehearsal), and a late fulfiller's public proof taken over by a `slashAndClaim`-er (§6, "Late locks"). It also includes any proof broadcast before its prover's lock was mined: the verifier sees no prover, and fulfil checks only `msg.sender == job.prover`, so whoever holds the lock first is paid (the broadcast rule below).
- With a binding marker, the job pays only for a proof made for it and for the prover holding its lock: a proof of another job, another chain or another prover is refused (`JournalPrefixMismatch`, `ProofNonceMismatch`). What a marker does not do: a bound proof is still a valid proof of its statement elsewhere (natively, and for an unbound job of the same statement); the caller of an Open job can still cancel it ahead of your claim and keep a result you broadcast; a staked third party can still lock the job first (it cannot settle: it pays the release penalty or the slash, and your proof stays valid for you when the job reopens). The router does not check that the program commits the prefix, nor what the guest computed: a prefix job whose program does not commit it can never be fulfilled (a caller-side residual, like any binding no honest proof satisfies). So the broadcast rule stays for every job.
- The router cannot tell whether the pinned bytes depend on the input. Pinning a constant header or a version word binds nothing: that is integrator misuse. Pin the input.
- FIELDS costs gas linear in the pinned bytes: a few thousand gas for typical pins. The worst case is 8 slots of 32,768 bytes (a 256 KiB buffer). `test/fixes/JournalCap.t.sol` measures the execution gas of a whole `fulfillJob` (mock verifier, warm state, deploy profile, intrinsic calldata gas excluded) with a 32,768-byte journal: FIELDS `(0, 1)` 525,453; FULL 549,617; FIELDS 8 × `(0, 32,768)` 883,419 (the pin buffer adds about 358k); the same with a 64 KiB `inputData` 1,192,508; and with a callback that receives the journal as well 1,470,972. These are logged, not pinned (they move with the compiler). The ranges are in the descriptor, so a prover sees the cost before claiming, and it counts toward the fulfil gas limit (§9).

**NONE jobs** (no binding, `assignedProver != 0`):
- Only the assigned prover can ever lock the job: every claim path (`claimJob`, `claimJobDelegated`, `claimJobBatch`, `slashAndClaim`, `claimAndFulfillAssigned`) reverts `ExclusivityActive(jobId, assignedProver)` for anyone else (`claimJobBatch` reports that job as `false`), for the job's whole life, including after every slash, release and grace reopen. `exclusivityDuration` is ignored.
- No `CompetitiveBidConfig` (rule 4), so no bids. The job never feeds the EWMA price oracle (`excludeFromEwma` is forced).
- After a NONE prover's `releaseJob`, the job sits Open: only that prover may claim it, and it is in its 1h release cooldown. After a third-party slash, the job waits for the assigned prover or a cancel.
- **Price it fixed: `minPrice == maxPrice`.** Nobody else can claim, so the assigned prover can wait for the top of a Dutch ramp: a ramp always settles at `maxPrice`. After any slash, `cancelJob` is refused for `MIN_REOPEN_CANCEL_DELAY` = 24h (`CancelDelayNotMet`) while only the assigned prover may re-lock. A defaulting assigned prover gets none of its penalty back (the bonus share is burned), except the keeper share (`max(2% × collateral, 0.5 HEMI)`) when it slashes itself; and its speed premium is one budget across reopens (§5).
- Read the flag with `getJobExtras(jobId)` (§7).

**Prover checklist: before you claim**. Do all of this before `claimJob`, `claimJobDelegated`, `submitBid`, `slashAndClaim` or `claimAndFulfillAssigned`, because a claim you cannot deliver costs 5% at best (an immediate release) and 100% at worst (the slash):
1. Read the whole descriptor from the submit calldata (and check that it hashes to the job's `descriptorHash`, §5: a decoded descriptor that does not is not this job's), and fetch the **full witness** (`inputData`, or the off-chain data it points to). If the witness is only available after you claim, the caller can withhold it after your claim: price that risk or skip the job.
2. **Check the binary (2a), then execute the guest** on that witness (no proof yet). The journal must match the binding (the FULL hash, or the FIELDS hash of the pinned ranges). For a journal-prefix job, execute with your own prefix: `journal[0:64]` must be `abi.encode(jobId, yourStakedProver)` and the binding applies to the rest (a program that does not commit the prefix can never be fulfilled).
   **2a.** **Check that the binary is the job's program, before you run it.** `programId` is the only thing that ties a binary to the job; the verifier checks the proof against it at fulfil. RISC Zero: `compute_image_id(elf)` (risc0-zkvm 3.0.x; the `Digest` bytes, as in `ImageID`) equals `programId`. SP1: `vk.bytes32()` of your SDK's `setup(elf)` equals `programId`, with the SDK of step 7. OpenVM: `keccak256(abi.encode(app_exe_commit, app_vm_commit))` of `cargo openvm commit --exe <program>.vmexe`, under the program's `openvm.toml` and run in a directory of your own (step 9), equals `programId`, and `extraVerifierData` is `abi.encode(app_exe_commit, app_vm_commit)`. **Check and run only the built artifacts** the requester publishes (an ELF; for OpenVM a `.vmexe` and its `openvm.toml`), kept as plain files in a per-job directory. On a host that holds your prover key or can reach your signer, never build a requester's source, and never run `cargo` (or `cargo openvm`, `cargo prove`, `cargo risczero`) with a working directory inside or under any requester-supplied tree (its crate, a clone, an unpacked archive): a build runs the crate's build scripts and procedural macros, and rustup and cargo read `rust-toolchain.toml` and `.cargo/config.toml` from the working directory and every parent, whatever `--manifest-path` says (a toolchain `path` replaces `cargo` itself and an `[alias]` replaces a subcommand, before any flag is read). To check that a published artifact matches its source, launch the whole rebuild inside a disposable container or VM with no key and compare the ids: `cargo prove build --docker` and `cargo risczero build` start on the host, in the crate, before Docker is reached, and `--docker` mounts the host workspace. A `ProgramRegistry` entry's `buildCommand`, `containerImage` and `sourceUri` are registrant-supplied strings (first-come): run them only in that sandbox. Never trust a binary because the caller, `inputData`, a URL or a `ProgramRegistry` entry points to it: a registry entry does not authenticate a binary, and a decoy that commits the same journal passes step 2 and every SDK check, then fails at fulfil (`VerifierCallFailed`: a 5% release, or 100% if you wait for the slash; `test/b221i/RiscZeroVerifierVersion221i.t.sol`, `test_l3_*`). An output-identical rebuild (another toolchain, a no-op change) has another image id or vkey: it is a different program here. Every local verify (step 7, step 8, "prove first") is against the **job's `programId`**, never against the id of the binary you ran.
3. **Check the sizes.** The journal is ≤ `MAX_JOURNAL_BYTES` (32,768 B; exactly 32 B for `OPENVM_HALO2_V1`), and descriptor + journal + your seal fit the table in §3 for the path you will send (≥ 31,551 B of seal room on the safe paths, 31,772 B for `claimAndFulfillAssigned`; ≥ 31,484 B at worst, in the unsafe claim multicall row).
4. **Check the time.** The guest's cycle count gives the proving time; it must fit `fulfillmentTimeout` with margin. Plan to fulfil before the effective deadline: the speed bonus is 0 from there, and the 30-min `PROVER_GRACE` after it is for inclusion delay, not for proving (§6, "Late locks").
5. **`CUSTOM_VERIFIER` jobs:** the verifier has code, its codehash is on your allow-list (immutable verifiers only), it does not wrap a governance adapter or `Registry.verifyProof` (§6), and its seal fits. It is not an EIP-7702 delegated EOA (23-byte code `0xef0100 ‖ impl`, whose key holder can clear and restore it at will): submit refuses one (`CustomVerifierIsDelegated`), and a codehash allow-list already excludes designators (no contract's code starts with `0xEF`, EIP-3541). Under EIP-6780 code you saw at submit cannot vanish later, which is why a codeless verifier is not a bid-refund cause (§4).
6. **Gas.** Size the fulfil gas limit (§9).
7. **SP1 jobs (`SP1_GROTH16_V1`, `SP1_PLONK_V1`): the job's id fixes the wrapper. Prove with an SP1 SDK whose circuit is v6.1.0, in Groth16 mode for `SP1_GROTH16_V1` (`keccak256("sp1.groth16.v1")`) and in PLONK mode for `SP1_PLONK_V1` (`keccak256("sp1.plonk.v1")`).** The program (its ELF and vkey) is the same under both ids; only the last wrap differs, and its seal settles only a job of its own id. That is `SP1_CIRCUIT_VERSION` v6.1.0: SDK **6.1.0 to 6.10.0 (circuit v6.1.0)**. Build and test with **6.8.1**: it is the release this repository's nonce-bound fixture (`test/fixtures/SP1NonceBoundReceipt.sol`, settled through the router on every fulfil path) and its newest plain receipt (`test/fixtures/SP1VersionReceipts.sol` `SP1Sdk681Receipt`) are made with, and the first that fixes the SDK's native Rust verifier ([GHSA-p7v2-jjv3-8p8f](https://github.com/succinctlabs/sp1/security/advisories/GHSA-p7v2-jjv3-8p8f), SDK 6.0.0 to 6.8.0: Core and Compressed proofs from untrusted provers; the on-chain Groth16 path is unaffected), so run that verifier on proofs you did not make only with 6.8.1 or later. Pin it: every `sp1-*` and `slop-*` entry of `Cargo.lock`, the guest's included, at the one release (Cargo floats the transitive SP1 crates to the newest 6.x otherwise; `grep -A1 -E '^name = "(sp1|slop)-' Cargo.lock | grep version | sort | uniq -c` prints one line), and build your own host and guests with `--locked` (never a requester's guest: step 2a). Re-check this step on every SDK upgrade, a minor one included (6.0.2 to 6.1.0 changed the circuit). Read `VERSION()` (`"v6.1.0"`) and `VERIFIER_HASH()` from the job's adapter's `nativeVerifier()` before you claim: `0x4388a21c…` under `SP1_GROTH16_V1`, `0x5a093a2f…` under `SP1_PLONK_V1`. The seal is `SP1ProofWithPublicValues::bytes()` of a proof in the job's mode:
   - **`SP1_GROTH16_V1`**: `SP1ProofMode::Groth16` (`client.prove(&pk, stdin).groth16()`): 356 B, whose first 4 bytes are `VERIFIER_HASH()[0:4]` = **`0x4388a21c`**, then the exit code (0), the recursion VK root (`VK_ROOT()`), the proof nonce (bytes 68..100; 0 unless you set one, step 7a) and the 8 Groth16 words.
   - **`SP1_PLONK_V1`**: `SP1ProofMode::Plonk` (`client.prove(&pk, stdin).plonk()`): 964 B, whose first 4 bytes are **`0x5a093a2f`**, then the same exit code, VK root and proof-nonce words (bytes 4..100), then the PLONK proof.
   - `publicValues` is the proof's public values byte for byte, in both modes.

   Anything else reverts `VerifierCallFailed` at fulfil, and the lock can then only be released (5%) or slashed (100%): a seal of the other wrapper (a PLONK seal for an `SP1_GROTH16_V1` job, or a Groth16 seal for an `SP1_PLONK_V1` job), a proof from **SDK 6.0.0 to 6.0.2** (prefix `0x0e78f4db` Groth16 or `0xbb1a6f29` PLONK, circuit v6.0.0, the range of advisory [GHSA-63x8-x938-vx33](https://github.com/succinctlabs/sp1/security/advisories/GHSA-63x8-x938-vx33), CVE-2026-40323: a soundness gap in the V6 recursion circuit, fixed in 6.1.0), or a TEE-wrapped one (with a TEE proof attached, `bytes()` prepends it to the prefix). The router reports only `VerifierCallFailed()`; called directly (your local check below), the native verifier's own revert names the cause: under both wrappers `WrongVerifierSelector(received, expected)`, `InvalidExitCode()` and `InvalidVkRoot()`, and no revert data at all for a seal too short to decode (under 356 bytes for Groth16, under 100 for PLONK); under `SP1_GROTH16_V1` `ProofInvalid()` (a proof that fails) or `PublicInputNotInField()`; under `SP1_PLONK_V1` `InvalidProof()` (a proof that fails) or an `Error(string)` of the PLONK verifier: `"wrong proof size"` (any length but 964 bytes), `"inputs are bigger than r"`, `"openings bigger than r"`, `"error ec operation"`, `"error pairing"` and the like. Check the first 4 bytes and the length of your seal against the job's `VERIFIER_HASH()` and mode, and verify it locally against the **job's `programId`** under the **job's `proofSystemId`** (`Registry.verifyProof(proofSystemId, programId, publicValues, seal, "")` as an `eth_call` on your own node or an anvil fork, never a third-party RPC: the broadcast rule below) before your first claim and again after every SDK change, before the next claim. Every SDK release from 6.1.0 to 6.10.0 emits circuit v6.1.0 (one `groth16_vk.bin` and one `plonk_vk.bin`, each one's sha256 = its verifier's `VERIFIER_HASH()`); a later release may not (none is checked yet), so do not upgrade past 6.10.0 until this guide lists it. The SDK fetches the circuit's artifacts of each mode (`v6.1.0-groth16.tar.gz`, sha256 `18beebb6cd0cc9b4d4a240ee4f49511da6c2a7e51724bad4232de538a9147810`; `v6.1.0-plonk.tar.gz`, 2,305,113,029 B, sha256 `b3e2f5b5dd5ca89675c73975d2d1cc4a0f9e7cde048ec5354dabc7b0694aa39b`) on the first proof of that mode without checking them: fetch and check them yourself, and compare the extracted `groth16_vk.bin`'s or `plonk_vk.bin`'s sha256 with that verifier's `VERIFIER_HASH()`. A later SP1 circuit is a new verifier under a **new psId** (the old psId is deprecated), announced by a GT `OperationProposed` at least 24h ahead.
   - **A vkey names one exact ELF: build guests reproducibly.** The guest's ELF, and with it the vkey and `programId`, depends on its build environment: the same guest source built with sp1-zkvm 6.9.0 and the succinct toolchain v3 has vkey `0x00d50ee9…`, built with sp1-zkvm 6.8.1 and toolchain v2 `0x00122a03…`; each factor alone changes the ELF, and so does the `CARGO_HOME` path (the ELF embeds absolute registry paths). The derivation itself does not depend on the prover release (6.8.1's setup gives the 6.9.0-built ELF its 6.9.0 vkey). Provers prove the requester's ELF and check its vkey against `programId` (step 2a); requesters publish the exact ELF and build it reproducibly (`cargo prove build --docker` at the pinned release tag), so that anyone can rebuild it to the same vkey.
   - **Memory and time.** One Groth16 proof of a small guest (4,769 cycles) on the local CPU prover (`native-gnark`, 16 cores, a shared host) took 8 to 11 min wall and peaked at 27.5 to 28.5 GB of RSS (6.8.1: 11:05 and 27.6 GB with a nonce, 10:22 and 28.1 GB without). The peak is the gnark Groth16 wrap in the last minute or two, and it is fixed in size: a larger guest adds time in the earlier phases, not memory at the peak. Plan on at least 40 GB of free RAM per concurrent proof; `GOGC=25 GOMEMLIMIT=20GiB` keep the Go heap near 1.25 times the live set, and a memory-limited cgroup (for example a systemd scope with `MemoryMax=34G` and `MemorySwapMax=0`) makes an overrun kill only the proof. Disk: the circuit tarball 6.2 GB plus 7.8 GB extracted, the toolchain 1.7 GB, a host build about 3 GB. The PLONK wrap is heavier: one PLONK proof of the same guest (6.8.1, the same host) took 25 to 27 min wall and peaked at 51 to 52 GB of RSS (with and without a nonce), so plan on at least 64 GB of free RAM per concurrent PLONK proof, with `GOMEMLIMIT` and the cgroup limit raised to match (the fixtures were made under `MemoryMax=80G`, `GOMEMLIMIT=64GiB`, `GOGC=25`). Measure both modes on your own host before you serve either id.

   **7a. Nonce-bound SP1 jobs (the proof-nonce marker, §3a).**
   - **Prove locally**, on the CPU or CUDA prover, with `with_proof_nonce(limbs)`, `limbs` = `getProofNonce(jobId, yourStakedProver).limbs` in the view's order, in the job's mode: the nonce is public input 4 of both wrappers, at the same seal bytes 68..100, and the marker is accepted on both SP1 ids. The Succinct prover network ignores the nonce (its prove path passes none; checked at 6.10.0): a network proof carries nonce 0 and is refused.
   - **The SDK defect, and the fix.** Stock `sp1-prover` 6.1.0 to 6.10.0, 6.8.1 included, drop `with_proof_nonce` on the CPU and CUDA paths: the proof is valid but carries nonce 0, and the router refuses it (`ProofNonceMismatch(expected, 0)`; measured on stock 6.8.1: limbs `[1, 2, 3, 4]` requested, seal word 0). The cause is in `SP1LocalNode::prove_with_mode` (`src/worker/node/full/mod.rs` of the `sp1-prover` crate): it sends the controller task the inputs `[elf, stdin, mode, nonce]`, while the controller reads index 3 as the cycle limit and index 4 as the nonce. Until a fixed `sp1-prover` is released, nonce-bound jobs need a patched one, with one element inserted at index 3:
     ```diff
     --- src/worker/node/full/mod.rs   (SP1LocalNode::prove_with_mode, the controller task inputs)
                          mode_artifact,
     +                    Artifact(String::new()),   // inputs[3] is the cycle limit; the nonce belongs at inputs[4]
                          proof_nonce_artifact.clone(),
     ```
     ```toml
     # Cargo.toml of the host workspace: the crates.io sp1-prover of your pinned release, with the insertion above
     [patch.crates-io]
     sp1-prover = { path = "patched/sp1-prover" }
     ```
     Take the source from the crates.io archive of your pinned release and check it before you unpack it: a `path` patch drops that crate's checksum from `Cargo.lock`, so this is the only integrity check on the patched crate. For 6.8.1, `https://static.crates.io/crates/sp1-prover/sp1-prover-6.8.1.crate` has sha256 `2f0f1d58a3144090a2250f48d4743e3319e861a6537d3262d848380e2d284e59`, the `cksum` of the crates.io index entry (`https://index.crates.io/sp/1-/sp1-prover`, line `"vers":"6.8.1"`); read the index for another release:
     ```bash
     curl -fsSLO https://static.crates.io/crates/sp1-prover/sp1-prover-6.8.1.crate
     echo "2f0f1d58a3144090a2250f48d4743e3319e861a6537d3262d848380e2d284e59  sp1-prover-6.8.1.crate" | sha256sum -c -
     mkdir -p patched && tar -xzf sp1-prover-6.8.1.crate -C patched && mv patched/sp1-prover-6.8.1 patched/sp1-prover
     ```
     The file is byte-identical in 6.8.1 and 6.9.0, and the circuit and the prover arithmetic are unchanged. Then:
     ```rust
     // (nonce, limbs) = router.getProofNonce(jobId, stakedProver)   // an eth_call on your own node
     let proof = client.prove(&pk, stdin).groth16().with_proof_nonce(limbs).await?;   // SP1_GROTH16_V1; .plonk() for SP1_PLONK_V1
     let seal = proof.bytes();
     assert_eq!(&seal[68..100], &nonce.to_be_bytes::<32>());   // the pre-check, below
     ```
   - **The pre-check is mandatory.** Before you claim a nonce-bound job with a proof in hand (prove first), and again before you fulfil, compare `seal[68:100]` with `getProofNonce(jobId, yourStakedProver).nonce` (32 bytes, big-endian). For an operator-run prover the address is the **staked prover's** (`job.prover`), never the operator key's. Equal: the router's check passes. Different (0 from a stock prover or the network, or a proof made for another job, prover or chain): do not send. `Registry.verifyProof` and the SDK's own verify check the proof, not the nonce, so a passing local verification is not enough. A fulfil sent without the check reverts `ProofNonceMismatch(expected, actual)` before any payment: you keep the lock, and re-prove with the right limbs if `D + G` allows, else release (5%). Also check the wrapper: `seal[0:4] == 0x4388a21c` and `len(seal) == 356` for `SP1_GROTH16_V1`, `seal[0:4] == 0x5a093a2f` and `len(seal) == 964` for `SP1_PLONK_V1`. The one-element prover fix above serves both modes: it corrects the controller's inputs, before either wrap (the nonce-bound PLONK fixture, `test/fixtures/SP1PlonkNonceBoundReceipt.sol`, was made with it).
8. **RISC Zero jobs (`RISC_ZERO_GROTH16_V1`): prove with risc0-zkvm 3.0.x, in Groth16 mode.** 3.0.0 to 3.0.6 (the latest stable on 2026-10-20) emit the risc0 3.0 circuits; build guests with 3.0.3 or later ([GHSA-jqq4-c7wq-36h7](https://github.com/risc0/risc0/security/advisories/GHSA-jqq4-c7wq-36h7), guest `sys_read`). Pin it (`Cargo.lock`; Cargo does not cross a major on its own) and re-check this step on every major bump: risc0 5.0.0-rc.1 is published with another control root, and its seals (prefix `0xc27d1bc0` in risc0-ethereum `main`) are refused, so 5.x will be a new psId. Read `SELECTOR()` from the adapter's `nativeVerifier()` (**`0x73c457ba`**) before you claim. The seal is risc0-ethereum-contracts 3.0.x `encode_seal(&receipt)` of a Groth16 receipt: 260 B, its first 4 bytes `SELECTOR()`, then the 256-B proof; `publicValues` is the journal byte for byte. Anything else reverts `VerifierCallFailed` at fulfil (the verifier's `SelectorMismatch` or `VerificationFailed`), and the lock can then only be released (5%) or slashed (100%): a risc0 5.x or 2.x receipt, a Boundless set-inclusion seal (`SetVerifier` selector `0x242f9d5b`; a Boundless request must require selector `0x73c457ba`, and is posted only after your lock is mined: the broadcast rule below), a dev-mode receipt (`0xffffffff`, `RISC0_DEV_MODE`), or a succinct or composite receipt. Your host's `receipt.verify(image_id)` passes under the toolchain's own rules and does not show this: check the prefix, and run `Registry.verifyProof(RISC_ZERO_GROTH16_V1, programId, journal, seal, "")` as an `eth_call` on your own node against the job's `programId`, before your first claim and after every toolchain change. For a journal-prefix job the prefix names your staked address: a Boundless request must carry your own prefix as input, so the delivered seal settles the job only for you (the nonce marker is SP1's).
9. **OpenVM jobs (`OPENVM_HALO2_V1`, registered on 743111 only).**
   - **Toolchain.** cargo-openvm **v2.0.x** (v2.0.2 is OpenVM's newest production release; a patch release keeps the verifier, its keys and the proof format, so every v2.0.x proof is checked by the one registered verifier). Install the release binary (`cargo-openvm-v2.0.2-x86_64-unknown-linux-gnu.tar.gz`; check the sha256 GitHub publishes for it) or build it at the tag's commit (`cargo +1.91 install --locked --git https://github.com/openvm-org/openvm --rev 59a69b8b0cbee7011ac978e4cc07707ee3681944 cargo-openvm`: tag v2.0.2's commit; a `--tag` follows a tag that can be moved); guests build with Rust `nightly-2026-01-18` and `rust-src`. The registered verifier is the default aggregation with deferrals off (`v2.0-base`, what `cargo openvm setup --evm` generates): a guest that uses the deferral path needs another verifier and cannot be served.
   - **Work from the published artifacts, in a directory of your own.** Without `--exe`, `cargo openvm commit`, `run` and `prove` build the Cargo crate of the working directory, running its build scripts and procedural macros. Even with `--exe`, they (and `keygen`) look for a `Cargo.toml` in the working directory or a parent unless `--manifest-path` is given, and run `cargo metadata` on it unless `--target-dir` is given (`commit` also reads it to name its output); `keygen` and `run` read that directory's `openvm.toml` unless `--config` is given, and silently use the default configuration when there is none. Before any of that, rustup and cargo read `rust-toolchain.toml` and `.cargo/config.toml` from the working directory and every parent (a toolchain `path` replaces `cargo`, an `[alias] openvm` replaces `cargo openvm`). So the requester publishes `<program>.vmexe` (the `cargo openvm build` output) and its `openvm.toml`; you keep them as plain files in a per-job directory, and on a host that holds your prover key or can reach your signer you never run a command whose working directory is inside or under any requester-supplied tree (its crate, a clone, an unpacked archive). Create a directory once (`cargo new --bin openvm-work`, nothing of the requester's inside or above it), run every command from its parent, and pass every input explicitly, with a target directory per job (`keygen` writes the app keys beside it, so a shared one lets one job's keys replace another's): `M="--manifest-path openvm-work/Cargo.toml --target-dir openvm-work/jobs/<jobId>/target"`. Then `cargo openvm keygen --config <their openvm.toml> $M`; `cargo openvm commit --exe <their .vmexe> --config <their openvm.toml> $M`, and the same `--exe`, `--config` and `$M` on `run` and `prove evm`; `verify evm` with explicit `--proof` and `--app-commit` paths. A source rebuild, to check that the `.vmexe` matches its source, runs only inside a disposable container or VM with no key (step 2a).
   - **Program identity.** `cargo openvm commit` prints `exe commit:` and `vm commit:` and writes them, as `app_exe_commit` and `app_vm_commit`, to a `.commit.json` named after the crate it resolved (with the recipe above, `openvm-work/jobs/<jobId>/openvm/release/openvm-work.commit.json`). `programId = keccak256(abi.encode(app_exe_commit, app_vm_commit))` (the adapter's `programIdOf`, or `cast keccak "$(cast abi-encode 'f(bytes32,bytes32)' "$EXE_COMMIT" "$VM_COMMIT")"`), and `extraVerifierData = abi.encode(app_exe_commit, app_vm_commit)`, exactly 64 bytes (`OpenVmVerifierDataLength`, `OpenVmProgramIdMismatch` otherwise). Both commitments count: the executable commitment names the program (code, initial memory, entry point), the VM commitment the app VM configuration (its extensions, which opcodes they serve, the system parameters). The verifier accepts a proof under any configuration, so the same executable under another configuration could prove any output; the requester fixes both in the descriptor and a prover chooses neither.
   - **The journal is exactly 32 bytes** (`openvm::io::reveal_bytes32`; the aggregation configuration fixes the count, `cargo openvm keygen` refuses another, and the verifier refuses another length). A program with more output reveals a hash of it. Bindings: FULL over the 32 bytes, or FIELDS ranges within byte 32; no binding marker (submit rule 7). An OpenVM proof is therefore not bound to the job or the prover: it settles any job with the same statement, and the broadcast rule is its only protection.
   - **The proof.** `cargo openvm prove evm --input …` writes JSON with `user_public_values` (`publicValues`, 32 B) and `proof_data` (`proofBytes` = `accumulator ‖ proof`, 384 + 1,376 = 1,760 B). Memory: on CPU its heaviest stage, the Halo2 static-verifier proof, peaks at about 26 GB (measured with the stages run as separate processes); the one-process CLI keeps the 10.2 GB Halo2 proving key resident throughout and needs about 30 to 33 GB. OpenVM recommends a 32 GB GPU for `prove evm`. `cargo openvm setup --evm --download` fetches about 14.5 GB (`halo2.pk` and the KZG parameters).
   - **Verify locally before you fulfil:** `cargo openvm verify evm --proof <the .evm.proof prove wrote> --app-commit <that .commit.json>` (with both paths given it resolves no manifest), and `Registry.verifyProof(OPENVM_HALO2_V1, programId, publicValues, proofBytes, extraVerifierData)` as an `eth_call` on your own node against the job's `programId` and `extraVerifierData`.
   - **Gas.** The verifier call costs about 300k gas (the native verify 296k, through the adapter 304k; the CLI's simulation reports 337k for a whole verify transaction), and a FULL-bound OpenVM `fulfillJob` about 653k of execution (a real fulfil on a local chain: 772,282 gas in its receipt). Size the limit with the adapter-job formula (§9). A malformed proof (a point off the curve) makes the BN254 precompile consume all the gas it is given, so a refused OpenVM proof can burn the router's whole 4,000,000-gas verifier budget (SP1 and RISC Zero proofs fail far cheaper): never send one you have not verified locally.

A caller can always commit a binding no honest proof satisfies; the claiming prover is then slashed after the deadline and its grace (a known residual). Steps 1-3 are the defence, with 2a: a caller can also point you to a decoy binary whose journal matches the binding (residual 6, `DEPLOY_RUNBOOK.md`). If the proof itself turns out to be undeliverable after you claimed (a binding or size defect: `JournalMismatch`, `JournalPrefixMismatch`, `ProofNonceMismatch`, `JournalTooLarge`, `InvalidDescriptorHash`), re-prove if the fix fits before `D + G`, else release (5%) rather than wait for the slash (100%). Never release on a governance state (`RegistryPaused`, `AdapterDisabled`, `BlacklistedVerifier`, `EnforcedPause`): the lock is credited while it lasts (§5, "Which reverts mean what").

**The broadcast rule**. **Never broadcast a journal or seal for a job until your own lock on it is in an earlier, mined block.** A proof of a job without a binding marker binds the statement, not the prover, and Hemi's mempool is public and ordered by tip: anyone staked who sees your seal before your lock is mined can take the lock and settle the job with it (the caller can also `cancelJob` and keep the result).
- **For a job with a binding marker** (§3a) an early broadcast loses the job only to the caller's cancel (an Open job: the caller cancels and keeps the result) or to a griefing lock (a staked third party locks first; it cannot settle and pays the release penalty or the slash), never to a copier. The rule stays for every job.
- **The one exception: `claimAndFulfillAssigned`** (§4), one transaction that claims a job reserved to you and fulfils it. Nobody else can lock a reserved job, but its proof travels while the job is still Open, so send it only when that is safe: for a job with a binding marker (a copy settles for nobody else), or for a requester you trust (it could cancel ahead of the transaction and resubmit the statement for another prover), and then, for a window job, with at least 60 s of the window left in job-local time (a transaction held past the window end reverts `NotReserved` and leaves the job, and your published proof, open to anyone). Otherwise claim first. Even a safe send leaves the caller of the Open job its cancel: it can cancel ahead of the transaction and keep the result, and you lose the proving work, never stake.
- Send `claimJob` (or `slashAndClaim`, `settleBid`) **alone**. Wait for its receipt, then re-read `jobs(jobId).prover == you` at a block at or after the receipt's (a load-balanced RPC may lag). Only then send the fulfil.
- **No `multicall([claimJob, fulfillJob])`** or any other wrapper that carries the claim and the proof together, and **no pipelined nonces** (a fulfil signed and sent behind its claim before the claim is mined is copied pairwise).
- **A reverted transaction still publishes its calldata.** A fulfil that reverts (late, under-gassed, wrong lock) has published its seal.
- **`eth_call` shows the seal to your RPC operator.** Simulate fulfils only against an RPC you trust (your own node), and only after the lock is mined.
- **A proving market or service is a broadcast.** A request to Boundless, the Succinct prover network or any hosted prover publishes the job's statement, and its delivery publishes the proof: Boundless puts the request's input (inline or as a public URL) in a public log on Base when the request is posted, and the seal (with the journal or its claim digest) when it is delivered, in the RISC Zero Groth16 format `RISC_ZERO_GROTH16_V1` accepts; the prover network's fulfiller holds the stdin and the proof. **Prove first only on hardware you control.** To subcontract, claim alone first, and post the market request only after your lock is mined, with the market's deadline inside your lock's `D + G` (a delivery after it turns into a late lock any keeper can take over: §6, "Late locks"). The requester's witness becomes public either way. A binding marker narrows what a published proof settles (§3a): a Boundless request for a journal-prefix job carries your own prefix (step 8); the prover network cannot serve a nonce-bound job (it ignores the nonce, step 7a).
- **"Prove first"** (prove before you claim, so that proving time cannot eat the timeout) means: prove on your own hardware, `claimJob` alone, then fulfil after the receipt. It costs the speed bonus of the wait: `speedPremium × 12 s / fulfillmentTimeout` when the fulfil lands in the block after the claim (`claimAndFulfillAssigned`, where it is safe, pays the whole budget left). It works for a job with a binding marker too: the jobId and your staked address, which the prefix or the nonce needs, are known before the claim.
- **Claim with exact floors**: `claimJob(jobId, priceFloor, premiumFloor)` (`0xb2f51925`; `claimAndFulfillAssigned` takes the same two floors). `priceFloor` = the price an `eth_call` of `claimJob(jobId, 0, 0)` from your claiming address returns at a **mined** block; `premiumFloor` = `getPremiumCap(jobId)` at that same block; tolerance 0, also in `RESUME_GRACE` tails. Never `jobs(jobId).minPrice`, a `pending` read, `getCurrentPrice`, or 0 for a real send (§4, "Claim floors").
- Keep a per-job price high-water mark (the highest floor you sent); never claim below it; forget it only on your own lock, a terminal job or `MAX_REOPEN_COUNT`, never because another prover locked the job.
- Set a reservation price (`MIN_CLAIM_PRICE_WEI` in the reference daemons, default 0: set it) and skip jobs whose `maxPrice` is below it. **The reservation is in the job's token: HEMI wei** (1 HEMI = 10^18 wei), compared with `maxPrice` and the claim price; it is never an ETH amount. Set it to at least (your ETH cost per job × HEMI per ETH × a margin of at least 1.25) + your proving cost in HEMI:
  - The ETH cost per job is the claim and fulfil gas used (about 1M: `claimJob` ≤ 115k and a real Groth16 fulfil about 530-630k with the default 200k callback, §9; a job's callback can burn up to its `callbackGasLimit` on top) × (the base fee + the fulfil's tip at the hold-out floor, §6: 0.237 gwei for a 300-s job at the daemons' defaults) + the fulfil's L1 data fee. That is about **2.4e14 ETH-wei** (0.00024 ETH).
  - **Size it for 300-s jobs**, the shortest `fulfillmentTimeout` (`MIN_FULFILLMENT_TIMEOUT`): the requester chooses the timeout and the reference daemons have no timeout filter, so a value sized for 2-h jobs (whose hold-out floor is lower) undercharges every 300-s job.
  - Convert, then add the margin: 2.4e14 ETH-wei × 50,000 HEMI per ETH × 1.25 = `MIN_CLAIM_PRICE_WEI=15000000000000000000` (15 HEMI). Writing the ETH figure itself (`240000000000000`, 0.00024 HEMI) leaves the key without a reservation: a caller's dust-priced jobs then drain its ETH. The daemons page `RESERVATION-UNIT` at start for a non-zero value below 10^17 wei (0.1 HEMI) and `RESERVATION-UNSET` for 0 on 743111 and 43111, and print the reservation in HEMI in their banner. A job whose `maxPrice` is below the reservation is never claimed: the reference submitter, `script/job-submitter.sh`, ramps to 20 HEMI by default (above this 15-HEMI example) and refuses to start when `MIN_CLAIM_PRICE_WEI`, exported in its shell, is above its `MAX_PRICE_WEI`. It also requires `ASSIGNED_PROVER`, the address of the key that serves its jobs (below).
  - Re-size it when the HEMI/ETH rate or the L1 fee moves (more than about 15%). The daemons' optional cover monitor does the arithmetic: set `HEMI_PER_ETH` (an integer, how many HEMI one ETH buys; not ETH per HEMI, not a USD price) and `HEMI_PER_ETH_EXPIRES` (unix seconds, at most 31 days ahead; `$(date -d '+7 days' +%s)`), and it pages `RESERVATION-LOW` at start and every `COVER_CHECK_SEC` (3,600 s) when the reservation is below 1.1 × (`COVER_GAS_PER_JOB` (1,000,000) × (base fee + max(`TIP_START_WEI`, the 300-s hold-out floor)) + 2 × the `GasPriceOracle` L1 fee bound of a 2,048-byte fulfil) × `HEMI_PER_ETH`, computed in decimal strings (the HEMI-wei figure exceeds 2^63 above 9.22 HEMI: never bash integers), and `RESERVATION-RATE-EXPIRED` once the rate expired. It only pages: it never changes what is claimed. Never derive the rate from an on-chain HEMI pool (none is liquid; a pushed price lowers the floor).
- **The caller's cancel + resubmit hold-up** (residual 16(f)). A cancel is free on an Open job without a live bid, and the proof binds the statement, not the jobId: a prove-first prover's caller can cancel ahead of the pending claim and repost the same statement cheaper. Per-jobId floors and the high-water mark do not help (the new job has a new id); a second ratchet keyed by the statement (programId, proofSystemId, `keccak256(inputData)`, the journal binding, the verifier) is optional. A prove-first proof of a job with a binding marker is specific to that job: the resubmitted job needs a new proof. Prove first only for callers you trust.
- **One sender per staked key.** A reference daemon signs at the key's next mined nonce and replaces whatever is pending there. Never run `job-prover.sh` and `demo-prover.sh`, a bidding tool, rescues or hand sends on the same key: competitive bidding, hand and late-lock rescues and delegated-claim fulfils use a key no reference daemon runs on. The daemons adopt every `JobClaimed` of their key but manage only locks whose descriptor they can build; any other lock of the key gets one `FOREIGN` line and is never fulfilled, released or sent for.
- **Prover-host toolchain.** The reference daemons parse `cast` output and are tested on **Foundry 1.5.1 and 1.8.5** only (stable releases; `scripts/test-prover-daemons.sh` runs on both in CI). Install one explicitly (`foundryup --install v1.5.1`, or `v1.8.5`; a plain `foundryup` installs whatever is newest), never a nightly. Any other `cast` (or, for `job-prover.sh`, `forge`) refuses to start with a `PAGE: TOOLCHAIN` line; `ALLOW_UNTESTED_FOUNDRY=1` starts anyway, with that page, at your own risk. The daemons export `FOUNDRY_DISABLE_NIGHTLY_WARNING=1` for every `cast` and `forge` call (a nightly prints a warning banner to stderr on every subcommand) and parse stdout only. Why it matters: cast 1.8 prints `cast block --json` inside a `{"schema_version", "success", "data"}` envelope, which a parser written for 1.5.1 reads as block 0 / time 0, so a restart with a fresh `STATE_DIR` recovers no live lock (each is slashed) and scans no job, silently; a nightly's banner merged into a parsed output drops live locks and corrupts raw transactions. A daemon refuses to start on a head at block 0 or timestamp 0 off the dev chains (`PAGE: HEAD-ZERO`) and pages `LOOKBACK` when a fresh `STATE_DIR`'s lock recovery is empty (`LOCK_LOOKBACK_BLOCKS=0`) or starts at block 0 while `eth_blockNumber` is above `LOCK_LOOKBACK_BLOCKS`. Your own tooling: read chain data with `cast rpc --raw` (raw JSON-RPC, printed identically by 1.5.1 and 1.8.x) or `cast call` with a return signature, never `cast block --json`, `cast tx --json` or `cast estimate --json` (wrapped by 1.8), never `cast receipt <hash> status` (`1 (success)` on 1.5.1, `true` on 1.8), and keep stderr out of what you parse. cast 1.8.x (not 1.5.1) also looks the selector of every revert of `cast call` up online (OpenChain / Sourcify) unless `~/.foundry/cache/signatures` names it, and no flag turns that off: where egress is DROPped each revert waits 15 s (8 kept locks took 121 s per poll). The reference daemons seed the protocol's errors into that cache at start and re-check it every poll; for your own tooling on 1.8.x, run `forge build` of this repo once as that user, allow HTTPS to the signature services (api.4byte.sourcify.dev) or REJECT rather than DROP. Pin the version and keep provisioning from running a bare `foundryup` on prover hosts: the daemons re-read `cast --version` every poll, page `TOOLCHAIN-CHANGED` on a change and hold new claims (serving their locks) on an untested version. A fresh `STATE_DIR`'s lock recovery retries a failed `eth_getLogs` window at half its size; one that keeps failing pages `LOOKBACK-FAILED` and is retried every poll while the known locks are served (no new claims until it completes), and a refusal to start on an unreadable RPC read pages `RPC`. Run each daemon under a supervisor that restarts it and alerts when it exits: `ERROR_LOG` cannot report a dead process. The recovery retries a failed window once at the same size before halving it, and grows a halved window back after a few reads (halving for good would leave a 108,000-block recovery at one block per call for hours after isolated transient errors); it runs in time slices (`LOOKBACK_SLICE_SEC`, default 60 s) with every known lock served between them, and pages `LOOKBACK-SLOW` after `LOOKBACK_PAGE_SEC` (600 s). An unwritable `~/.foundry/cache/signatures` is retried every 10 min instead of re-seeded every poll; `ERROR_LOG` and the page lines name an RPC by scheme and host only (a keyed provider URL carries its key in the path; the key is still on `cast`'s command line).
- **The daemons' DA hold-out pages** (§6, "The DA throttle"). `PAGE: PENDING-UNMINED` when an accepted fulfil or release is still not mined `PENDING_PAGE_BLOCKS` (default 10) blocks after its first acceptance while the head advances (again every 50 blocks); the line names the nonce, the live tip and maxFee, the transaction and the job. `PAGE: SAFE-LAG` when the safe head trails the head by more than `SAFE_LAG_PAGE_SECS` (default 600 s; `ts(latest) − ts(safe)` on the daemon's RPC, `scripts/check-l2-lag.sh`'s reading), again every 30 min while it lasts. Neither changes what the daemon does: it keeps re-publishing and climbing its ladder, and never releases on a filter (a release is only for a defect of the proof, §5). What to do: check the router's `paused()` (paused: the lock is credited, keep it). Unpaused, with the lock's last moment (`D + PROVER_GRACE`) near and the fulfil still out:
  1. **Find out what holds it.** Ask a second, independent endpoint for the pooled transaction: `cast rpc --rpc-url "$RPC_2" eth_getTransactionByHash "$TX"` (`TX` from the page). If it answers `null` and `SAFE-LAG` has not paged, your own endpoint accepts and never forwards (a black hole), and a release sent through it never lands either. The sequencer then holds nothing at that nonce: send the release of step 3 through `$RPC_2`, at an ordinary fee (`TIP=0.01gwei MAX_FEE=1gwei`: no 1.1× is needed), and move the daemon to another endpoint. Otherwise (the second endpoint knows the transaction, or `SAFE-LAG` paged) it is the DA filter: the release must replace the pooled fulfil at its nonce (a release at the next nonce waits behind the filtered fulfil).
  2. **Price the release before you send it.** At the pooled nonce it needs `TIP` and `MAX_FEE` each at least 1.1 × the page's tip and maxFee (geth replaces a pooled transaction only above both), and it costs about 225,000 gas × (base fee + `TIP`) (§9). It saves 95% of the lock's `lockedCollateral` (`jobs(jobId)`, field 10: the slash takes 100%, the release 5%). The page prints the fees, the cost and the saving, and with `HEMI_PER_ETH` set says which is larger. Under a hold no tip beats, the ladder keeps climbing: at the 100-gwei default ceiling (99.1 gwei after about 52 missed blocks) the release costs about 0.0245 ETH, 1,222 HEMI at 50,000 HEMI per ETH, against 95 HEMI saved on a 100-HEMI lock. **Release only if its cost in HEMI is below what it saves.** Otherwise stop the daemon (its ladder only raises what the pooled fulfil pays if the hold ends) and leave the lock. A ceiling sized from what the lock is worth keeps the release worth sending (§6, "Escalate the tip").
  3. Send it with the daemon stopped (one sender per key):
  ```bash
  cast send --rpc-url "$RPC_URL" --private-key "$PK" --nonce "$NONCE" --gas-limit 500000 --priority-gas-price "$TIP" --gas-price "$MAX_FEE" "$HEMI_PROVE" 'releaseJob(bytes32)' "$JOB_ID"
  ```
  with `NONCE` from the page. The release (100 bytes, under every filter) costs 5% of the collateral instead of the slash's 100%. Restart the daemon after it is mined: it re-reads the job.
- **The daemons' alert rule.** Page on every `ERROR_LOG` line that contains `PAGE`, `HEAD-STALE`, `ESCALATION-CAPPED`, `STEP-DOWN`, `REFUSED`, `FOREIGN` or `LOCK-LOST`, and on the daemon's exit (run it under a supervisor; `ERROR_LOG` cannot report a dead process). Every line that precedes a certain slash carries `PAGE`:
  - `LOCK-LATE`: a lock still yours `LOCK_LATE_SEC` (default `PROVER_GRACE_SEC / 2`, 900 s) before its last safe moment, whatever the cause, which the line names (a proof not ready, a fulfil not prepared, an RPC that answers without revert data, a failed read, a fulfil sent that late). Once per lock per 5 minutes; hourly while a pause or disable credits the lock; and once more when it is past that moment;
  - `LOCK-STUCK`: the daemon cannot settle the lock on its own and never releases on the cause (a revert outside its release allow-list, a deadline revert, a release that would revert, demo-prover's lost proof). At first sight, then hourly;
  - `LOCK-LOST`: a lock found slashed;
  - `RPC-DOWN`: the head unreadable for `SCAN_STALL_POLLS` polls in a row (default 10), and again every that many. Every such poll writes `ERROR_LOG`.

  The new-job scan runs at most `SCAN_BUDGET_SEC` per pass (default min(`POLL_INTERVAL`, 20 s)), checked after every job it handles, its claim attempt included (mined, reverted or not sent), together with whether a lock has entered its `LOCK-LATE` window since the pass began: once either holds, the scan stops before the next job, inside a block if need be, its cursor holds below the first block not finished, and the locks are served again without the poll's sleep. The next pass skips the jobs of that block it already handled, with no RPC read (`STATE_DIR/scan-done`), so no job is read twice. A flood of new jobs, in one block or many (jobs priced below the reservation, jobs cancelled at once, claims that revert because the caller cancels ahead of them), never keeps a lock waiting longer than the budget plus one job (one claim attempt and its receipt wait), then the claim retry pass's own budget plus one entry (it re-checks at most `CLAIM_RETRY_BUDGET` entries, after one liveness read). A lock that enters its `LOCK-LATE` window during either pass is served after the job or entry in progress: after such a stop of the scan the retry pass waits for the next poll, which serves the locks first. `job-prover.sh` skips a job built for another descriptor, or whose `maxPrice` is below `MIN_CLAIM_PRICE_WEI`, on the `JobSubmitted` log's data (`descriptorHash`, `maxPrice`; both fixed for the job's life) with no RPC read; `demo-prover.sh` scans `HashChainRequested`, which only the consumer's owner or keeper emits. `PAGE: SCAN-BEHIND` (no slash: new jobs wait) when the scan ends short of the head `SCAN_BEHIND_POLLS` polls in a row (default 10): its cursor held by an `eth_getLogs` that fails, a job that holds it or the budget, or more than `SCAN_BEHIND_BLOCKS` (default an hour of blocks) below the head; demo-prover's wait for a proof it is making counts only by that distance. At most hourly; every failed scan, and every job that holds the cursor, writes `ERROR_LOG`, and one line follows when the scan is no longer behind. On `SCAN-BEHIND`, read the lines before it: a failing `eth_getLogs` (a provider's range cap or an outage: point `RPC_URL` at another endpoint), a job that holds the cursor (a pause, disable or blacklist until the lift; funds), or more new jobs than the daemon reads in a budget (a flood, a slow or rate-limited endpoint: use your own or a keyed one).

  A claim the router refuses because the key's free stake does not cover the job's collateral (`claimJob`, like `claimJobDelegated` and `claimAndFulfillAssigned`, reverts `Panic(0x01)` from Staking's `lockCollateral`, or `PendingUnstakeConflict` when only a pending unstake is in the way) does not lose the job: the daemons keep it in the claim retry set, marked with the key's available collateral (Staking's `getAvailableCollateral`: the stake not locked in a job nor committed to an unstake), and re-check it by `eth_call` once that rises (a lock settles, a top-up, a cancelled unstake); until then it costs no claim simulation, but one such job per pass, in turn, is read (one `jobs()` call) and leaves the set once it is no longer Open (cancelled, locked by any prover, settled, at `MAX_REOPEN_COUNT`). The available collateral never rises above its peak in normal operation (a settled lock returns it there; rewards are paid to the wallet), and a slash or a release penalty lowers the peak for good, so without that read the entries of ended jobs would stay. `PAGE: STAKE-SHORT` (no slash: those jobs wait) at most hourly while claims are refused for stake, naming the job, the revert and the available collateral; top up the stake to serve them sooner. A full claim retry set (`CLAIM_RETRY_CAP`, 256), or a caller's full share (`CLAIM_RETRY_PER_CALLER`, 16), evicts its oldest such entry for a new job (an `ERROR_LOG` line names it): a requester makes them at no lasting cost (jobs at up to 500% collateral, cancelled for a full refund once refused), and they could not be claimed before the stake rises anyway. `PAGE: RETRY-FULL` (no slash; at most hourly, every refused job in `ERROR_LOG`) when a full set has none to evict: the job is not added, and the daemon never claims it (its log cursor has passed it). That loses every job that needs the set: a ramped job first seen below the reservation (every `job-submitter.sh` job), `BiddingActive`, `ClaimBelowFloor`, a reset job. Read `STATE_DIR/retry` (field 2 is each job's caller): a caller that floods the set holds at most `CLAIM_RETRY_PER_CALLER` entries; with genuine jobs, raise `CLAIM_RETRY_CAP`.

  The limiter is `STATE_DIR/pages`, so a restart does not page again. Every RPC call gives up after `RPC_TIMEOUT_SEC` (default your `ETH_RPC_TIMEOUT`, else 10 s; cast's own default is 45 s); set it above your endpoint's p99. On `LOCK-LATE` or `LOCK-STUCK`, find the cause in the lines before it. If the lock cannot be settled in time, release it by hand (5%) with the daemon stopped, priced first (§6, "Release"). On `RPC-DOWN`, point `RPC_URL` at another endpoint and restart: `STATE_DIR` keeps the locks.
- The reference daemons never run a caller's binary: they claim only jobs of their own fixed descriptor (job-prover: the fixture's image id; demo-prover: the consumer's `programId`) and verify their proof against that `programId` before every claim, so the decoy-program trap of the prover checklist above cannot reach them. A prover that executes a caller-supplied guest must check its image id (or SP1 vkey) against the job's `programId` itself. Their descriptors carry no binding marker (the fixture's journal and seal are fixed), so they never claim a marker job; they keep the two-transaction path (no `claimAndFulfillAssigned`), release on `JournalPrefixMismatch` and `ProofNonceMismatch` like the other proof defects, and treat `NotReserved` as a job that is not open to them. For an SP1 job the job's id picks the proving mode, and a seal of the other wrapper never leaves the host (`script/lib/prover-lib.sh` `pl_sp1_mode`, `pl_seal_problem`): `job-prover.sh` refuses to start with one, and `demo-prover.sh` refuses such a `FIXTURE_SEAL` at start (without one, its fixture seal for an SP1 consumer is the wrapper's 4-byte prefix and 32 zero bytes, which only a mock verifier accepts), runs its `PROVE_CMD` with `SP1_PROOF_MODE` (`groth16` or `plonk`), refuses the default (RISC Zero) `PROVE_CMD` before building it, and does not claim with a generated seal of the other wrapper.
- **job-prover's jobs are assigned to its key.** `script/job-prover.sh` proves the RISC Zero fixture statement (`test/fixtures/RiscZeroTestReceipt.sol`), whose image id, journal and seal are public: an open job on it is claimed at the opening price and fulfilled with that seal by any staked key that sees it. Its descriptor (`script/TestFulfill.s.sol` `plan(address)`, built at start for the daemon's own key) therefore binds NONE (`expectedJournalHash` and `journalFields` 0) with that key as `assignedProver`, and `script/job-submitter.sh` submits exactly that descriptor for `ASSIGNED_PROVER` (required; no open variant). The router lets only the assigned key lock such a job, for its whole life (any other claim reverts `ExclusivityActive`); a third party running the same daemon builds the descriptor for its own key, another descriptor hash, and never claims these jobs. Under a FULL binding an `assignedProver` reserves nothing without an `exclusivityDuration`. NONE jobs take no bids, so a competitive job for job-prover uses `JOB_BINDING=full` (`planFull(address)`: the FULL variant, open to every claimer and bidder; set `CLAIM_COMPETITIVE=1` too). The banner's `Descriptor:` line names the hash and the binding.
- The late-lock rescue follows the same rule (§6, "Late locks").

### `AuctionConfig` (11 fields)

```solidity
struct AuctionConfig {
    uint96  minPrice;              // in HEMI wei; the ramp's start (the price rises from here, §2); min == max means
                                   //   fixed price; also the bid floor (reserve)
    uint96  maxPrice;              // the ramp's top; must be >= minPrice
    uint40  rampUpPeriod;          // seconds (job-local) from submit to full price (<= 7 days)
    uint8   curveType;             // 0=Linear, 1=Quadratic (setter cap; higher reverts)
    uint40  fulfillmentTimeout;    // seconds the prover has after the lock (300 s .. 7 days)
    uint96  lockCollateralBps;     // bps of settledPrice locked as prover collateral; 0 = default
    uint96  speedPremium;          // extra HEMI paid if fulfilled fast; deposited by the caller; <= maxPrice; one budget across reopens (§5);
                                   // must be 0 on a competitive job (underbidWindow > 0), SpeedPremiumOnCompetitiveJob
    uint40  exclusivityDuration;   // seconds only assignedProver may claim: 0, or 60 s to 24h (InvalidExclusivityDuration);
                                   //   ignored for NONE (pass 0)
    uint32  callbackGasLimit;      // gas budget for the callback: 0 = default 200k, else 50k..500k
    bool    excludeFromEwma;       // ignored: governance sets it per program (forced true for NONE)
    bool    laxCallbackMode;       // accepted for compatibility, ignored at settlement (callbacks are observational); setPreset refuses true
}
```

Limits: `speedPremium <= maxPrice` (`InvalidSpeedPremium(speedPremium, maxPrice)`, also enforced by `setPreset`). For `CUSTOM_VERIFIER` jobs `lockCollateralBps <= 10_000` (100%; `InvalidCollateralBps`), and 0 defaults to 10,000 for them. Adapter jobs keep their default (the adapter's `defaultCollateralRatio`, else 15,000) and the 50,000 cap. The `MIN_COLLATERAL_AMOUNT` floor applies. So the collateral is `max(ceil(settledPrice × bps / 10,000), MIN_COLLATERAL_AMOUNT)` (the division rounds up), with `bps` the ratio resolved and snapshotted at submit (`lockCollateralBps`, or when it is 0 the defaults above) and the floor snapshotted at submit too (`getJobSnapshots`, §7); for a cheap job the floor dominates: with the 100 HEMI floor of the live chains, a 1-HEMI `CUSTOM_VERIFIER` job locks 100 HEMI, 100 times its price.

More submit checks the field comments do not show: `minPrice != maxPrice` with `rampUpPeriod = 0` reverts `InvalidRampUpConfig()` (a ramp needs a period; only a fixed-price job has none); a deposit `maxPrice + speedPremium` below `MIN_JOB_DEPOSIT` = 1 HEMI reverts `DepositTooSmall(deposit, minimum)`, and one above `type(uint96).max` `DepositOverflow(deposit)` (`test/b221i/LifecycleDocs221i.t.sol`, `test_r6d4_auctionConfigValidation`); the largest collateral the job can lock, `ceil(maxPrice × bps / 10,000)`, above `type(uint96).max` reverts `CollateralOverflow(collateral)` (the claim raises the same typed error, which a job accepted at submit never reaches); and a `CUSTOM_VERIFIER` job whose verifier is blacklisted reverts `BlacklistedVerifier(verifier)`, the error claim, bid and fulfil raise. A non-zero `exclusivityDuration` below 60 s (`MIN_EXCLUSIVITY_DURATION`) reverts `InvalidExclusivityDuration(duration)`, on submit and in `setPreset`: a window opens at the submit block, so 60 s reserves four 12-s blocks after it (a reactive prover lands one block after the submit at the earliest).

For a simple fixed-price test job: `minPrice == maxPrice`, `rampUpPeriod = 0`, `curveType = 0`, `fulfillmentTimeout = 3600`, everything else 0 or false. Deposit = `maxPrice + speedPremium`. NONE jobs should always be fixed-price (§3a).

`getPresetDeposit(name)` returns the deposit of a preset (`maxPrice + speedPremium`) as `uint256`. `setPreset` refuses a preset with `laxCallbackMode = true` (`InvalidConfig`).

### `CycleConfig` (8 fields; all zero for "no cycles")

`(uint64 expectedCycles, uint96 cycleCommitCollateral, uint8 snapshotMode, uint16 snapshotToleranceBps, uint16 snapshotFullBonusOvershootBps, uint16 snapshotUndershootPenaltyBps, uint16 snapshotFullPenaltyUndershootBps, uint16 snapshotResolverRewardBps)`. The `snapshot*` fields are overwritten at submit from the governance values (caller values ignored). Used only by a job whose adapter is registered with a cycle attestation mode (none is at launch: `expectedCycles > 0` then reverts `CycleCountsNotSupported`): in SelfVerified mode the adapter's reported cycle count settles the cycle terms at fulfil; in Committee mode the BatchCycleCommittee's attested median does, when the job's epoch resolves. `CUSTOM_VERIFIER` jobs are never metered. Leave zeroed for basic Groth16-only flows.

### `CompetitiveBidConfig` (5 fields; all zero for "no auction")

`(uint40 underbidWindow, uint40 maxBiddingDuration, uint40 maxBidExtension, uint96 minBidDecrement, uint8 bidExtensionCurveType)`. Enables bidding, where provers underbid each other below the Dutch ceiling. Leave zeroed for direct claim. `underbidWindow` and `maxBiddingDuration` are capped at 7 days and `maxBidExtension` at 24 hours (`InvalidBidConfig()`). `maxBidExtension` is 0 (every anti-snipe extension is exactly 60 s, `MIN_SNIPE_GUARD`) or at least 60 s: a value from 1 to 59 s would cut the extension below 60 s, down to no counter-bid block at all, and reverts `InvalidBidConfig()`. Not allowed on NONE jobs.
- **Ordered bounds.** With `underbidWindow > 0`, submit reverts `InvalidBidConfig()` unless `300 s (MIN_UNDERBID_WINDOW) ≤ underbidWindow ≤ maxBiddingDuration ≤ 7 days` and `maxBidExtension ≤ 24 h` (a `maxBiddingDuration` of 0 is `InvalidBidConfig`). `underbidWindow` is the exact length of every round's first bid window in job-local time (`firstBidTime + underbidWindow`; pauses and their grace tails only lengthen it). Anti-snipe extensions stay capped at `firstBidTime + maxBiddingDuration`, so they need `maxBiddingDuration > underbidWindow` (with equality they are no-ops).
- **No speed premium on a competitive job**: `speedPremium != 0` with `underbidWindow > 0` reverts `SpeedPremiumOnCompetitiveJob()` on every submit path. The premium is for Dutch-only jobs (§5).
- **`minBidDecrement` is required.** With `underbidWindow > 0`, `minBidDecrement = 0` reverts `Error("minBidDecrement required")` at submit (checked before the window bounds above), and `bidExtensionCurveType > 1` reverts `Error("Invalid bidExtensionCurveType")`. The decrement a bid must beat is the larger of `minBidDecrement` and 1% of the current bid (§4), so `minBidDecrement = 1` (wei) leaves the 1% rule alone; a 0 is not "1% only", it is a revert. On a `minPrice = 0` job the lowest bid is 1 wei: `submitBid(jobId, 0)` reverts `ZeroBidAmount()` (`test/b221i/LifecycleDocs221i.t.sol`, `test_r6d4_bidConfigValidation`, `test_r6d4_zeroBidAndDecrementRule`).

### Deposit accounting

At submit time, HemiProve pulls from `msg.sender`: `depositedAmount = maxPrice + speedPremium` plus `cycleCommitCollateral` when set. **Caller must have `approve`d the router first.**

`jobId = keccak256(abi.encode(block.chainid, router, jobIndex, descriptorHash))`. Grab it from the return value or from `event JobSubmitted(bytes32 indexed jobId, ...)`. `JobSubmitted` carries only `descriptorHash`: provers read the full descriptor, binding words included, from the submit calldata.

### FeeRateSnapshotted event

Emitted alongside `JobSubmitted`: `event FeeRateSnapshotted(bytes32 indexed jobId, uint16 feeRateBps)`. This is the **pinned** fee rate — the protocol fee at fulfill will always use this value, regardless of any governance changes between submit and fulfill (no fee-change sandwich). Off-chain indexers should record it per-job.

## 4. `claimJob` — prover locks

```solidity
// Every claim carries the lowest price and premium budget it accepts.
function claimJob(bytes32 jobId, uint96 priceFloor, uint96 premiumFloor)
    external whenNotPaused nonReentrant returns (uint96 price);                        // 0xb2f51925
function claimJobDelegated(bytes32 jobId, address prover, uint96 priceFloor, uint96 premiumFloor)
    external whenNotPaused nonReentrant returns (uint96 price);                        // 0x363e6708
function claimJobBatch(bytes32[] calldata jobIds, uint96[] calldata priceFloors, uint96[] calldata premiumFloors)
    external whenNotPaused nonReentrant returns (bool[] memory results);               // 0xf100ca00
```

The earlier one-argument forms (without floors) are unrouted (`Error("Unknown selector")`): rebuild every client.

- Reverts `ClaimBelowFloor(jobId, price, priceFloor, premiumCap, premiumFloor)` (`0xc8cea62a`), with nothing locked, unless the Dutch price at inclusion is ≥ `priceFloor` and the premium budget left (`getPremiumCap`) is ≥ `premiumFloor` ("Claim floors", below). `premiumCap` in the payload is always the live cap. The claim returns the price.
- Reverts `StakingBlockDelayNotMet` if the caller staked in the same block (`block.number > depositBlock` required). No wall-clock wait (there is no minimum staking age).
- Reverts `RegistryPaused(jobId)` while the Registry is paused, for every job except `CUSTOM_VERIFIER` jobs.
- Reverts `ExclusivityActive` if `assignedProver != 0`, the caller is someone else, and the exclusivity window is still open. The window is measured in job-local time, so any window that blocks the job (a pause, its adapter's disable, its verifier's blacklist) freezes it. A window is 0 or at least 60 s (§3). For a NONE job the assigned prover is the only possible locker, forever (§3a). A reopen keeps the window only in some cases (NONE jobs always keep their locker): `releaseJob` and `graceRelease*` clear `exclusivityDuration` and the assigned prover, so once the assigned prover releases, anyone may claim at once; a slash clears them when the slashed prover is the assigned one (or none is assigned) and keeps them when another prover held the lock (that window had already lapsed, and stays lapsed: "Competitive bidding" below); `gracePauseRelease` keeps them (§6; `test/b221i/LifecycleDocs221i.t.sol`, `test_r6d3_*`).
- Reverts `BiddingActive(jobId)` while a bid is live. Such a job is won by bidding (`submitBid` / `settleBid`), not by a direct claim. The round marker (`competitiveBidStartTime`) is set only while a round is live or its winner holds the lock: every bid drop (a governance-cause refund through `refundBid` or `settleBid`, the bid-phase `gracePauseRelease`) and every reopen (`releaseJob`, `gracePauseRelease`, `graceRelease*`, a slash) clears it, so the job is directly claimable again at a price at or below the round's best bid or the winning bid.
- Reverts `ReleaseCooldownActive(jobId, prover, end)` for 1 hour (`RELEASE_COOLDOWN`) after the same prover released this job or left it through `gracePauseRelease`, and after it took its own governance-cause bid refund (`refundBid` or its own `settleBid`), only when it took that refund before the bid's wall-clock deadline (`wallBidDeadline`). The same cooldown blocks `submitBid`.
- Reverts if `job.reopenCount >= MAX_REOPEN_COUNT (10)` (the reopen-loop backstop).
- Locks `ceil(settledPrice × bps / 10,000)` (the submit-time snapshot of the resolved ratio, §3; at least the submit-time `MIN_COLLATERAL_AMOUNT`) from the prover's stake as `lockedCollateral`. A collateral above `type(uint96).max` would revert `CollateralOverflow(collateral)`; submit already refuses a job that could reach it.
- Sets `lockDeadline = block.timestamp + fulfillmentTimeout`. The lock can still fulfil (speed bonus 0) through `lockDeadline + PROVER_GRACE` (30 min) and release until one second before it (release needs job-local time `< lockDeadline + PROVER_GRACE`, fulfil `≤`), and a slash opens 30 s after that (§6).
- Emits `JobClaimed(jobId, prover, operator, settledPrice, bonusAmount, lockDeadline)`. `bonusAmount` is always 0 (§6). `lockDeadline` is raw and only a lower bound of the effective deadline, even for a lock taken after a pause: a lock taken inside a `RESUME_GRACE` (the 15 min after the last lift of a blocked stretch) inherits the rest of that grace. Keepers schedule from `getJobStatusView` or `lockDeadline + getJobExtras(jobId).pauseCredit`, re-read at the time.

`settledPrice` at claim time = the Dutch price at the job's elapsed ramp time. The ramp runs in job-local time (the union pause clock, §7): a router pause freezes it, and so do a Registry pause and a Disabled window of the job's adapter (adapter jobs) or a blacklist window of the job's verifier (`CUSTOM_VERIFIER` jobs, which ignore a Registry pause). Overlapping windows freeze it once, and it stays frozen for `RESUME_GRACE` (15 min) after the last lift of a blocked stretch. For fixed-price (`min == max`) it's constant. After a reopen the ramp resumes where the last lock left it: at that lock's own price for a direct claim, and at `e*(S)`, the ramp point whose price is at most the winning bid `S`, for a lock won by bidding (`settleBid` stores it as `elapsedAtLock`). A reopened job resumes at (not above) the price it was last locked at, and the ramp rises from there as usual. It is directly claimable at once (the round marker is cleared), so the ramp rises only until someone claims or bids.

### Claim floors

A claim is priced at inclusion. Without a floor, any reset ordered ahead of your pending claim locks it at the lower price: a bid round that ends without a lock, a floor bid followed by `settleBid` and a zero-hold `releaseJob` (about 5 HEMI), or a free pause exit (residuals 16(a), 16(d)). With a floor it reverts `ClaimBelowFloor`, and the reset only delays you. The rules:
- **Exact floors, tolerance 0.** `priceFloor` = the price an `eth_call` of `claimJob(jobId, 0, 0)` from your claiming address returns at a **mined** block; `premiumFloor` = `getPremiumCap(jobId)` at that same block. No tolerance, also in a `RESUME_GRACE` tail: once a router pause has run longer than 15 min (from the pause start + 15 min + 1 s) every lock holder has a free exit (the Locked `gracePauseRelease`), so any tolerance is extractable for free. An honest claim still lands: inclusion only climbs the ramp, and the cap never rises, so an exact premium floor never reverts spuriously.
- **Never seed a floor** from `jobs(jobId).minPrice`, a `pending` read, 0, or `getCurrentPrice` (it reads 0 or the frozen ceiling while a bid is live or the job is Locked). A floor of 0 is accepted on-chain (a `minPrice = 0` job is priced 0) but leaves the claim repriceable (residual 16(l)).
- **`ClaimBelowFloor` and `BiddingActive` mean wait and retry, never chase the price down.** Re-quote at a later mined block. Keep a per-job price high-water mark (the highest floor you sent): never claim below it, and forget it only on your own lock, a terminal job or `MAX_REOPEN_COUNT`, never because another prover locked the job (a sybil's settle is such a lock). Never ratchet the premium floor. The reference daemons put such a job in a bounded claim retry set (`STATE_DIR/retry`: `CLAIM_RETRY_CAP` 256 entries, `CLAIM_RETRY_PER_CALLER` 16, `CLAIM_RETRY_BUDGET` 4 re-checks per poll, strictly after the key's own locks) and move the log cursor on; the entry leaves the set on a lock, a terminal job, `MAX_REOPEN_COUNT` or a deterministic skip, and a full set evicts entries that wait for free stake first (`PAGE: RETRY-FULL` when it has none; §3a, "The daemons' alert rule"); a pause, disable or blacklist revert is not a skip: the daemons hold the log cursor and keep the entry until the lift.
- **Funds.** A claim refused for funds holds the cursor (no new lock while a send of the key is unaffordable): the daemons' gate re-reads the balance before every claim and clears once it covers the refused send plus a claim, or on any accepted publish.
- **Canary.** After a mined claim check `JobClaimed.settledPrice ≥` the floor you sent (the daemons page `PAGE: CANARY`).
- **Competitive jobs** (`underbidWindow > 0`): the reference daemons skip them unless `CLAIM_COMPETITIVE=1`.
- **Abandoned claims.** A claim you stopped waiting for can stay pooled and land later at its embedded floor (≥ the high-water mark when signed): the mark binds new sends only. A same-nonce claim TTL-cancel is not implemented.
- **`claimJobBatch`.** The floor arrays are parallel to `jobIds` (`ArrayLengthMismatch(n, length)` for either, after `EmptyBatch` and `MaxBatchSizeExceeded`); an entry below its floors fails (`false`) with nothing locked. A `false` entry carries no reason: re-simulate that entry alone with `claimJob` before classifying it.
- **`claimJobDelegated`.** The operator (PERM_CLAIM-trusted) chooses the floors. Without them a delegated claim is repriceable like a direct one: a settle + release reset leaves `lastReopenTimestamp` 0, so the 24h delegated-claim cooldown does not fire (unless a slash stamped it less than 24h before: then the release re-stamps it, and delegated claims revert `DelegatedClaimCooldownActive(jobId, release + 24h)`, §6 "Release"). The operator can claim but not release: `releaseJob` is the lock's prover's own (`JobNotLocked` for anyone else).
- **`slashAndClaim(jobId, priceFloor)`** takes the floor of the lock you observed (§6, "Late locks").

### One-transaction claim and fulfil for a reserved job (`claimAndFulfillAssigned`)

```solidity
function claimAndFulfillAssigned(
    bytes32 jobId,
    uint96 priceFloor,                    // claimJob's floors, with the same meaning
    uint96 premiumFloor,
    JobDescriptor calldata descriptor,    // as fulfillJob
    bytes calldata publicValues,
    bytes calldata proofBytes
) external whenNotPaused nonReentrant returns (uint96 price);                          // 0xce6eda56 (Fulfill facet)
```

It claims an Open job reserved to the caller and fulfils it in the same transaction, and returns the claim price. `JobClaimed` and then `JobFulfilled` are emitted in that one transaction.
- **Reserved to the caller at inclusion** means: a NONE job whose assigned prover is the caller, or a job whose assigned prover is the caller, inside its live exclusivity window (job-local time `< rampUpStart + exclusivityDuration`). Any other Open job reverts `NotReserved(jobId)` (`0x33529975`) before any claim check: an open job, a job with no window or an ended one, a window with no assigned prover or another one. A NONE job assigned to someone else reverts `ExclusivityActive`, a live bid or bid round `BiddingActive`, as `claimJob`. A job that is not Open, or does not exist, gets `claimJob`'s `JobNotOpen` / `JobNotFound`. While the job is reserved to you nobody else can lock it or bid on it in that block.
- **Direct only.** The caller is the prover: an operator key sending it is a third party (`NotReserved`, or `ExclusivityActive` on a NONE job). Delegated provers claim with `claimJobDelegated` and fulfil themselves. There is no batch variant (a `multicall` of several such calls is atomic: each must be reserved to the sender).
- **The legs.** The claim leg is `claimJob`'s rules in `claimJob`'s order (the release cooldown, the reopen limit, the adapter, Registry and verifier states, stake eligibility, the floors: `ClaimBelowFloor` with nothing locked). The exact floors are the price an `eth_call` of this function (or of `claimJob(jobId, 0, 0)`) returns at a mined block, and `getPremiumCap(jobId)` at that block (§4, "Claim floors"). Collateral is locked as for any claim and released by the fulfil in the same transaction. The fulfil leg is `fulfillJob`'s, with the caller as the lock's prover: the descriptor hash, the journal cap, the binding (a marker's prefix or nonce names the caller), the governance errors, the gas preflight, the verifier, the settlement and the callback (§5). Any failure reverts both legs: nothing is claimed.
- **The bonus.** The lock is fresh (`lockDeadline = now + fulfillmentTimeout`), so the speed bonus is the whole premium budget left, `getPremiumCap(jobId)` at inclusion (`previewSpeedBonus(jobId)` of the Open job, §7). Against a claim and a fulfil one block later it pays the caller's premium rate for the block saved (`speedPremium × 12 s / fulfillmentTimeout` more); with no premium the payment is the same.
- **What it saves.** One inclusion and one receipt wait (the result lands a block earlier), about 45,000 L2 gas against `claimJob` then `fulfillJob` (one 21,000 base cost, the claim's calldata, the second transaction's cold reads: about 7% of a real Groth16 fulfil, not half), and one L1 data fee.
- **When it is safe.** The proof travels in the mempool while the job is still Open: it is the broadcast rule's one exception (§3a). Use it for a job with a binding marker, or for a requester you trust, and then for a window job only with at least 60 s of the window left in job-local time (a transaction held past the window end reverts `NotReserved`, its proof is then public, and the job is open to anyone; `getJobStatusView` or `getJobExtras` give the credit). Otherwise `claimJob` alone, then fulfil after the receipt. The caller of the Open job can always cancel ahead of it and keep the result: you lose the proving work, never stake. A job settled this way is never Locked across a block: no release, slash or reopen applies to it.
- **Gas limit:** the fulfil formula of §9 over this call's calldata, plus the claim leg, which runs before the fulfil preflight. `script/lib/FulfillGas.sol` `forClaimAndFulfillAssigned` adds 300,000 (`CLAIM_LEG_GAS`; a cold claim leg measures about 95,000), and `claimAndFulfillAtQuote` sends it at the exact floors, only for a descriptor that assigns the job to the broadcaster and is NONE-bound (use it only for jobs whose caller you trust, such as your own `script/job-submitter.sh` drill jobs) or carries a binding marker; anything else it refuses, to be claimed first. `script/TestFulfill.s.sol --sig 'claimAndFulfill()'` does it for a `job-submitter.sh` drill job (§9).

### Competitive bidding (`submitBid`, `settleBid`)

- `submitBid(jobId, bidAmount)` reverts `BidBelowMinPrice(bid, minPrice)` when `bidAmount < minPrice`: `minPrice` is the caller's reserve. Set it deliberately on competitive jobs (an SDK default of at least 10% of `maxPrice` is sensible); with the floor, two provers racing at ramp start settle at `minPrice`.
- Eligibility at bid time counts stake net of the prover's pending unstake. It is checked at bid time only: a `requestUnstake` after the bid is not re-checked. The soft-lock, not the remaining stake, secures the bid.
- The ceiling is frozen at the Dutch price of the round's first bid while bids are live. When a bid is dropped without a lock (a governance-cause refund through `refundBid` or `settleBid`, the bid-phase `gracePauseRelease`), the ramp resumes at the **best live bid** (its ramp point, rounded down; or the first-bid point if that is lower) and the round marker is cleared: a direct claim then locks at a price ≤ that bid, and the next bid opens a new round. At settle the lock records `e*(S)` (above), so a release, a grace release or a slash of the winner reopens the job at a price ≤ the winning bid, directly claimable.
- **Binding bids.** A live bid ends only in a lock (`settleBid`) or an outbid, unless a governance cause holds or a pause has run longer than 7 days. There is no forfeit (a 100% burn of the soft-lock before the bid deadline): it would let any bidder end a live round at a price nobody stood behind, which reprices every pending claim. `releaseJob` is Locked only (`JobNotLocked` on an Open job).
  - **`refundBid(jobId)`** (`0x427163dc`; no pause gate): the live bidder's free refund while a governance cause holds (the adapter Disabled or Unregistered; for a `CUSTOM_VERIFIER` job the verifier blacklisted), exactly `settleBid`'s governance-cause predicate. The soft-lock is unlocked (nothing burned), the ramp resumes at the best live bid with the round marker cleared, `BidInvalidated(jobId, bidder)`. `JobNotOpen` for a job that is not Open, `NotJobProver` for anyone but the live bidder, `NoGovernanceCause(jobId)` (`0x2bc6444e`) without a cause. A codeless custom verifier is not a cause (submit, bid and claim refuse one; under EIP-6780 code you saw cannot vanish later).
  - **The cooldown is keyed on the wall clock.** Your own refund (`refundBid`, or your own `settleBid` under a cause) cools you down on the job for 1h only if it lands before `wallBidDeadline`. From that deadline anyone gets the identical refund through `settleBid` uncooled, and a cause freezes job-local time, so a job-local rule would cool an honest winner settling late and hand its round to another prover.
  - **Through pauses.** A bid stays binding through any router or Registry pause of up to 7 days (the bid-phase `gracePauseRelease` needs a pause longer than that, §6): a routine pause only freezes the round, which resumes at the lift with its remaining job-local time. Your soft-lock stays locked up to `maxBiddingDuration` + pause credit, plus up to 7 days of pause (residual 16(h)). The 7 days apply to a round still live at the pause start: if your round had already ended when the pause began and nobody had settled it, the bid stays soft-locked for the whole pause, however long (`gracePauseRelease` reverts `BidDeadlinePassed`, `settleBid` is paused, `refundBid` needs a cause), and becomes your lock when it is settled after the lift. Settle a won round at once.
  - **The walk-away** is: wait for the round to end, `settleBid` (anyone may, once the round has ended in job-local time and the router is unpaused: `getJobStatusView(jobId).bidDeadline`, which equals `wallBidDeadline` unless pause credit accrued after the last bid: a pause that began after it, or a clock still running at the bid, such as a lift's `RESUME_GRACE` tail; the view is then later by that credit, never earlier, `test_r6g2_viewBidDeadline_divergesInGraceTail`), then fulfil or `releaseJob` at the snapshotted penalty: `releasePenaltyBps × max(S × collateralBps / 10,000, minCollateral) / 10,000` for your winning bid S, all three from `getJobSnapshots(jobId)` (5% by default; the penalty floor can be governed down to 1%). Price it into the bid. `cancelJob` reverts `BidsActive` while a bid is live, and `cancelStaleJob` is not a bidder exit (it needs a Disabled adapter, a blacklisted verifier or `MAX_REOPEN_COUNT`).
  - Settle locks the bid's soft-lock as the lock collateral (the same formula on the same per-job snapshots); there is no top-up.
- A bid that does not undercut the current bid by the minimum decrement (the larger of `minBidDecrement` and 1% of the current bid) reverts `BidDecrementTooSmall(decrement, minimum)`; an overbid (bid ≥ current bid) reports `decrement = 0`, never a Panic. `minBidDecrement` is at least 1 wei (a 0 reverts at submit, §3), and a bid of 0 reverts `ZeroBidAmount()` whatever `minPrice` is. A bid whose soft-lock collateral would exceed `type(uint96).max` reverts `SoftLockCollateralOverflow(collateral)`; submit's own collateral-overflow check makes this unreachable for any accepted job.
- Bid windows (`bidDeadline`, `maxBiddingDuration`, extensions) run in job-local time: a pause freezes them. `BidSubmitted.newBidDeadline` is the wall-clock-effective deadline at emission, and `getBidState(jobId).wallBidDeadline` stores it (pause credit earned after that bid does not move it; the 6-value `bidStates(jobId)` getter does not return it). `BidDeadlineNotPassed.deadline` (except on a third party's early settle, below), the stored `bidDeadline` and `firstBidTime`, and `competitiveBidStartTime(jobId)` are raw job-local values. Adding `getJobExtras(jobId).pauseCredit` converts only `bidDeadline` (and a Locked job's `lockDeadline`) to the wall clock; `firstBidTime`, `competitiveBidStartTime` and `settlementTimestamp` are readings in an older frame, used only as differences. Or read `getJobStatusView`.
- `settleBid` does not re-check the winner's stake: the soft-locked bid collateral secures it, so letting stake drop is not a free exit. A bid is refunded (`BidInvalidated`) when governance disabled or unregistered the adapter or blacklisted the verifier, and for no other cause. Such a governance-cause refund is available to the **live bidder** as soon as the cause exists (the disable stops the job's own clock, so it cannot wait for the job-local deadline), through `settleBid` or `refundBid`, and stamps its 1h cooldown only before `wallBidDeadline` (above). Anyone else must wait until the wall clock passes `wallBidDeadline`, the deadline the last bid announced (`BidDeadlineNotPassed(jobId, wallBidDeadline)` before; a gate on the job-local `bidDeadline`, which a job with pause credit reaches early on the wall clock, would let a third party strip a live bid mid-round during a disable). That covers only credit earned before the last bid: a router or Registry pause after it does not move `wallBidDeadline`, so after such a pause the wall clock can pass `wallBidDeadline` while the round still has job-local time left, and a third party can then strip it as soon as a cause begins (residual 16(j); the outcome is the lift race, 16(c)). A third party's invalidation does not cool the bidder down. A live bidder whose bid is not invalid still waits for the job-local deadline. A settle that locks the job needs the job-local deadline. The caller can then `cancelJob` (no bid is live any more; `CancelDelayNotMet` still applies within 24h of a `lastReopenTimestamp` stamp: a slash's, or a direct release's inside a slash's 24h, §6 "Release").
- `submitBid` reverts `CustomVerifierHasNoCode(verifier)` for a custom verifier without code.
- **Settle promptly.** `settleBid` is permissionless and pays nobody, and the winner's timeout starts only at settle. A winner that skips it cannot leave through the bid-phase `gracePauseRelease` once the round has ended (`BidDeadlinePassed`), and has no other exit without a cause: a lazy winner sits until someone settles it after the round's job-local end (`getJobStatusView(jobId).bidDeadline`; `wallBidDeadline` unless pause credit accrued after the last bid, a resume-grace tail running at the bid included). Callers and keepers should settle finished rounds.
- An assigned prover's exclusivity window that has lapsed is never re-armed by a bid drop or a reopen: a bid drop shortens `exclusivityDuration` by the ramp shift, and `settleBid` keeps only the time the assigned prover had left (nothing if the window had lapsed or another prover won). A later reopen restores that time only through a `gracePauseRelease` or a slash of another prover: a release, a `graceRelease*` or a slash of the assigned prover itself clears the window (above, `ExclusivityActive`).
- **Hold loops (delay griefing).** A bid at `minPrice` cannot be underbid. The cheapest delay round is: bid at the floor, settle, hold the lock until just before the end of its grace (`lockDeadline + PROVER_GRACE`), `releaseJob`. It costs 5% of the collateral, fully burned, which is 5 HEMI at the 100 HEMI collateral floor for any `minPrice` below about 66.7 HEMI, lasts up to `underbidWindow + fulfillmentTimeout + 30 min`, needs only two identities (the 1h cooldown is per prover and job), and repeats up to `MAX_REOPEN_COUNT` = 10 times. A plain Dutch job with `minPrice` near 0 has the same loop through `claimJob` / `releaseJob`. The loop buys only delay: the job comes back at a price ≤ the last lock's, directly claimable. A release with nothing left to earn spends the job's whole speed-premium budget (§5). **Each round's delay also includes the re-climb**: a winning floor bid released at once puts the ramp back at `minPrice` (`e*(minPrice) = 0`), and a prover whose cost is above that waits for the ramp to climb back, up to `rampUpPeriod` (≤ 7 days). Callers of competitive jobs: set `minPrice` near the expected clearing price and keep `rampUpPeriod` short; also windows of at least 5 min (the submit minimum) and no longer than needed, exclusivity or NONE, a higher `lockCollateralBps`, and an alert on repeated `JobReleased` / `BidSettled` for one job; at `MAX_REOPEN_COUNT` anyone can cancel the job (§6).
  - **What the floors change** (residuals 16(a), 16(b), 16(e)). The cheapest reset of a pending claim is a sybil floor bid, ≥ 300 s of round (25 Hemi blocks without your claim, then ordered ahead of it in the 26th), then `settleBid` + a zero-hold `releaseJob`: `penaltyBps × max(S × collateralBps, minCollateral)` of the snapshots, 5 HEMI at 5% (1 HEMI at the 1% floor), and the job reopens at `e*(S)` with the marker cleared. For a **floored** claim it is delay only: the claim reverts `ClaimBelowFloor` and is retried at the next quote. A floorless or chasing claim, direct or delegated, is repriced. A floor bid also blocks direct claims for ≥ 300 s per round (up to `maxBiddingDuration` + pause credit, at most 10 rounds) while it binds the bidder. The job kill does not need rounds: ten sybil claim + release pairs in one block take a job to `MAX_REOPEN_COUNT` (about 50 HEMI at 5% on a floor-bound collateral), after which anyone may `cancelStaleJob` it at once and the caller is refunded.
- `settleBid` and `submitBid` revert `RegistryPaused(jobId)` while the Registry is paused (except `CUSTOM_VERIFIER` jobs); the governance-cause refund above still goes through.
- **Underbid censorship** (a residual). On Hemi's tip-ordered blocks the incumbent bidder can try to keep underbids out of blocks until the bid deadline. Bid early rather than at the last block, and re-sign a stuck bid at the same nonce with a higher tip (§6, "Inclusion delay").

## 5. `fulfillJob` — settle with a proof

```solidity
function fulfillJob(
    bytes32 jobId,
    JobDescriptor calldata descriptor,   // MUST match the descriptor at submit (hash-checked)
    bytes calldata publicValues,          // the journal / SP1 public values
    bytes calldata proofBytes             // the seal
) external whenNotPaused nonReentrant;

function fulfillJobHashed(
    bytes32 jobId,
    HashedDescriptor calldata hd,         // (programId, proofSystemId, callbackContract, assignedProver, tag,
                                          //  inputDataHash, expectedJournalHash, journalFields): 8 fields
    bytes calldata callbackExtraData,
    bytes calldata extraVerifierData,
    bytes calldata publicValues,
    bytes calldata proofBytes
) external whenNotPaused nonReentrant;   // skips sending inputData; supports every binding mode
```

`HashedDescriptor` carries `expectedJournalHash` and `journalFields`, copied verbatim from the job's descriptor. The hashed path re-derives the same `descriptorHash` and checks the binding exactly like `fulfillJob`.

Preconditions:
- Job status must be `Locked`.
- `msg.sender == job.prover`.
- Not past the end of the prover's grace: job-local time `<= lockDeadline + PROVER_GRACE` (30 min). Effective deadline (wall clock) = `jobs(jobId).lockDeadline + pauseCredit` (`getJobExtras`, §7); the fulfil is accepted until 30 min after it, with a speed bonus of 0 from the deadline on.
- The descriptor hashes to `job.descriptorHash`: `keccak256(abi.encode(programId, proofSystemId, callbackContract, assignedProver, tag, keccak256(inputData), keccak256(callbackExtraData), keccak256(extraVerifierData), expectedJournalHash, journalFields))`, 10 words (it is **not** `keccak256(abi.encode(descriptor))`).
- `publicValues.length <= MAX_JOURNAL_BYTES` (32,768), else `JournalTooLarge(length, max)`.
- A binding marker's check passes (§3a): the journal prefix, else `JournalPrefixMismatch(jobId, prover)`; the SP1 proof nonce, else `ProofNonceMismatch(expected, actual)`.
- The journal (after the prefix, under the journal-prefix marker) matches the binding (§3a), else `JournalMismatch(expected, actual)`.

The journal cap and the binding are checked first. Then the router reads the governance state that would block the verification, then its gas preflight runs (§9), and then the adapter is looked up by `descriptor.proofSystemId` (through the Registry) and called as `verifyProof(programId, publicValues, proofBytes, extraVerifierData)`. The full revert order (`fulfillJobHashed` the same; `fulfillJobBatch` per job; `claimAndFulfillAssigned` from step 4 on, after `EnforcedPause`, `NotReserved` and the claim leg's errors, §4):
1. `EnforcedPause()` (the router is paused);
2. `JobNotLocked(jobId)`, `NotJobProver(jobId, sender)`;
3. "Past deadline" (job-local time past `lockDeadline + PROVER_GRACE`);
4. `InvalidDescriptorHash(expected, actual)`;
5. `JournalTooLarge(length, max)`, then the marker's `JournalPrefixMismatch(jobId, prover)` or `ProofNonceMismatch(expected, actual)`, then `JournalMismatch(expected, actual)`;
6. adapter jobs: `RegistryPaused(jobId)` (the Registry is paused), then `AdapterDisabled(psId)`; `CUSTOM_VERIFIER` jobs: `BlacklistedVerifier(verifier)`;
7. `InsufficientGasForFullSettlement()`;
8. the verifier call: `VerifierCallFailed()` (fixed, selector-free: the verifier or the Registry call reverted, returned fewer than 32 bytes or ran out of its gas budget; the verifier's own revert data never crosses); adapter jobs then `InsufficientGasForSettlement()`.

Adapters attest only that tuple: no jobId, prover or caller context reaches them (`IHemiProveVerifier`); the router itself binds the job and the prover, through the markers (§3a). If verification fails, the tx reverts (the prover keeps its collateral but no payout, and can retry until the end of its grace). There is no relayed or signed fulfil path: every fulfil is sent by the job's prover itself.

**Which reverts mean what**. A failed fulfil is either a defect of your proof (release: 5%, burned, beats a 100% slash) or a temporary state (keep the lock; it is credited while the state lasts):

| Revert | Meaning | Do |
|---|---|---|
| `JournalMismatch`, `JournalTooLarge`, `InvalidDescriptorHash` | your journal or descriptor cannot be paid | fix it if you can; otherwise `releaseJob` before the end of the grace |
| `JournalPrefixMismatch`, `ProofNonceMismatch` | your proof was not made for this job and your staked address: a journal without your prefix, a seal with nonce 0 (a stock SP1 prover, the prover network) or another job's or prover's nonce | re-prove with your own prefix or `getProofNonce` limbs if that fits before `D + G`; otherwise `releaseJob` |
| `VerifierCallFailed()` | the verifier rejected the proof, **or** a state the router did not name | adapter job: re-read `Registry.paused()` and the adapter status **at the same block**, and release only if neither shows a cause (Disabled; Unregistered is no cause). `CUSTOM_VERIFIER` job: only `isBlacklisted(verifier)` is a cause (a Registry pause neither blocks nor credits it): release unless it is blacklisted |
| `RegistryPaused`, `AdapterDisabled`, `BlacklistedVerifier`, `EnforcedPause` | a governance pause, disable or blacklist | **keep**: retry after the lift, or take the free exit (`gracePauseRelease` after 15 min of a pause; `graceRelease*` during a disable or blacklist) |
| `InsufficientGasForFullSettlement` | your gas limit | resend with more gas (§9) |
| "Past deadline" | the grace is over | do not resend: the next send publishes your proof (§6, "Late locks") |
| no revert data (HTTP 429, 5xx, a timeout, a refused connection) | your transport | retry with backoff; **never release on it** |

Payout math (all in HEMI wei; cycle-mode terms omitted):
```
protocolFee    = (settledPrice + speedBonus) * feeRateSnap / 10000   // feeRateSnap pinned at submit
proverPayout   = settledPrice + speedBonus + bonusAmount - protocolFee
callerRefund   = depositedAmount - settledPrice - speedBonus
// Conservation: proverPayout + callerRefund + protocolFee == depositedAmount + bonusAmount
// bonusAmount == 0 for every job (§6)
```

`JobFulfilled.protocolFee` is the fee **after** the committee diversion (the share sent to the BatchCycleCommittee reward pool when `committeeRewardDiversionBps > 0`), so from the event the identity reads `proverPayout + callerRefund + protocolFee + diverted == depositedAmount + bonusAmount`.

The protocol fee (and its committee share) is charged on the speed bonus too, not only on `settledPrice`.

**Speed premium**. `speedPremium` is one **cumulative** budget per job, not per lock, and only Dutch jobs carry one: a competitive job (`underbidWindow > 0`) with a premium reverts `SpeedPremiumOnCompetitiveJob()` at submit, so every lock of a premium job is claim-won and `getPremiumCap` is 0 on a competitive job:
```
remaining  = min(effective lockDeadline - now, fulfillmentTimeout)   // job-local; pause credit counts as time left; 0 from the deadline on
u          = speedPremium * remaining / fulfillmentTimeout            // this lock's uncapped bonus
used       = speedPremium - getPremiumCap(jobId)                      // spent by the job's earlier locks
speedBonus = max(0, u - used)                                         // never reverts; a first lock is paid u
```
- `getPremiumCap(jobId)` is the budget **left**: it starts at `speedPremium` and only falls. At every reopen (Locked → Open) the lock being given up is charged its share, `speedPremium − u` at that moment (rounded up, added to what earlier locks used, clamped at the whole budget): at the release for `releaseJob`, at the pause start for `gracePauseRelease`, at the disable or blacklist start for `graceRelease*` (job-local time is frozen from then). A slash spends the whole budget. Claim-won holds h1, …, hk that end in releases, followed by a fulfil after hold h, pay `max(0, speedPremium × (1 − (h1 + … + hk + h) / fulfillmentTimeout))`, the same as one lock held for the total, so splitting a hold across sybil locks gains nothing.
- A zero-hold release costs the budget nothing. A release with nothing left to earn (at the deadline, or in the grace) spends all of it, so every later lock of the job earns 0. Since every premium lock is claim-won, the budget is exactly the one-lock model.
- **Hold-and-release** (residual 16(i)): an intervening locker that holds a Dutch premium job for h and releases strips `speedPremium × h / fulfillmentTimeout` from every later prover, for the 5% release, or for nothing under a pause that has run longer than 15 min (residual 16(d), §6; the exit opens at the pause start + 15 min + 1 s). The stripped premium is refunded to the caller, and a pending claim whose `premiumFloor` was the exact cap reverts `ClaimBelowFloor` (re-quote and retry).
- Worked numbers (`speedPremium` = 100, `fulfillmentTimeout` = 1h): one lock fulfilled 54 min in is paid 10. Lock A held 27 min and released, then lock B fulfilling 27 min in: cap 55, B paid 10. Holds of 10 and 15 min released, then a lock fulfilling 5 min in: cap 58.33, paid 50. A 59-min hold released leaves 1.67. Two holds released 1 s before their deadlines leave 0.0278, then 0. A Dutch hold loop with a premium of 1,000 and a 2h timeout, ten 1h holds by two identities: the budget is gone after the second hold.
- The premium measures lock-to-fulfil latency. A prover that proves first still earns almost all of it, but it claims **alone** and fulfils after the claim's receipt (§3a, the broadcast rule): that costs `speedPremium × 12 s / fulfillmentTimeout` when the fulfil lands in the next block. Never send claim and fulfil together. What the budget removes is the payment for holding a reservation.
- A lock or a submit inside a `RESUME_GRACE` (the 15 min after the last lift of a blocked stretch) inherits the rest of the grace as extra time (one grace, however many windows overlapped), and a fulfil inside that grace is paid its whole uncapped bonus, within the budget left. Bounded by `speedPremium`.
- The bonus is 0 from the deadline on, also inside the prover's grace: whoever delays your fulfil's inclusion until the deadline strips the premium (it goes back to the caller). Fulfil as soon as the proof exists, with tip escalation (§6, "Inclusion delay").
- `getJobStatusView` reports the raw `speedPremium`; read the cap with `getPremiumCap` (FulfillCycle facet, at the router).

Post-fulfill: `job.status = Fulfilled`, `lockedCollateral` released back to prover's `totalStaked`, the protocol fee (after the committee diversion) added to the router's `accumulatedProtocolFees()`, prover stats incremented, EWMA updated (unless excluded).

**The fee stays in the router.** Nothing reaches `protocolFeeRecipient` at fulfil: the router keeps the fee (of the job's deposit it pays out everything else, so its HEMI balance ends the fulfil higher by exactly the accrued amount). The only exit is `withdrawProtocolFees()`, an owner call (so a 24h GT op on the live chains, not a guardian emergency selector), which sends the whole accrued amount to the `protocolFeeRecipient` set **at the withdrawal** and emits `ProtocolFeesWithdrawn(recipient, amount)`; with nothing accrued it reverts "No fees". Treasuries and monitors watch `accumulatedProtocolFees()` and `ProtocolFeesWithdrawn`, not the recipient's balance (`test/b221i/LifecycleDocs221i.t.sol`, `test_r6d5_feeAccruesInRouterUntilWithdraw`).

Emits: `JobFulfilled(jobId, prover, caller, settledPrice, bonusAmount, proverPayout, callerRefund, protocolFee, speedBonus, actualCycles, publicValues)`.

### Callback (optional)

If `descriptor.callbackContract != address(0)`, HemiProve calls `IHemiProveCallback.onProofVerified(context, publicValues, callbackExtraData)` **at most once per job**: in the transaction that fulfils the job, under `callbackGasLimit`, and only if the address has code. It is never called for a job that is cancelled or never fulfilled, never at a slash, release or reopen, and never retried. The callback is **observational**: the job settles and the prover is paid whatever it does. `CallbackFailed(jobId, callback, reason)` is emitted if and only if:
- the address has no code (an EOA, a precompile, a contract not deployed yet): it is **not called**, and `reason` is empty;
- the call reverts (out of gas included); or
- it returns at least 32 bytes whose first word is zero.

`reason` is the first 256 bytes of the revert or return data. Any other outcome is an accept and emits nothing: a non-zero first word (any value, not only a canonical `true`), or a return shorter than 32 bytes (empty included) from a contract. An empty `reason` is a codeless target or an empty revert (`eth_getCode` at that block tells them apart). Nothing requires the address to implement `IHemiProveCallback`, and submit does not check its code, so a callback deployed later (CREATE2) is called once it has code: check the code on the target chain before you submit. There is no rejection counter and no force-accept split. To make payment conditional, use the binding (§3a), never the callback; to see whether a result was delivered, watch `JobFulfilled` and `CallbackFailed`, never only your own callback.
- **It runs inside the prover's fulfil transaction**, before the job settles. The prover chooses when it runs (any time up to the end of its grace, in any order across your jobs) and pays its gas up to `callbackGasLimit`; `tx.origin` is the prover.
- **Use `context`, not the router's views of the job.** During the callback `verifiedResults(jobId)` and `getVerifiedResult(jobId)` revert `PendingSettlement(jobId)` (`isPendingSettlement(jobId)` is true), `getJobStatusView(jobId)` reports the job Fulfilled (its other members still pre-settlement), and the raw `jobs(jobId)` getter returns the pre-settlement (Locked) values.
- **`context.settledPrice` is the claim price, without the speed bonus.** The bonus, the fee and the payout are in `JobFulfilled` (§8), emitted after the callback; `previewSpeedBonus(jobId)` read during the callback returns the bonus about to be paid.
- **`publicValues` is the whole journal**: under the journal-prefix marker it starts with the 64-byte prefix, and the program's own output starts at byte 64.

**Authenticate every callback**. Anyone can submit a job that names **your** contract as its callback, with any `programId` and an accept-all custom verifier: the binding protects only the payer of that job, not you. A callback handler that changes state must:
- require `msg.sender == HEMIPROVE` (the router; `HemiProveCallbackBase` does this);
- accept only its **own** jobs: `context.caller == address(this)` and a job id it recorded when it submitted (`HemiProveConsumer` does both through `pendingJobs`);
- check what it relies on: `context.trust == GovernanceApproved` (no custom verifier), the proof system and the `programId`. `HemiProveConsumer` exposes an `_authorizeJob(ProofContext)` hook for this (default: accept). Check `context.proofSystemId` even for an SP1 program you trust: its vkey settles under both SP1 ids, each on its own setup (the Groth16 ceremony, the PLONK reference string; `DEPLOY_RUNBOOK.md` residual 18), so a check of the `programId` alone accepts both and rests on both;
- bind the commitment it checks with a FIELDS pin instead of trusting a value from `callbackExtraData`, which the submitter chose.

The repo's `src/examples/SchemaValidatedCallback.sol` follows this template too (it inherits `HemiProveConsumer`; jobs are submitted with its owner-only `requestProof`). An older version of it stored and decoded the result of any job naming it: do not copy one.

**A callback that decodes with a `ProgramRegistry` schema** decodes with a copy of a schema its owner reviewed off-chain, never with the registry's live entry. The entry's controller (a first-come registrant, or its family admin) can replace the schema in any block, including around your transaction inside one block, so a schema taken from the registry when you request the proof can be its own. Store the reviewed bytes when you pin the schema (a constant, a constructor argument, an owner-only setter, or a `requestProof` argument only when `requestProof` is owner-only: on a permissionless request the requester chooses the schema): ship them, have the owner supply them, or copy the registry's bytes once at the pin and check them against the reviewed hash. Record the pinned hash with each job and decode every result with that copy. Never read the registry when you request: a comparison there adds nothing once the copy is held, and lets the controller refuse every later request with one `setIOSchema`. A program's registry status is advisory as well (a revoked program's jobs still settle): watch `ProgramRevoked` for the programs you pin and unpin to stop (`IO_SCHEMA_INTEGRATION_GUIDE.md`, "Pin the schema you decode with"; `SchemaValidatedCallback`: `pinSchema`, `pinSchemaHash`, `SchemaHashMismatch` at the pin, `SchemaNotPinned`). Decode every field with one `SchemaLib.decode` call: one self-call per field re-parses the schema each time, which puts an 8-field schema such as Oxygen's over the 500,000 `callbackGasLimit` cap (about 570,000 gas), where one pass needs about 330,000 on a program's first result (`IO_SCHEMA_INTEGRATION_GUIDE.md`, "Decode every field in one call").

`HemiProveConsumer` returns `false` without touching its state for any job that is not its own; one of its own jobs leaves `pendingJobs` before `_authorizeJob` runs (the router calls back at most once), so a job that `_authorizeJob` refuses also returns `false` and is no longer pending. A handler that reverts rolls its state back, `pendingJobs` included (the base runs it inside a self-call): the job then stays pending until it is cleared (below).

**Consumer bookkeeping: cancel and clear.** A consumer's job can end without its handler running to completion: a third party's `cancelStaleJob` (at `MAX_REOPEN_COUNT`, or after a long disable; it refunds the consumer), or a fulfil whose callback failed or was refused. The template handles both:
- `_cancelProof(jobId) returns (bool ended)`: a job that has ended (Fulfilled or Cancelled, by anyone) is not sent to the router, its bookkeeping is cleared; any other status (Open, Locked, or a value the template does not know) calls the router's `cancelJob` (the router's revert passes through: `JobNotExpired` for a live lock, `BidsActive`, `CancelDelayNotMet`, ...), then re-reads the status and clears the job if it has ended. It returns `false`, leaving the job pending, when the call only slashed an expired lock (the job reopened; cancel again after the 24h delay, and retry on `CancelDelayNotMet`: a claim + release inside that 24h moves the delay to 24h after the release, §6 "Release"). Expose it behind your own access control.
- `clearEndedJob(bytes32 jobId) returns (bool cleared)` (`0xd5007b67`, public, anyone): clears the bookkeeping of a job that has ended on HemiProve, whoever ended it. It only reads the router (an ended job never calls back again), deletes `pendingJobs[jobId]` and emits `ProofCancelled(jobId)` (Cancelled; the deposit was refunded to the consumer) or `ProofDropped(jobId)` (Fulfilled, but the result was not applied here: the journal is in the router's `JobFulfilled`). It returns `false`, changing nothing, for a live job, an unknown status, a job that does not exist, an id with nothing recorded, and for the job whose result the contract is handling (a transient mark: the router reports that job Fulfilled during its callback).
- `_onJobEnded(bytes32 jobId) internal virtual returns (bool cleared)`: the hook where an inheritor clears its own state for an ended job (`OxygenConsumer` clears its current job, so its keeper's next `proveNextBlock` heals at once; `HashChainConsumer` deletes `jobParams`). It runs on every clear, also for ids the contract never submitted: check your own state.
- **Decode router enums tolerantly.** The template reads `getJobStatusView`'s status as a raw `uint8` (`_jobStatusRaw`) and treats a value it does not know as "not ended"; `_jobStatus` reverts `UnknownJobStatus(status)` for one. `onProofVerified` forwards its calldata unchanged to the handler, so a `ProofContext.trust` value the base does not know reverts only where an inheritor reads it (the callback then returns `false`: an unknown trust is never treated as `GovernanceApproved`). Router enums that reach callbacks or views (`JobStatus`, `VerifierTrust`, `AdapterStatus`, `CycleAttestationMode`, `CurveType`) are append-only and frozen in what existing callbacks and views carry (`CHANGELOG_ABI.md`, the standing rule): a new state maps onto an existing member or ships behind a new selector. Decode them as `uint8` in your own code too, and never let an unknown value revert a path that must complete.

The commitment templates (`InputCommitmentCallback`, `PrivateInputCallback`) detect a wrong input but cannot withhold payment, and `PrivateInputCallback`'s predicted jobId breaks if another submit lands first: store the commitment under the jobId the submit returns. Their commitments are public: commit `H(salt ‖ input)`, never a bare input. Under the journal-prefix marker an `InputCommitmentCallback` inheritor overrides `_commitmentOffset()` to 64 + the commitment's offset in the program's output (its FIELDS offset is the output offset). `ProofResultStore` stores only `(publicValuesHash, prover, fulfilledAt)` of the whole journal; take the journal from `JobFulfilled` and check it with `matches(jobId, publicValues)`, which takes the whole journal (prefix included), never the output alone.

## 6. Slash / release / cancel

```solidity
// Any keeper, after the effective deadline + PROVER_GRACE (30 min) + TIMESTAMP_SLACK (30 s):
// getJobStatusView(jobId).slashOpensAt
function slashAndReopen(bytes32 jobId) external whenNotPaused nonReentrant;
// The claim leg reverts ClaimBelowFloor below priceFloor (the observed lock's price); returns the price
function slashAndClaim(bytes32 jobId, uint96 priceFloor) external whenNotPaused nonReentrant returns (uint96 price);

// The prover voluntarily gives up its lock (Locked only; the lock's prover only; while job-local
// time < lockDeadline + PROVER_GRACE: one second less than the fulfil window)
function releaseJob(bytes32 jobId) external nonReentrant;

// The live bidder's free refund, only while a governance cause holds (NoGovernanceCause
// otherwise): a live bid is binding
function refundBid(bytes32 jobId) external nonReentrant;

// Caller only
function cancelJob(bytes32 jobId) external nonReentrant;
function cancelJobBatch(bytes32[] calldata jobIds) external nonReentrant;

// Anyone: an Open job stale under governance, or at MAX_REOPEN_COUNT
function cancelStaleJob(bytes32 jobId) external nonReentrant;

// Locked: the job's prover or its authorized claiming operator, once the router pause (or, for
// adapter jobs, a Registry pause) has lasted more than 15 min. Open: the live bidder, only
// once that pause has lasted more than 7 days.
function gracePauseRelease(bytes32 jobId) external nonReentrant;

// Anyone, while the job's adapter is Disabled (graceRelease) or its custom verifier is
// blacklisted (graceReleaseWithDescriptor), for a lock that is not late (not past D + G + 30 s
// at the window start)
function graceRelease(bytes32 jobId) external nonReentrant;
function graceReleaseWithDescriptor(bytes32 jobId, JobDescriptor calldata descriptor) external nonReentrant;
```

**Exit costs at a glance**. D is the effective deadline (`lockDeadline + pauseCredit`), G = `PROVER_GRACE` = 30 min. "Claimable" means a direct `claimJob` works at once; "the lock's share" is what the lock used of the premium budget (§5).

| Exit | When | Cost to the prover or bidder | The job afterwards |
|---|---|---|---|
| `releaseJob` (Locked) | the lock's prover, before D + G (the grace included; D + G − 1 s is the last second, while a fulfil still lands at D + G) | the snapshotted release penalty, `MIN_RELEASE_PENALTY_BPS` (default 5%) of `lockedCollateral`, **all burned** | Open, `reopenCount + 1`; claimable: a claim-won lock at its own price, a bid-won lock at ≤ the winning bid (round marker cleared); the lock's share charged; the releaser is cooled down 1h; exclusivity and the assigned prover cleared (kept on NONE jobs); `lastReopenTimestamp` re-stamped to the release time if it was stamped less than 24h before, else cleared |
| `refundBid`, or the bidder's own `settleBid`, during a governance cause | the live bidder, at any time while the adapter is Disabled or Unregistered (custom: the verifier blacklisted); `NoGovernanceCause` otherwise | none (soft-lock unlocked) | Open; ramp at the best live bid, marker cleared; `BidInvalidated`; 1h cooldown only if taken before `wallBidDeadline` |
| A third party's `settleBid` during a governance cause | anyone, once the wall clock passes `wallBidDeadline` | none (the bidder's soft-lock unlocked) | as above; nobody is cooled down |
| `settleBid` then `releaseJob` (the walk-away from a binding bid) | the winner, after the bid deadline (anyone may settle once the round has ended in job-local time and the router is unpaused: `getJobStatusView(jobId).bidDeadline`, never earlier than `wallBidDeadline`) | the snapshotted penalty: `releasePenaltyBps × max(S × collateralBps / 10,000, minCollateral) / 10,000` (`getJobSnapshots`; 5% by default), burned | as a released bid-won lock |
| `gracePauseRelease` (Locked) | a pause of more than 15 min; the lock was live (not past D + G + 30 s, the slash-open point) at the pause start | none (any lock holder, a sybil's too: residual 16(d)) | Open, no `reopenCount` bump; exclusivity, assigned prover and `lastReopenTimestamp` kept; marker cleared (claimable at ≤ the winning bid); the lock's share charged at the pause start; 1h cooldown |
| `gracePauseRelease` (bid phase) | a pause of **more than 7 days** (`GracePauseDelayNotMet(jobId, pauseStart + 7 days)` before); the round had not ended at the pause start | none (soft-lock unlocked) | bid dropped, ramp at the best live bid, marker cleared; 1h cooldown |
| `graceRelease*` | the adapter Disabled or the verifier blacklisted; the lock was not past D + G + 30 s (the slash-open point) at the window start | none (anyone may call it) | Open, `reopenCount + 1`; exclusivity and the assigned prover cleared (kept on NONE jobs); `lastReopenTimestamp` cleared; marker cleared; the lock's share charged at the window start |
| slash | after D + G + 30 s (`slashOpensAt`) | 100% of `lockedCollateral`: the keeper share to a keeper that is not the caller, the rest **burned** | Open, `reopenCount + 1`, marker cleared, premium budget spent; `lastReopenTimestamp` stamped (the caller's 24h cancel delay); exclusivity and the assigned prover cleared when the slashed prover is the assigned one or none is assigned, kept otherwise and on NONE jobs |

There is no other bidder exit: a live bid is binding (§4). Inside its grace a lock can fulfil (speed bonus 0) through D + G, or `releaseJob` (5%) until D + G − 1 s (the release check is strict: at D + G itself only the fulfil lands, and a lock not released by then is slashed from D + G + 31 s; `test/b221i/LifecycleDocs221i.t.sol`, `test_r6d2_*`). The penalty-free exits end where the slash opens: a lock not past D + G + 30 s when a disable, a blacklist or a pause begins has its free exit; one past it has none and is slashed (during a disable or blacklist at once, after a pause once it lifts). So a lock frozen by such a window has exactly one of the two, and someone can always act: anyone (`graceRelease*` or the slash), or the prover (`gracePauseRelease`) during a pause and a keeper after it. The downtime extension (`extendLocksForDowntime`, §8) leaves a lock that was already past its slash-open point at the outage start slashable, and `topUpDeposit` and `timeRemaining` still end at D. A job settled by `claimAndFulfillAssigned` (§4) holds no lock across a block: none of these exits applies to it.

**Slash.** Slashable once job-local time is past `lockDeadline + PROVER_GRACE + 30 s`, i.e. wall time past the effective deadline + 30 min + 30 s: `getJobStatusView(jobId).slashOpensAt` is the first second (a lower bound while a pause clock runs). A keeper that slashes at `D + 31 s` reverts "Not expired yet". A pause cannot make a live job slashable: the job's union pause clock runs while any window that blocks it is active (the router pause; for adapter jobs the Registry pause and its adapter's disable; for `CUSTOM_VERIFIER` jobs its verifier's blacklist) and for `RESUME_GRACE` = 15 min after the last lift of a blocked stretch, and the job is credited all of it, each second once. An atomic `[unpause, slashAndReopen, pause]` reverts "Not expired yet". A prover that was already late when the pause began stays slashable. The guarantee is in chain time: Hemi block timestamps follow block height, so a lift that lands in a catch-up burst after a sequencer stall can use up the remaining time and the 15-min grace in seconds of real time. Operators lift with the head current (`DEPLOY_RUNBOOK.md`), and provers keep a margin.
- **A late lock stays slashable during a disable or blacklist window.** `slashAndReopen`, `slashAndClaim` and the `cancelJob` auto-slash refuse with `UseGraceRelease` / `UseGraceReleaseWithDescriptor` only while the lock is live: the window freezes job-local time, so a lock that is late during it was late before it began, and is slashed as usual. During the window `slashAndClaim` still reverts as a whole, because its claim leg refuses the disabled adapter (`AdapterDisabled`) or the blacklisted verifier (`BlacklistedVerifier`): keepers use `slashAndReopen`. "Late" here means past `lockDeadline + PROVER_GRACE + 30 s`, and `graceRelease*` uses the same point. A lock inside its grace, or in the 30 s after it (past D, not past `D + G + 30 s`), when the window began is not slashable (`UseGraceRelease*`), but anyone may `graceRelease*` it penalty-free; until the window ends its time is frozen, so otherwise it waits for the re-enable (then fulfils in the rest of its grace), or its prover releases (5%, before D + G). With the free exit at `D + 30 s` beside the grace, such a lock would be stranded for the whole window, and one in `(D + G, D + G + 30 s]` could do nothing at all.
- A `CUSTOM_VERIFIER` job ignores a Registry pause here too: an expired custom lock is slashable during a Registry-only pause (`RegistryPausedUseGracePauseRelease` applies to adapter jobs only).

Slash split: the keeper gets `max(2% × slashedAmount, MIN_KEEPER_REWARD = 0.5 HEMI)`, and **everything else is burned**. Nothing is added to `bonusAmount` (it stays 0): a share funding a "bonus for the next prover" could be collected by the caller's own sybil, on any job whose binding or witness the caller controls.
- When the keeper is the job's caller (`slashAndReopen`, `slashAndClaim` or the `cancelJob` auto-slash), the keeper reward is **burned** too: `JobReopened.keeperReward == 0`. A third-party keeper, including a sybil of the caller and the defaulting prover itself, keeps the keeper share: that is the only **on-chain** value a caller can extract from a failure it engineers. It is not the only value: a caller that reads your proof from a broadcast (a fulfil sent before your lock was mined, a reverted fulfil, or one it kept out of blocks until the grace ended) can take the result and `cancelJob`, or settle through a sybil. NONE jobs are not immune either: the caller's own sybil keeper slashes a held-out lock, and the caller cancels after the 24h delay. The broadcast rule (§3a), the grace and tip escalation (below) are the controls.

`slashAndClaim(jobId, priceFloor)` is **atomic** slash + reclaim by the keeper themselves (they immediately claim the reopened slot). The claim leg carries your `priceFloor` (premium floor 0: the slash spends the budget) and reverts `ClaimBelowFloor` below it, which unwinds the slash; the call returns the price. The whole call reverts if the claim fails (for example on a NONE job, which only its assigned prover may claim, or while the job's adapter is disabled or its verifier blacklisted). On a lock won by bidding the slash clears the round marker, and the claim locks at `P(e*(S))`, a price ≤ the winning bid, never at the round's first-bid ceiling. The new lock's premium is 0 (the slash spent the budget). Send `slashAndClaim` **alone**, never wrapped with a fulfil.

**Late locks**. A fulfil must land by `D + G` (D the effective deadline, G = `PROVER_GRACE` = 30 min; the speed bonus is 0 from D), and a slash opens only after `D + G + 30 s`. A fulfil that lands in `(D + G, D + G + 30 s]` reverts ("Past deadline"), but its journal and seal are now public, and from `D + G + 31 s` anyone eligible can `slashAndClaim` and settle the job with that proof (a job without a binding marker binds the statement, not the prover). For a job with a binding marker the published proof names its late prover (the prefix) or carries its nonce: a rescuer cannot settle with it, needs its own proof, and gets only the keeper share unless it proves within its own lock. So:
- Fulfil as soon as the proof exists, and escalate the tip on the same nonce for every block the fulfil misses (below, "Inclusion delay"). The grace is there for inclusion delay; it is not proving time. Read the end of the window from `getJobStatusView(jobId)` (`lockDeadline` + 30 min) or `jobs(jobId).lockDeadline + getJobExtras(jobId).pauseCredit + 1,800`.
- If you miss `D + G`, **do not broadcast `fulfillJob`**. The rescue takes two steps: send `slashAndClaim(jobId, floor)` **alone** at `slashOpensAt` (or `claimJob(jobId, floor, 0)` alone if a keeper slashed first), wait for its inclusion and re-read `jobs(jobId).prover == you`, and only then fulfil. You recover the keeper share (you are a keeper other than the caller) and the job's price; the premium is 0 (the slash spent the budget). It is not possible during an adapter disable or verifier blacklist (above). A `multicall([slashAndClaim, fulfillJob])` at `D + 31 s` puts the seal in the mempool before the lock exists: anyone can copy it and take both the keeper share and the job.
- **The rescue floor.** `floor` = P(`elapsedAtLock`) of the lock you observed: `AuctionMath.computePrice(minPrice, maxPrice, rampUpPeriod, curveType, elapsedAtLock)` from `jobs(jobId)` read while that lock is live, or the value an `eth_call` of `slashAndClaim(jobId, 0)` returns at a mined block at or after `slashOpensAt`. Compute it **once**, before any slash, and persist it: never re-read `elapsedAtLock` later, because a later bid drop can zero `jobs(jobId).elapsedAtLock` (§6, `cancelStaleJob`). A rescue whose lock changed under it (a keeper slashed the observed lock first, a sybil won a `minPrice` round, that lock expired) reverts `ClaimBelowFloor` instead of locking at the later lock's lower price: `slashAndClaim` is not repriceable only within the observed lock, and the floor is what binds it there.
- The `claimJob(jobId, floor, 0)` fallback can be blocked like any direct claim by a floor bid (`BiddingActive` for ≥ 300 s per round, residual 16(e)): `slashAndClaim` is the only atomic rescue. The reference daemons do no late-lock rescue: use a key no daemon runs on (§3a, one sender per staked key).
- Never `gracePauseRelease` a lock while you hold a valid proof for it: fulfil after the lift.

**Release.** `releaseJob` (the prover of a Locked job only; `JobNotLocked` otherwise) before the effective deadline plus the 30-min grace costs the snapshotted release penalty (`MIN_RELEASE_PENALTY_BPS`, default 5% of `lockedCollateral`). All of it is burned: Staking burns half and sends the other half to the router, which forwards it to the burn destination in the same call (`JobReleased.newBonusAmount` stays 0). The job reopens and the prover is cooled down for 1h on this job (§4).
- **The last second is D + G − 1.** The release needs job-local time `< lockDeadline + PROVER_GRACE`, the fulfil `≤`: at D + G itself a fulfil lands and a release reverts "At or past deadline", and an unreleased lock is slashed from D + G + 31 s (100%, not 5%). The reference daemons release at most 2 blocks before D + G; a hand release sent for the last second is the one exposed.
- **A release clears the reservation.** It clears `exclusivityDuration` and the assigned prover (a NONE job keeps its only locker), so after the assigned prover releases, anyone may claim at once at P(`elapsedAtLock`), inside the original window.
- **A release can move the caller's cancel delay.** `lastReopenTimestamp` (the stamp behind `CancelDelayNotMet` and the delegated-claim cooldown) is stamped by a slash. A direct `releaseJob` landing less than 24h after the stamp **re-stamps it to the release time**; otherwise it clears it. So after a slash at T, a sybil's claim + release at T + 23h makes the caller's `cancelJob` revert `CancelDelayNotMet(jobId, T + 47h)` from T + 24h, and each further claim + release inside the new 24h moves it again, up to `MAX_REOPEN_COUNT`, where the delay is waived: at most nine releases, about 9 days, at the release penalty each (≥ 5 HEMI at the 100 HEMI floor and 5%, about 45 HEMI in all). It buys only delay (the job stays claimable at the ramp price), and less than a hold round (§4, "Hold loops"). Callers and consumer keepers retry on `CancelDelayNotMet`, at its `allowedAfter`. There is no operator's release: `releaseJob` is the lock's prover's own, a PERM_CLAIM operator that claimed for it gets `JobNotLocked`, and the prover's release of a delegated lock stamps nothing (`test/b221i/LifecycleDocs221i.t.sol`, `test_r6d1_*`, `test_r6g1_*`).
- A lock won by bidding reopens at a price ≤ the winning bid. Its round marker is cleared, so the job is directly claimable there at once.
- The lock's share of the premium budget is charged at the release (`speedPremium` minus what the lock could still have earned): a zero-hold claim-won release charges nothing, a release in the grace spends the whole budget.
- Release only for a defect of your proof (§5, "Which reverts mean what": `JournalMismatch`, `JournalPrefixMismatch`, `ProofNonceMismatch`, `JournalTooLarge`, `InvalidDescriptorHash`, a `VerifierCallFailed` with no governance cause), never because of a pause, disable or blacklist, and never on an RPC error without revert data. A release is itself a transaction that can be held out of blocks: send it before `D + G` with the same tip escalation as a fulfil.
- **Price a release before you send it.** `releaseJob` uses about 225,000 gas (224,192 measured with every touched account cold, before refunds; §9), and it saves 95% of `lockedCollateral`. Release only if 225,000 × (base fee + your tip) × HEMI per ETH is below 0.95 × `lockedCollateral`. A release that replaces a pooled transaction at its nonce needs at least 1.1 × both of its fees. After a ladder has climbed to the 100-gwei default ceiling that is about 0.0245 ETH (1,222 HEMI at 50,000 HEMI per ETH) against 95 HEMI saved on a 100-HEMI lock: leave such a lock. A release at 1.1 × the pending fees, sent without pricing it, loses 557-1,127 HEMI per 100-HEMI lock at the default ceiling. The reference daemons' `PENDING-UNMINED` page prints the replacement's fees, its cost and its saving.

**Binding bids.** The current bidder of an Open competitive job has no walk-away: there is no forfeit (a 100% burn before the bid deadline), and neither its event nor Staking's burn hook exists. `releaseJob` reverts `JobNotLocked` on an Open job. The bid ends in a lock (`settleBid`, then fulfil or `releaseJob` at the snapshotted penalty, `getJobSnapshots`) or an outbid, unless:
- a governance cause holds (the adapter Disabled or Unregistered; for a `CUSTOM_VERIFIER` job the verifier blacklisted; a codeless verifier does not count): `refundBid(jobId)` or the bidder's own `settleBid` refunds the soft-lock for free at any time (`BidInvalidated(jobId, bidder)`), with the 1h cooldown only before `wallBidDeadline`; others get the same refund through `settleBid` from `wallBidDeadline`, uncooled. `refundBid` reverts `NoGovernanceCause(jobId)` otherwise;
- a router or Registry pause has run longer than 7 days: the bid-phase `gracePauseRelease` (below).
Either way the ramp resumes at the best live bid with the round marker cleared (§4). Residuals: 16(c) (the lift race: when a cause or a pause over 7 d ends, a live leader that dropped for free leaves the job to a sybil at no more than its bid, and pending honest underbids revert `JobNotOpen`; counter: send a first bid in the lift block), 16(h) (bound through any pause under 7 d), 16(j) (a third party's governance-cause refund of a live leader once the wall clock passes `wallBidDeadline` under a cause; pause credit earned after the last bid does not move `wallBidDeadline`).

**Cancel.**
- `cancelJob` on an Open job refunds `depositedAmount` (plus the cycle commit collateral) to the caller. The job's `bonusAmount` is prover-derived, so it is **burned**, never refunded: `JobCancelled(jobId, caller, refundAmount, bonusBurned)` (0: nothing accrues to it). The same holds for `cancelJobBatch` and `cancelStaleJob`.
- On a Locked job past its effective deadline + 30 min + 30 s (`slashOpensAt`; the prover's grace included), `cancelJob` first auto-slashes with the caller as keeper (keeper reward burned) and reopens the job. The caller then cancels in a follow-up call, after `MIN_REOPEN_CANCEL_DELAY = 24h` (24h after the slash, or after a later direct release that re-stamped it: "Release" above; retry on `CancelDelayNotMet(jobId, allowedAfter)`); when the slash brings `reopenCount` to `MAX_REOPEN_COUNT`, the same call cancels.
- Before that point `cancelJob` reverts `JobNotExpired`. This includes a lock whose adapter was disabled (or verifier blacklisted) before its effective deadline: the disable stops the job's clock, so use `graceRelease` / `graceReleaseWithDescriptor`. A lock that was already late when the adapter was disabled is auto-slashed like any late lock. `CancelSlashFailed` remains for a late lock whose auto-slash a router pause, or for an adapter job a Registry pause, refuses.
- A job with a live bid reverts `BidsActive`.
- **`cancelStaleJob(jobId)`** (anyone; refunds the caller):
  - an Open job at `MAX_REOPEN_COUNT` can never be locked again: anyone may cancel it **at once**;
  - otherwise the job's adapter must be Disabled (or its custom verifier blacklisted) for more than `STALE_JOB_CANCEL_DELAY` = 7 days, measured from the start of the live window (the start the router's union clock records for the key, `getKeyClock(key).a`, key = the psId, or `bytes32(uint256(uint160(verifier)))` for a custom verifier), **and** more than 7 days must have passed since the job was last submitted or reopened ("Stale delay not met" before). The reopen time is `rampUpStart + elapsedAtLock` from `jobs(jobId)` (a submit, and every Locked → Open: release, slash, `graceRelease*`, `gracePauseRelease`), or `lastReopenTimestamp` when later (a slash stamps it and a direct release inside its 24h re-stamps it; there is no operator's release, "Release" above). Counting only `rampUpStart` would start the 7 days `elapsedAtLock` before the reopen after a direct release or a grace exit. A bid drop (a governance-cause refund, `gracePauseRelease` of a bid) moves `rampUpStart` forward (by at least the frozen round; to the best bid's ramp point), which does not count as age. Such a forward shift also zeroes `elapsedAtLock`, so the base point is at or before the wall time of the drop, and for a governance-cause drop at or before the key clock's anchor `since`: the stale cancel opens at `since + 7 days + 1` (a stale `elapsedAtLock` would date the base point into the future without bound). A brief disable does not expose week-old jobs.
- Consumer contracts should keep their own cancel path (`HemiProveConsumer._cancelProof`).

**gracePauseRelease.** A penalty-free exit while the router is paused (or, except for `CUSTOM_VERIFIER` jobs, the Registry), available once the pause has lasted more than `MIN_GRACE_PAUSE_DELAY` = 15 min (`GracePauseDelayNotMet` before). The countdown starts at the earlier pause start when both are paused. A `CUSTOM_VERIFIER` job under a Registry-only pause reverts "Not paused"; a terminal job, or an Open job without a live bid, reverts `JobNotLocked`.
- Locked job: only the job's prover, or its `claimingOperator` while still authorized, may call it (`NotJobProver` otherwise). The lock must still have been live at the pause start (`JobExpiredBeforePause` for a prover that was already late: past `lockDeadline + PROVER_GRACE + 30 s` in job-local time, the slash-open point, so a lock inside its grace may exit). The job reopens with no `reopenCount` bump and keeps its exclusivity, assigned prover and `lastReopenTimestamp`; the prover gets the 1h release cooldown. A pulse of short pauses re-anchors the 15-min countdown at each new pause start but cannot cause a slash.
- **Overlapping windows.** Job-local time is frozen from the start of the job's blocked stretch, which is at or before the pause start, so the liveness test reads job-local time at the pause start, exactly, whatever other windows overlap: a prover that was late (past the slash-open point) before the pause reverts `JobExpiredBeforePause`. The same value sets the premium cap and the bid-phase check below.
- A lock won by bidding reopens at ≤ the winning bid with its round marker cleared (directly claimable); the lock's share of the premium budget is charged at the pause start.
- Open job with a live bid: only the current bidder may call it (`NotJobProver` otherwise), and only once the pause has run longer than `MIN_BID_PAUSE_EXIT_DELAY` = 7 days: before that it reverts `GracePauseDelayNotMet(jobId, pauseStart + 7 days)` (inside the first 15 min the shared check reports `pauseStart + 15 min`; it reverts at exactly `pauseStart + 7 days` and succeeds one second later). `pauseStart` re-anchors at each new pause, so pulses never accumulate. A routine pause (the stall procedure, a hot pauser key, the 24h GT unpause op) therefore only freezes a live round: at the lift it resumes with its remaining job-local time, and pending underbids land. The bid is dropped and its soft-lock unlocked (no `reopenCount` bump, no `lastReopenTimestamp` stamp), the Dutch clock resumes at the best live bid, the round marker is cleared (the job is directly claimable at ≤ that bid), and the bidder gets the 1h cooldown. The caller may `cancelJob` at once (subject only to the 24h delay of a live `lastReopenTimestamp` stamp: a slash's, or a release's that re-stamped it, "Release" above). If the round had already ended at the pause start (job-local `bidDeadline` reached), it reverts `BidDeadlinePassed(jobId)`: the winner settles after the lift, and the Locked rules apply.
- Emits `GracePauseReleased(jobId, prover, releasedCollateral, operator)` (operator 0 for the bid-phase exit).
- **A router pause is not loss-free** (residual 16(d)). After 15 min of any router pause (a hot pauser key's and the stall broadcaster's included), or of a Registry pause for adapter jobs, every lock holder has this penalty-free Locked exit: a free reset of any lock (a sybil's too) to P(`elapsedAtLock`), which only delays floored claims (hence tolerance 0, §4), and a free Dutch premium strip of `speedPremium × h / fulfillmentTimeout`, charged at the pause start and refunded to the caller (pending claims at the exact premium floor revert and are re-quoted).

**graceRelease / graceReleaseWithDescriptor**. While the job's adapter is Disabled (or its custom verifier blacklisted), anyone may release a Locked job penalty-free, so a caller whose prover is gone is not stuck. The lock must not be past `lockDeadline + PROVER_GRACE + 30 s` in job-local time at the window start (the slash-open point, the prover grace included; `JobExpiredBeforePause` otherwise: such a lock is slashed instead, during the window). The prover keeps its stake but loses its lock: `reopenCount + 1`, exclusivity and the assigned prover cleared (NONE jobs keep it), the round marker cleared (a bid-won lock reopens at ≤ the winning bid), the lock's share of the premium budget charged at the window start. A third party can use it on a **live** lock: watch `AdapterDisabledEvent` and `VerifierBlacklisted` for the proof systems you lock on.

**Verifier swaps**. `reactivateAdapter(psId, newAdapter)` followed 48h later by `executePendingReactivation(psId)` installs a new verifier for every in-flight lock of that psId and puts the adapter back to the status it had: Active, or Deprecated if it was deprecated before the disable (its successor kept; only the owner's `undeprecateAdapter` makes it Active again, `AdapterUndeprecated`). The instant re-enable, `reactivateAdapter(psId, 0)`, does the same without a swap. `graceRelease` then reverts "Adapter not disabled", and a lock has its remaining time plus 15 min. If the new verifier rejects proofs made for the old one, a locked prover can only release (5%) or be slashed. Watch `VerifierSwitchProposed`: the adapter stays Disabled during the 48h, so nothing of that psId can be fulfilled, and a live lock whose proof will not verify under the new adapter should `graceRelease` (penalty-free) before the swap executes. The same goes for a live bid on that psId: `refundBid` is free while the adapter is Disabled, but after `executePendingReactivation` it reverts `NoGovernanceCause` and the bid binds (walk-away: settle, then `releaseJob` at the snapshotted penalty). Governance uses in-place swaps only for proof-compatible hotfixes; a semantic upgrade gets a new psId, and the old one is deprecated (`deprecateAdapter`), which keeps in-flight locks provable under the old verifier.

**Inclusion delay and tip escalation**. Hemi's blocks are cheap (30M gas, a base fee of a few hundred wei that rises only about 2% per full block) and ordered by tip, so an observer can keep a transaction that pays a fixed tip out of blocks for a while by filling them at a slightly higher tip. A fixed margin ("2 blocks before the deadline") does not protect against that. What does:
- **Fulfil as soon as the proof exists**, not near the deadline.
- **Escalate the tip AND `maxFeePerGas` on the same nonce**. For every block your fulfil (or release) misses while it is pooled, re-sign it at the same nonce with both fields at least 10% higher (geth's replacement rule; the reference daemons use 12.5%, `TIP_BUMP_PERMILLE` 1125), up to the effective ceiling `min(TIP_CEILING_WEI, balance / gasLimit, the RPC's --rpc.txfeecap / gasLimit)`: a signature above the balance or the RPC's fee cap (op-geth's default 1 ETH) is refused, not pooled. **Set the ceiling from what the lock is worth:** `TIP_CEILING_WEI` ≤ (price + `lockedCollateral`) × ETH per HEMI / the fulfil's gas used (about 643,000 for a real Groth16 fulfil, measured cold; §9). For 15-50 HEMI jobs (100 HEMI of collateral) at 50,000 HEMI per ETH that is about 3.6-4.7 gwei. The ceiling is key-wide, so size it for the cheapest lock the key takes. The daemons' 100-gwei default prices an attacker who pays to hold you out. Under a hold that no tip beats (the DA filter, an endpoint that never forwards), a ladder that climbs to it pays about 0.06 ETH for a fulfil that lands when the hold ends, and makes a same-nonce release cost more than it saves ("Release" above). Start at the larger of a sane tip (the daemons: twice `eth_maxPriorityFeePerGas`, at least 0.01 gwei) and the **hold-out floor** `HOLDOUT_FLOOR_WEI / (blocks left × (block gas − gasLimit))`, re-evaluated every block (default 1 ETH: 0.09 gwei with 450 blocks left, 0.27 gwei at 150, 20.5 gwei at 2, for a 5.6M-gas fulfil), so that even a late first send is expensive to hold out. A derived start above the ceiling is clamped to ceiling / 1.125.
- **Keep retrying AND keep re-broadcasting** until the job is Fulfilled or until 2 blocks before `D + G`; release only before that, and only for a defect of the proof (§5). Re-publish the live signature every block, also at the ceiling ("already known" means it is pooled); while that fails, also re-publish the last accepted signature. A failed publish while nothing of yours is pooled is not a missed block (no bump); count at most one step per 12 s of wall time (a catch-up burst after a stall is one step). On a refusal fall back to the last accepted signature or step down. Never let the wall clock end an accepted send: a halted chain keeps it pooled for the catch-up. (Stopping once a bump falls under 10% is not safe: about 16 min of failed writes on a live chain can leave no fulfil in any pool.) One sender per key (§3a). Publish to two endpoints, one of them self-hosted, and prefer a private or sequencer-direct submission path where one exists (the reference daemons publish to one endpoint).
- **What holding a fulfil out costs**. Holding an escalating fulfil out of every block costs `Σ_k (30M − gasLimit) × min(C_eff, max(floor_k, t0 × 1.125^k))` over the blocks k it is held, with `C_eff = min(TIP_CEILING_WEI, balance / gasLimit, txfeecap / gasLimit)` and `floor_k` the hold-out floor: about 191 ETH for an on-time fulfil held through the whole grace at the daemon defaults (2.38 ETH per block at the 97.70 gwei top of the ladder), and at least `HOLDOUT_FLOOR_WEI` whenever the first acceptance happens (a late send, a restart). A balance- or fee-cap-capped ladder lowers it (about 4.96 ETH at a 0.01 ETH balance): fund the key for the escalation (each pending fulfil's gas limit × the ceiling you set), not only for the gas. At a ceiling sized from the lock (about 4 gwei) the top of the ladder costs a holder about 0.1 ETH per block, still far above a lock's worth. Hemi's sequencer also caps each block at 130,000 estimated DA bytes (`DEPLOY_RUNBOOK.md`, threat model, residual 15 (the DA throttle)), so an attacker may instead fill a block's DA budget with about 6.1M gas of incompressible calldata. That fill costs about `6.1M × the tip it must beat` plus its L1 data fee, about 0.0006 ETH per block at a 0.3 gwei L1 base fee. That fee is at the unthrottled cap only: Hemi's L1 fee has no surge price, so as the throttle shrinks the block cap a block costs the filler about 3.6e-6 ETH. The cheaper of the two fills sets your cost: divide the gas term by about 5, or by about 10 in the worst case, once your tip is above about 0.026 gwei. Under a batcher backlog the per-transaction cap can fall below any fulfil's size, and then no tip helps ("The DA throttle", next).
- **The DA throttle** (`DEPLOY_RUNBOOK.md`, threat model, residual 15 (the DA throttle)). Hemi's sequencer leaves out of its blocks every transaction whose estimated DA size (FastLZ of the signed transaction: `l1GasUsed / 16` in its receipt) is above the batcher's per-transaction cap, **whatever it tips**, and every later nonce of the same sender with it. The pool accepts such a fulfil and never mines it. There is no cap while the batcher's unposted backlog is under 3.2 MB; above that the cap is 20,000 estimated bytes, falling to 150 at 12.8 MB. A filler can build that backlog during a batcher posting stall (standard fulfils, 455-583 estimated bytes, are filtered after 34-41 min of one) and, against large fulfils, with no stall at all (above about 8.5-17 KB of estimated DA).
  - **Keep proof-carrying fulfils small.** Estimate the fulfil's DA size before you claim (`GasPriceOracle.getL1GasUsed(signedTx) / 16`, about 57 high for the signature) and skip a job whose fulfil would be large. A journal or `inputData` of about 23 KB or more is above 20,000, so it is filtered from the first throttled block; a 10-proof batch with 1-KB journals is about 12,700. When `inputData` is large, send `fulfillJobHashed`: it leaves `inputData` out of the calldata (about 57 KB less for a 64-KB input; for a small input it is slightly larger, 473 against 455). Requesters: a journal or input above about 8-20 KB loses inclusion under any throttle.
  - **Tip on short deadlines.** Outside the throttle the priority fee is what makes stuffing your fulfil out of blocks costly (above, "What holding a fulfil out costs"): on a short deadline, start with a real tip, not the minimum. Under the filter no tip helps.
  - **What protects you** is the router pause that the guardian's pauser keys send once the backlog reaches about 2.75 MB (`DEPLOY_RUNBOOK.md`, "L2 liveness and the DA throttle"). It credits your lock and stops every slash, and after the lift you have your remaining time plus 15 min. A lock already inside its grace when its fulfil was filtered keeps only what was left of the grace.
  - **If your fulfil is accepted but not mined** while the head advances, or the safe-head lag (`ts(latest) − ts(safe)`) exceeds 600 s, suspect the throttle; the reference daemons page on both (`PAGE: PENDING-UNMINED`, `PAGE: SAFE-LAG`; §3a). Check the router's `paused()` first: a paused router credits your lock, so keep it. If the router stays unpaused and the fulfil stays out as `D + PROVER_GRACE` nears, `releaseJob` (100 bytes, 5%) still lands where the slash (100%) would, but only as a replacement of the pooled fulfil at the same nonce: a release at the next nonce waits behind the filtered fulfil. Price it first ("Release" above; §3a has the steps and the command): once the ladder has climbed under the filter, 1.1 × its fees can cost more than the 95% of the collateral the release saves, and then you leave the lock. If a second endpoint does not know the pooled transaction and `SAFE-LAG` has not paged, the hold is your own endpoint (it accepts and never forwards): send the release through the second endpoint, at an ordinary fee.
- **Release rule by job type**. For a `CUSTOM_VERIFIER` job a `VerifierCallFailed` is the verifier's own rejection whatever `Registry.paused()` says (a Registry pause neither blocks nor credits a custom job): release before `D + G` unless the verifier is blacklisted. An adapter that reads Unregistered is no cause either (no credit, no grace exit): release.

What the grace does not remove (threat-model residuals in `DEPLOY_RUNBOOK.md`):
- **Premium stripping by inclusion delay.** The speed bonus is 0 from the deadline D on, inside the grace too. Whoever keeps your fulfil out of blocks until D (an observer, or the job's caller) moves the premium back to the caller's refund. Tip escalation is the control.
- **Underbid censorship.** An incumbent bidder can try to keep underbids out of blocks until the bid deadline (§4). Bid early and escalate.
- **Late locks after the grace.** A fulfil kept out past `D + G` reverts and publishes its proof (above, "Late locks").
- **Free exits during a router pause** (residual 16(d), "gracePauseRelease" above): after 15 min every lock holder can reset its lock for free, and a held Dutch premium can be stripped for free (refunded to the caller).
- **The DA throttle** ("The DA throttle" above): under a batcher backlog your fulfil can be left out of blocks whatever it tips; the guardian's router pause is the defence.

    returns (uint256 releasePenaltyBps, uint256 minCollateral, uint256 collateralBps);

- `jobs(jobId)` returns 27 fields. Its `lockDeadline` is raw, as of the job's last base point (submit, lock or reopen). `getJobExtras` returns what it does not: `pauseCredit` (seconds credited since the last base point, 0 for terminal jobs; effective deadline = `lockDeadline + pauseCredit`; job-local time = `block.timestamp - pauseCredit`), `pauseBase` and `assignedOnly` (the NONE flag). The field `premiumUsedPpm` is read through `getPremiumCap(jobId)` = `speedPremium × (1,000,000 − premiumUsedPpm) / 1,000,000`, the premium budget left (`premiumUsedPpm` is cumulative; §5).
- `getJobExtras` does not know that a fulfil is in progress: read from inside a callback, it still reports pause credit for a job that is about to be Fulfilled. `pauseCredit` converts `lockDeadline` and `bidDeadline` only (§4).
- `getJobStatusView` reports effective values for Open and Locked jobs: `lockDeadline` and `bidDeadline` are wall-clock-effective (pause credit added; 0 stays 0), `timeRemaining` is measured in job-local time, and `auctionTimeElapsed` / `currentAuctionPrice` follow the paused and bid-frozen ramp. Terminal jobs, and a job mid-settlement, report raw values. `getCurrentPrice(jobId)` follows the same paused, bid-frozen ramp. The trailing `slashOpensAt` is, for a Locked job, `lockDeadline + pauseCredit + PROVER_GRACE + 30 + 1`: the first wall-clock second a slash (or `cancelJob`'s auto-slash) can land, a lower bound while a pause clock runs; 0 for any other status. `lockDeadline` and `timeRemaining` still end at the deadline (the speed bonus ends there); the prover's fulfil runs on through `lockDeadline + 1,800 s` and its release until one second before (`slashOpensAt − 32` is the last release second, `slashOpensAt − 31` the last fulfil second), and the free exits to the slash-open point, `lockDeadline + 1,830 s` at the window start. `getBidState(jobId)` has a 7th member, `wallBidDeadline` (§4); the 6-value `bidStates(jobId)` getter does not return it. `JobStatusView` has 22 members, `settledPrice` directly after `bonusAmount` (there is no `totalProverReward`: read `settledPrice`, `getPremiumCap` and `getJobSnapshots`).
- `getJobSnapshots(jobId)` returns the job's submit-time release penalty (bps), collateral floor and effective collateral bps, decoded exactly as the release, claim, bid and settle paths read them (each from its +1-offset snapshot, or the live value for a pre-snapshot job). Use it to price a bid and its walk-away (`releasePenaltyBps × max(S × collateralBps / 10,000, minCollateral) / 10,000`, §4) and to monitor residual costs; it is not a floor tolerance (floors use tolerance 0).
- **The union pause clock.** A job's clock C counts the seconds of the union of the windows that block it: the router pause, the Registry pause (adapter jobs), its adapter's Disabled windows (adapter jobs) or its custom verifier's blacklist windows (`CUSTOM_VERIFIER` jobs), each extended by `RESUME_GRACE` (15 min) after its lift. A second inside several overlapping windows is credited once (overlapping windows are never summed); overlapping or touching windows merge into one blocked stretch, so a joint or staggered lift, or a key lift in the same block as a pause lift, leaves one grace after the last lift; and job-local time `now − (C − pauseBase)` never runs backwards, so `timeRemaining` never exceeds `fulfillmentTimeout`, and a lift never lowers a Dutch price, reopens a closed bid round or restores a lapsed exclusivity window. `clockOf(psId, address(0))` is an adapter job's C, `clockOf(CUSTOM_VERIFIER, verifier)` a custom-verifier job's; a job's credit since its last base point is `clockOf(...) − pauseBase` = `getJobExtras(jobId).pauseCredit`. While a window is active (or within its `RESUME_GRACE`), every effective deadline keeps moving, so it is a lower bound. The router holds the union clock; the Registry keeps none: it reports each of its transitions (pause, unpause, a disable, a re-enable, a blacklist, an unblacklist) to the router in the same transaction (`syncRegistryWindow`), and the router re-reads the condition. `getUnionClock`, `getKeyClock(key)` (key = the psId, or `bytes32(uint256(uint160(verifier)))`) and `getKeyEpochCut` expose the state, reconstructible from the events of §8.
- The Registry exposes `paused()`, `pauseTimestamp()` (the start of the live pause, or 0) and `clockSink()` (the router it reports to); it has no clock views.
- `getJobStatusView(jobId).proofSystemId` (and `verifierTrust`) is the job's in every state: the verified result's for a Fulfilled job, the submit-time psId otherwise. A cancelled `CUSTOM_VERIFIER` job reports `CUSTOM_VERIFIER` and `UserSubmitted`, and `jobProofSystems(jobId)` keeps a cancelled job's psId.
- `previewSpeedBonus(jobId)`: the speed bonus a fulfil included at this block's timestamp pays. For a Locked job it is exactly the `JobFulfilled.speedBonus` of a fulfil in this block (0 from the effective deadline on, never above `getPremiumCap`); for an Open job it is the bonus of a lock taken and fulfilled in one block (`claimAndFulfillAssigned`), the whole budget left, `getPremiumCap(jobId)`; 0 for an unknown or terminal job and for a job without a premium. Read it at a mined block, like the claim floors.
- `totalPaidToProvers()`: everything the router has paid provers for proofs since deploy, `Σ JobFulfilled.proverPayout` (price and speed bonus net of the protocol fee; an IOU credit counts when credited) plus `Σ CycleCollateralSettled.toProver` (a prover's share of a cycle collateral, at the fulfil or at the committee's resolution). Keeper shares (the slash keeper reward, the cycle resolver bounty), refunds, collateral unlocks and bid soft-lock returns are not counted.

`JobStatusView` is the recommended read for UIs — it unpacks the fields you actually need without the 27-tuple destructure.

The nine struct getters (`jobs`, `bidStates`, `bidConfigs`, `cycleConfigs`, `presets`, `priceHistories`, `operatorAuthorizations`, `pendingCycleSettlements`, `auditRecords`) answer at the router address; they are routed to the Core facet.

## 8. Events for indexers

Priority events (fire on happy path):
- `JobSubmitted(jobId, proofSystemId, caller, programId, descriptorHash, depositedAmount, minPrice, maxPrice, fulfillmentTimeout, trust)`
- `FeeRateSnapshotted(jobId, feeRateBps)` — same tx as JobSubmitted
- `JobClaimed(jobId, prover, operator, settledPrice, bonusAmount, lockDeadline)` — `lockDeadline` raw at lock, and a lower bound of the effective deadline (§4); `settledPrice ≥` the claim's `priceFloor` (check it: the canary, §4)
- `JobFulfilled(jobId, prover, caller, settledPrice, bonusAmount, proverPayout, callerRefund, protocolFee, speedBonus, actualCycles, publicValues)` — `protocolFee` includes the speed-bonus share and excludes the committee diversion (§5); `speedBonus` is `max(0, u − used)`, at most `getPremiumCap` (§5)
- `JobClaimed` and `JobFulfilled` in **one transaction** (same transaction hash) are a `claimAndFulfillAssigned` (§4): the job was never Locked across a block. Pair the two events as for a claim and a later fulfil; no other event marks the path
- `PriceUpdated(proofSystemId, programId, settledPrice, newEwma, sampleCount)` — advisory

Fault events:
- `JobReopened(jobId, slashedProver, slashCaller, slashedAmount, keeperReward, burnedAmount, newBonusAmount, reopenCount, newRampUpStart, elapsedAtLock, operator)` — `keeperReward == 0` when the caller slashed; `burnedAmount` includes the bonus share (nothing goes to `newBonusAmount`); `elapsedAtLock` of a bid-won lock is `e*(S)`
- `JobReleased(jobId, prover, penaltyAmount, newBonusAmount, timeHeld, operator)` — the whole penalty is burned; `timeHeld` is the wall-clock time from the lock to the release (pauses inside the hold count; a downtime extension does not shorten it); `operator` is always `address(0)` (only the prover releases)
- `bonusAmount` / `newBonusAmount` / `bonusBurned` are 0 for every job of this deploy (the fields stay)
- `JobCancelled(jobId, caller, refundAmount, bonusBurned)` — the earlier form with `bool bonusIncluded` has another topic0
- An earlier implementation's forfeit event is **removed** with the forfeit (binding bids): no current contract emits it. Drop its handler.
- `BidInvalidated(jobId, bidder)` — a governance-cause refund: `settleBid` and `refundBid` (topic0 `0x66580e28…`)
- `GracePauseReleased(jobId, prover, releasedCollateral, operator)` — also the bid-phase exit (operator 0)
- `CallbackFailed(jobId, callbackContract, reason)` — observational; emitted if and only if the callback address has no code (not called; empty `reason`), the call reverted (out of gas included), or it returned a zero first word (§5). `JobFulfilled` is the settlement signal, never `CallbackFailed`

Pause clocks:
- Router `PauseClockSet(uint40 anchor, uint40 total)` on every router pause and unpause (same signature as the BatchCycleCommittee's event: filter by address).
- Router `UnionClockSet(uint40 anchor, uint40 total, bool registryPaused)` at every router or Registry pause and unpause (the union clock's "router or Registry paused" base); `KeyClockSet(bytes32 indexed key, bool active, uint40 a, uint40 t, uint40 c, uint24 epoch, uint40 prevEnd)` when an adapter's Disabled window or a verifier's blacklist window starts or ends (key = the psId, or `bytes32(uint256(uint160(verifier)))`; keys are enumerable from these logs); `FirstPauseMarked(uint40 firstPauseA, uint40 firstPauseR)` and `KeyEpochCut(bool routerBase, uint24 epoch, uint40 firstPause)` for the union clock's bookkeeping. Every field of `getUnionClock` and `getKeyClock` is reconstructible from these and `PauseClockSet`. The Registry emits no clock event (it keeps no clock).
- **The downtime extension** (AuxGov, `extendLocksForDowntime(jobIds, expectedProvers, expectedLockDeadlines, downtimeStart, downtimeEnd, reason)`, owner or the GT guardian's emergency selector, **only while the router is paused**). It credits an outage the pause clock did not see (a sequencer stall before the router pause landed) to the Locked jobs that lived through it; the recovery order is pause the router, extend while it stays paused, lift last. The attested window `[downtimeStart, downtimeEnd)` must end at or before the router pause start and span at most 24 h (`InvalidDowntimeWindow(start, end, pauseStart)`); at most 10 ids. Per id: `DeadlineExtended(bytes32 indexed jobId, uint40 extension, uint40 lockDeadline)` (the new raw deadline), or `DeadlineExtensionSkipped(bytes32 indexed jobId, uint8 reason)` with reason 1 not Locked, 2 the lock changed (its prover or raw `lockDeadline` differs from the batch's expected values: another lock, an earlier extension, the same id earlier in the batch), 3 already extended (once per lock; a reopen resets it), 4 locked after the window, 5 the window touches a window the job's clock already credits, 6 the lock was past its slash-open point at the window start. Once per call: `DowntimeCredited(uint40 downtimeStart, uint40 downtimeEnd, uint256 applied, string reason)`. An applied lock is extended by exactly `downtimeEnd − max(downtimeStart, lock start)` and stands where it stood at the window start: the same time to its deadline, the same prover grace, the same speed-bonus fraction, less any time between `downtimeEnd` and the router pause start (the operators' tooling ends the window at the pause start). A lock is extended once: a second outage in the same lock's life gets no extension (reason 3). Open jobs get no extension (their ramp, bid rounds and exclusivity advanced through the stall; nothing is slashed for it). `getJobStatusView` and `getJobExtras` include the extension at once.

Registry: `AdapterReactivated` when a re-enable executes (the adapter goes back to the status it had: Active, or Deprecated if it was deprecated before its disable, §6 "Verifier swaps"); `AdapterUndeprecated(bytes32 indexed proofSystemId)` when the owner returns a Deprecated adapter to Active (`undeprecateAdapter`: new submits of that psId are accepted again).

Staking: `UnstakeCancelled(prover, amount)` reports the amount counted back as active stake, which can be less than the pending amount (the rest stays pending). `StakeReduced(address indexed prover, uint128 amount, uint128 newTotal, uint128 newPendingUnstake, bool slashed)` after every slash (`slashed` true) and every non-zero release penalty: per prover, `totalStaked = Σ Staked.amount − Σ Withdrawn.amount − Σ StakeReduced.amount`, with `newTotal` as a checkpoint, and `newPendingUnstake` is the pending unstake after the reduction (lower only when the reduction capped it).

All router events are on the **router address**, not the facets. Filter by `HEMIPROVE`.

| Op | Median gas | Max gas |
|---|---:|---:|

| `claimJob` | 112k | 115k |
| `fulfillJob` (mock verifier) | ~365k | ~560k |

| `fulfillJob` (`SP1_GROTH16_V1` / `SP1_PLONK_V1`, FULL-bound, real proof) | 578,000 / 639,000 (`test/integration/SP1PlonkProofs.t.sol`) | as above |
| `fulfillJob` (`OPENVM_HALO2_V1`, real Halo2 proof) | ~653k execution (772,282 in a local receipt) | ~4.6M for a malformed proof (the whole verifier budget, §3a step 9) |

FIELDS adds gas linear in the pinned bytes (~4k for a one-byte pin; the worst case is 8 slots of 32,768 bytes, §3a); a binding marker's check adds little (a 64-byte compare, or one keccak for the nonce). The union pause clock is read from the router's own storage (no Registry call), only where a deadline or the ramp needs it. The verifier calls alone: SP1 `verifyProof` about 258k, OpenVM about 300k.

**Fulfill gas limit**. Before it calls the verifier, the router checks the gas left (`InsufficientGasForFullSettlement()` otherwise), even though a fulfill uses far less. At that point it wants `2 × CUSTOM_VERIFIER_GAS_LIMIT + callbackGasLimit + SETTLEMENT_GAS_BUFFER + 100k` = **4,600,000 + `callbackGasLimit`** for an adapter job, or **2,600,000 + `callbackGasLimit`** for a `CUSTOM_VERIFIER` job (`callbackGasLimit` from the job's config; 0 means the 200,000 default). Everything spent before the check comes on top, so size the transaction's gas limit as:

```
gasLimit >= 4,600,000 (adapter job) or 2,600,000 (CUSTOM_VERIFIER job)
          + callbackGasLimit
          + ~250,000                       // descriptor hash, journal cap, reads before the check
          + calldata intrinsic gas          // 21,000 + 16 per non-zero byte + 4 per zero byte
          + the FIELDS cost of the binding  // §3a; it runs before the check
          + ~8 gas per journal byte         // the JobFulfilled log, plus the callback copy
          + a margin (job-prover.sh uses 500,000)
```

For an adapter job with the default callback and about 1 KB of calldata this is about 5.6M; 5,000,000 is too low for larger callbacks or calldata (the measured minimum is 4.97M at the default callback and 5.28M at a 500k callback, before calldata).
- **`claimAndFulfillAssigned`**: the same formula over its own calldata, plus the claim leg, which runs before the fulfil preflight in the same transaction (a cold claim leg measures about 95,000; `script/lib/FulfillGas.sol` `forClaimAndFulfillAssigned` adds 300,000, `CLAIM_LEG_GAS`). `eth_estimateGas` finds it too.
- `eth_estimateGas` (cast send, ethers, viem) binary-searches the limit and finds a working one. Prefer it, or an explicit limit from the formula.
- **Never** size a fulfil with `forge script --gas-estimate-multiplier`: it multiplies the simulated gas **used**, which is far below the gas the check wants, so the result can land on either side of it. Send the fulfil with an explicit limit from the formula (`cast send --gas-limit`, an SDK `gas` field) or with `eth_estimateGas`.
- **`forge script` always sizes from the simulated gas**, flag or no flag: every broadcast transaction gets the gas used in the local simulation × 1.3 (`gas_estimate_multiplier` defaults to 130). A script fulfil therefore reverts `InsufficientGasForFullSettlement` on-chain after its claim has landed, and the lock is slashed, while the script's own `require`s, which check the simulation and not the receipt, pass. Give every script fulfil an explicit `{gas: N}` call option: `script/lib/FulfillGas.sol` computes N by the formula above (4,600,000 + `callbackGasLimit` + 250,000 + 16 per calldata byte + 8 per journal byte + 500,000) and sends `fulfillJob{gas: N}`. On a live chain, claim and fulfil are **two separate runs** (the broadcast rule, §3a: `forge script --broadcast` simulates a whole run first and then sends its transactions without waiting for receipts unless `--slow`, and every check in the run sees only the simulation): run the claim, wait for its receipt, then run the fulfil, which `FulfillGas.requireOwnLock` refuses unless the chain shows the job Locked by the broadcaster. `script/TestFulfill.s.sol` (`--sig 'claim()'`, then `run()`) and `script/LiveE2E.s.sol` follow it. Both build their fixture descriptors for the broadcaster, NONE-bound with the broadcaster as `assignedProver` (the fixtures are public, §3a): `TestFulfill` claims a `script/job-submitter.sh` job only when its `ASSIGNED_PROVER` is the broadcaster, and every `LiveE2E` phase runs on the same key.
- **Script claims carry exact floors, never a literal 0.** `script/lib/FulfillGas.sol` `quoteClaim` simulates `claimJob(jobId, 0, 0)` as the claiming account at the block the script forks (rolled back) and reads `getPremiumCap` there; `claimAtQuote` quotes and then broadcasts `claimJob(jobId, price, premiumCap)` from the same account (a reset ordered ahead of the claim makes it revert `ClaimBelowFloor` instead of locking lower); `slashFloor` gives the `slashAndClaim` rescue floor (computePrice at the live lock's `elapsedAtLock`). Before a live-chain claim, `requireClaimable` refuses a job that is not Open or whose descriptor hash is not the one the fulfil run rebuilds, and the job id comes from the **mined** `JobSubmitted` log of the submit run's receipt, never from a simulated `submitJob` return (any foreign submit mined first shifts it). `TestFulfill.s.sol` `claim()` prints `CLAIM_PRICE_FLOOR=<wei>` and `CLAIM_PREMIUM_FLOOR=<wei>`. `LiveE2E.s.sol` on a live chain is four runs, each after the previous one's receipts: `runSubmit(address)` (prints the `jq` that reads `JOB_IDS` from its mined receipts), `runClaim(address,bytes32[])`, `runFulfillLocked(address,bytes32[])`, `checkFulfilled(address,bytes32[])`; `DemoInteraction.s.sol` `step2_submitJob` prints the command that reads `JOB_ID` from its receipt.
- **The one-transaction script path.** `script/TestFulfill.s.sol --sig 'claimAndFulfill()'` (env as `claim()`) sends `claimAndFulfillAssigned` for a `script/job-submitter.sh` drill job in one run: `requireClaimable`, the exact floors, then `FulfillGas.claimAndFulfillAtQuote`, which refuses (reverts) unless the descriptor assigns the job to the broadcaster and is NONE-bound or carries a binding marker (§4, "When it is safe"), and sends with the explicit `{gas: N}` of `forClaimAndFulfillAssigned`. It prints `CLAIM_PRICE_FLOOR`, `CLAIM_PREMIUM_FLOOR` and `FULFIL_GAS_LIMIT`. The drill jobs qualify: NONE-bound, assigned to the broadcaster, and submitted by the operator's own submitter, the one party that could cancel ahead of the transaction.

## 12. Common pitfalls

- **Approving the wrong contract**: HEMI approve for `submitJob` goes to `HEMIPROVE` (router); HEMI approve for `stake` goes to `STAKING`. Two different `approve` calls needed.
- **Descriptor hash mismatch on fulfill**: pass the *exact same* descriptor struct at fulfill — any byte diff in `inputData` / `extraVerifierData` / the binding words reverts `InvalidDescriptorHash`. Cache it off-chain, or read it back from the submit calldata.
- **A job with no binding**: `expectedJournalHash == 0` without an `assignedProver` reverts `InvalidJournalBinding(3)` at submit. Bind FULL or FIELDS (§3a), or name your prover (NONE).
- **A binding over re-encoded bytes**: `expectedJournalHash` must hash the bytes the guest actually committed (serde / bincode framing included). A FIELDS pin computed over `abi.encode(input)` when the guest committed `env::commit(&input)` never matches, and the claiming prover is slashed. Test the binding against a real journal before going live.
- **Pins that bind nothing, or only part of the input**: a pin on a constant header or version word, a pin that leaves out a length word or an ABI head offset, a pin placed after a variable-length field, a word the consumer rebuilds from `msg.sender` left free. Each lets a proof of another input settle. Follow the binding cookbook (§3a) and run the mutation check.
- **Same-block claim**: a prover cannot `claimJob` in the block their stake landed — the next block already unblocks. Enforced via `StakingBlockDelayNotMet`; there is no wall-clock minimum staking age.
- **Post-activity withdraw cooldown**: after any settlement event (fulfill / release / slash / bid refund / grace), the prover's `withdrawUnstaked` reverts `PostActivityCooldownActive` for `MIN_POST_ACTIVITY_COOLDOWN` (1 hour). Off-chain daemons read `IHemiProveStaking.lastProverActivityAt(prover)` (view) or subscribe to `ProverActivityMarked` to compute the earliest safe withdraw time.
- **Release cooldown**: after releasing or grace-pause-releasing a job, or taking its own governance-cause bid refund (only one taken before `wallBidDeadline`), the same prover cannot claim it or bid on it for 1 hour (`ReleaseCooldownActive`).
- **Raw deadlines**: `jobs().lockDeadline` and `JobClaimed.lockDeadline` are raw. A keeper that slashes at the raw deadline after a pause wastes gas ("Not expired yet"); read `getJobExtras(jobId).pauseCredit` or `getJobStatusView`. The slash opens 30 min + 30 s after the effective deadline: schedule from `getJobStatusView(jobId).slashOpensAt`.
- **Descriptor size**: `inputData + callbackExtraData + extraVerifierData` over 65,536 bytes reverts `DescriptorTooLarge` at submit. Put large witnesses behind a hash in `inputData` and have the guest commit that hash.
- **Journal size**: a journal over 32,768 bytes reverts `JournalTooLarge` on every fulfil path, and a FIELDS slot ending past it reverts `InvalidJournalBinding(5)` at submit. Guests that need more output commit a digest of it.
- **`fulfillJob` gas**: see §9. Under-provisioned tx reverts with `InsufficientGasForFullSettlement()`. Use the §9 formula or `eth_estimateGas`; a `forge script` gas multiplier is not reliable, and `forge script` sizes every transaction from the simulation even without one: pass an explicit `{gas: N}` (`script/lib/FulfillGas.sol`) and run claim and fulfil as separate runs on live chains.
- **Treating a bid as an option**: a live bid is binding. `refundBid` reverts `NoGovernanceCause` unless the adapter is Disabled or Unregistered or the custom verifier is blacklisted; a pause frees the bid only after 7 days; `releaseJob` on an Open job reverts `JobNotLocked`. The walk-away is settle, then fulfil or release at the snapshotted penalty (`getJobSnapshots`, §4): price it into the bid, and fund the soft-lock for `maxBiddingDuration` + pause credit + up to 7 days of pause (for a won round left unsettled when a pause begins: the whole pause).
- **Reading the premium**: `speedPremium` is the deposit, not what a fulfil earns; read `getPremiumCap(jobId)`, the budget left. A fulfil is paid `max(0, u − used)`, which is less than the cap whenever the lock has held for a while (§5). Only Dutch jobs carry a premium: `getPremiumCap` is 0 on a competitive job.
- **Fulfilling at the last second**: a fixed margin does not hold against inclusion delay on Hemi. Fulfil as soon as the proof exists and escalate the tip on the same nonce (§6, "Inclusion delay"). The fulfil is accepted until 30 min after the effective deadline (speed bonus 0 after it); one that lands later publishes your proof for the next `slashAndClaim`-er (§6, "Late locks").
- **Broadcasting a proof before your lock is mined**: a `multicall([claimJob, fulfillJob])`, a fulfil nonce-pipelined behind its claim, a `multicall([slashAndClaim, fulfillJob])` rescue, a reverted fulfil, an `eth_call` of the fulfil to an RPC you do not run, or a proving-market request (Boundless, the prover network) posted before your lock: each shows your seal to someone who can take the lock first and settle with it. Claim alone (at exact floors, §4), wait for the receipt, re-read `jobs(jobId).prover`, then fulfil (§3a).
- **Releasing on a governance state**: `RegistryPaused`, `AdapterDisabled`, `BlacklistedVerifier` and `EnforcedPause` at fulfil mean keep the lock (it is credited), not release (5%); re-read the Registry before acting on `VerifierCallFailed` (§5); for a `CUSTOM_VERIFIER` job only a blacklisted verifier is a cause, not a Registry pause.
- **Claiming without a floor**: `claimJob(jobId, 0, 0)` in a real send, or a floor seeded from `jobs(jobId).minPrice`, `getCurrentPrice` or a `pending` read, locks at whatever price a reset ordered ahead of you leaves (residuals 16(a), 16(l)). Quote with an `eth_call` at a mined block, send that exact price and `getPremiumCap`, and on `ClaimBelowFloor` or `BiddingActive` wait and retry; never chase the price down.
- **A competitive job with a premium, or a short window**: `speedPremium != 0` with `underbidWindow > 0` reverts `SpeedPremiumOnCompetitiveJob()`, and `underbidWindow < 300 s`, `maxBiddingDuration < underbidWindow`, `maxBiddingDuration > 7 days` or a `maxBidExtension` from 1 to 59 s reverts `InvalidBidConfig()` at submit. Anti-snipe extensions need `maxBiddingDuration > underbidWindow`. An `exclusivityDuration` from 1 to 59 s reverts `InvalidExclusivityDuration` (0 or at least 60 s; also in `setPreset`).
- **Two senders on one staked key**: two daemons (`job-prover.sh` and `demo-prover.sh` included), a bidding tool or hand sends on one key replace each other's pending claims and fulfils at the same nonce. One sender per staked key (§3a); the reference daemons refuse a second instance only on the same host.
- **An SP1 proof from the wrong SDK or in the wrong mode**: both SP1 verifiers are circuit v6.1.0, one per wrapper. A proof of SP1 SDK 6.0.0 to 6.0.2 (prefix `0x0e78f4db` Groth16, `0xbb1a6f29` PLONK, advisory GHSA-63x8-x938-vx33), a seal of the other wrapper (a PLONK seal on an `SP1_GROTH16_V1` job, a Groth16 seal on an `SP1_PLONK_V1` job: `WrongVerifierSelector`) or a TEE-wrapped one reverts `VerifierCallFailed` at fulfil, and the lock costs 5% (release) or 100% (slash). Prove with SDK 6.1.0 to 6.10.0 (circuit v6.1.0; 6.8.1 is the release this repository builds and tests with; pinned; re-check on every upgrade) in the mode the job's `proofSystemId` names, and check that the seal starts with that verifier's `VERIFIER_HASH()[0:4]` (`0x4388a21c` Groth16, `0x5a093a2f` PLONK) before you claim (§3a, step 7).
- **A nonce-bound SP1 job proved without its nonce**: a stock `sp1-prover` (6.1.0 to 6.10.0 drop `with_proof_nonce`) or the Succinct prover network (it ignores the nonce) makes a valid proof with nonce 0, and the fulfil reverts `ProofNonceMismatch(expected, 0)`. Prove locally with a fixed or patched `sp1-prover`, and compare `seal[68:100]` with `getProofNonce(jobId, yourStakedProver).nonce` before you claim (prove first) and before you fulfil: `Registry.verifyProof` does not check it (§3a, step 7a). The address is the staked prover's, never an operator key's.
- **A journal prefix framed by `commit`**: the prefix must be the journal's first 64 raw bytes, `abi.encode(jobId, prover)`, committed with `commit_slice` before the output; `commit` adds serde or bincode framing, and alloy `abi_encode()` of a struct with a dynamic member puts a `0x20` offset word first. Either reverts `JournalPrefixMismatch` (§3a, "Binding markers").
- **A RISC Zero receipt from the wrong toolchain or of the wrong type**: the RISC Zero verifier is risc0 3.0 (`SELECTOR()` `0x73c457ba`). A risc0 5.x receipt, a Boundless set-inclusion seal, a dev-mode receipt or a non-Groth16 receipt reverts `VerifierCallFailed` at fulfil, and the lock costs 5% (release) or 100% (slash). Prove with risc0-zkvm 3.0.x (pinned; re-check on every major bump) in Groth16 mode, and check the seal's prefix and a local `Registry.verifyProof` before you claim (§3a, step 8).
- **Building a requester's source, or running cargo in its files, on your key host** (provers): a Cargo build runs the crate's build scripts and procedural macros, and rustup and cargo read `rust-toolchain.toml` and `.cargo/config.toml` from the working directory and every parent before any flag (a toolchain `path` replaces `cargo`, an `[alias]` a subcommand), so a requester's tree is code the requester runs on your machine. `cargo openvm commit`, `run` and `prove` build the working directory's crate unless given `--exe`. Check and prove from published artifacts (an ELF; an OpenVM `.vmexe` and its `openvm.toml`) kept as plain files, from a working directory of your own, and launch any source rebuild (`cargo prove build --docker`, `cargo risczero build`, a registry entry's `buildCommand`) inside a disposable sandbox with no key (§3a, steps 2a and 9). Requesters: publish those artifacts.
- **Running a binary that is not the job's program** (provers and requesters): `programId` (the RISC Zero image id, the SP1 vkey, the OpenVM commitments' hash) is the only tie between a job and a binary. A prover that runs whatever the caller, `inputData` or a registry entry points to can be handed a decoy with the same journal: every check passes until the fulfil reverts. Provers: compute the image id / vkey of the binary and compare it with `programId` before executing it (§3a, step 2a). Requesters: publish the exact binary your `programId` names (a reproducible build and its image id / vkey); an output-identical rebuild has another id, so provers who fetch it from a mirror or a squatted registry entry can never fulfil your job.
- **Deposit and collateral bounds**: the deposit `maxPrice + speedPremium` must fit in `uint96` (`DepositOverflow`), a job's `cycleCommitCollateral` may be at most `2 × maxPrice` (`CycleCollateralCapExceeded`), and the largest lock collateral, `ceil(maxPrice × bps / 10,000)`, must fit in `uint96` (`CollateralOverflow`). The total pulled at submit (deposit plus cycle collateral) is computed in 256 bits. Very large jobs may need to be split.
- **An unstake request can become irrevocable**: a pending unstake does not count against the Staking cap (`maxTotalStaked`), so a `requestUnstake` frees room under it. Once someone else stakes into that room, your `cancelUnstake` counts back only what room is left and reverts `MaxTotalStakedExceeded` when there is none: the request then stays pending for the whole 7-day `UNSTAKE_COOLDOWN`. While it is pending you cannot request another (`PendingUnstakeConflict`), and a claim or bid whose collateral would overlap the pending amount reverts `PendingUnstakeConflict`. Request only what you mean to withdraw, and expect it when the cap is nearly full. (On the 743111 rehearsal the cap is set out of reach, 2^200, so this is not rehearsed there.)
- **Staying staked through a `RevokeGuardianProposed`** (provers, committee members, requesters): the GT guardian's veto is the control against a compromised GT owner, and the owner can remove the guardian only with `proposeRevokeGuardian`, which takes effect 14 days later (`REVOKE_GUARDIAN_DELAY`; `RevokeGuardianProposed(readyAt)`). Treat every `RevokeGuardianProposed` as the start of your exit window, announced or not (a compromised owner can announce too). Stop claiming and bidding. **Fulfil every live lock you can fulfil within 7 days of the event** (`getJobStatusView(jobId).slashOpensAt`): a fulfil pays you and frees the collateral as on any day, and a bid you win you fulfil within a day of its settle. Take a free exit when one opens: `gracePauseRelease` once the router has been paused for 15 min, `graceRelease` or `refundBid` while the adapter is disabled or the custom verifier blacklisted. Release at the snapshotted penalty (5% at the defaults) only a lock you cannot fulfil by then (in Committee mode a fulfilled job's cycle collateral stays deferred until its epoch resolves, so there a release can be right). Then send **one** `requestUnstake` of your whole free stake. With a request already pending, `cancelUnstake` and request the total again if the Staking cap has room; if the cancel reverts `MaxTotalStakedExceeded`, let the pending part mature, withdraw it and request the rest at once. Withdraw as each request matures (7 days, and 1 hour after your last settlement). Done this way your stake is out by 338 h after the event, before the earliest drain a compromised owner can reach (384 h). Committee members request at once (14-day cooldown); requesters cancel their Open jobs. An Open job with a live bid reverts `cancelJob` with `BidsActive`: settle the bid at its round end (`settleBid`, anyone, at `wallBidDeadline`) and cancel; if the owner queues a verifier swap (`OperationProposed` of `disableAdapter` and `reactivateAdapter(psId, <new>)`, 24h ahead), act inside its disable window (at least 1h): after the round end `settleBid` drops the bid under the governance cause, or `graceRelease` evicts a settled lock, then `cancelJob` refunds in full; `cancelStaleJob` follows 7 days of a disable. `DEPLOY_RUNBOOK.md`, "Guardian revocation", has the timeline.
- **Unknown custom verifiers** (provers): a `CUSTOM_VERIFIER` job's caller controls verification and can make an honest proof fail after you claim. Collateral on such jobs is `max(price × lockCollateralBps (≤ 100%), MIN_COLLATERAL_AMOUNT)`: with the 100 HEMI floor of the live chains a 1-HEMI job puts 100 HEMI at risk. What you lose is burned, except the keeper share (`max(2%, 0.5 HEMI)`), which the caller can take through a sybil keeper. A custom verifier that wraps a governance adapter or `Registry.verifyProof` is outside the Registry's disable and pause protections (an adapter disable does not credit it). Allow-list immutable verifiers by codehash before claiming.
- **An OpenVM job bound like an SP1 or RISC Zero job**: the OpenVM verifier takes exactly 32 public-value bytes, so an `OPENVM_HALO2_V1` submit refuses the journal-prefix marker and any FIELDS range ending past byte 32 (`InvalidJournalBinding(7)`), and the nonce marker is SP1's (`InvalidJournalBinding(6)`). Its proof binds the statement only. Provers: `programId` is `keccak256(abi.encode(appExeCommit, appVmCommit))`, not the executable commitment alone, and an unverified malformed proof can burn the whole 4,000,000-gas verifier budget (§3a, step 9).
- **Claim and fulfil in one transaction on an unbound job**: `claimAndFulfillAssigned` publishes the proof while the job is still Open. On a job without a binding marker the caller can cancel ahead of it and resubmit the statement for another prover, and a window job's transaction held past the window end reverts `NotReserved` with its proof public. Use it for a bound job, or for a requester you trust with at least 60 s of window left; otherwise claim first (§4).
- **A callback address without code**: it is not called, and the fulfil emits `CallbackFailed(jobId, callback, "")`; the job settles and the prover is paid. Deploy it before the fulfil (a CREATE2 address may be named at submit) and check the code on the target chain (§5).
